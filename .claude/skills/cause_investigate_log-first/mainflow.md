## 絶対に守ること（全段を通して）

- **実機（本番で動いているダッシュボード）は読むだけ。** `bin/collect` は `ad logs` と `ad state-dir` しか呼ばない。書き込み・再起動系の CLI（`version restart` 等）は本スキルの範囲外——絶対に呼ばない
- **`MyDocs/イシュー/` 配下へは書かない。** `bin/report-draft` の既定出力先は一時フォルダで、実イシューの `調査レポート/` へ置くかどうかは呼び出し側（このワークフローを使っている人間または上位のスキル）が判断する
- **このスキルのフォルダ（`.claude/skills/cause_investigate_log-first/`）以外へは書かない。** ログの採取物・下書きレポートは、すべて呼び出し側が指定した出力先（既定は一時フォルダ）に置く

## 3つの不変条件

1. **直さない。** このスキルは原因の当たりを付けて下書きを残すところまでで、コードの変更は一切行わない。「直したくなる」発見があっても、それは「次に読むコードの場所」へ書き留めるだけに留める
2. **コードを読むのは段4の後。** 段0〜段4はログだけを材料にする。`report-draft` の「次に読むコードの場所」欄は、ファイルパスを**書き添えるだけ**で、その場でファイルを開いて読むことはしない——読むのはこのワークフローの外（呼び出し側が次に行う作業）
3. **ログに何も無いときは「無い」も成果。** 該当する行が0件だったこと自体が調査結果であり、失敗ではない。`bin/collect`・`bin/narrow`・`bin/report-draft` はいずれも0件を異常終了させず、「無かった」を明示して先へ進める

## §12-1　入口

呼ばれる場面：ダッシュボードや、そこが動かしているセッションホスト／ブラウザ／パーサのどこかで異常（エラー・警告・意図しない挙動）が疑われ、**まだコードを1行も読んでいない**段階。

登場人物：
- **主**（この手順を進行する側。ワークフロー全体の判断を持つ）
- **ワーカー**（段2で、窓の数が多く並行して目を通したいときだけ登場。`subagent_type: "general-purpose"` かつ `model: "sonnet"` で起動する）

道具（すべて `bin/` 配下、実行権限つき）：
- `bin/collect` — 段0＋段1
- `bin/narrow` — 段2
- `bin/report-draft` — 段4

## §12-2　手順（段0〜段4）

### 段0：いま何が動いているかを見る

**誰がやるか：主**

`bin/collect` を呼ぶと、内部で自動的に `agentdashboard running-state --json` を実行し、採取フォルダに `running-state.json` として残す（生きているカード・プロセスの一覧）。単独で見たい場合は `_shared/bin/running-state` を直接呼んでもよい。

**止まる条件：** 実機のプロセスそのものが見当たらない（`running-state` が空／エラー）場合、ログを採っても手がかりが無い可能性が高い。ここで一度止まり、対象が本当に動いているかを人に確認してから先へ進む。

### 段1：ログを採る

**誰がやるか：主**（分担が要るほど広い調査であれば、後続の段2でワーカーへ渡す前提で主がまとめて採取する）

```
bin/collect --since <期間> [--split <分>] [--card <ID>] [--grep <語>] [--level <水位>] [--out <出力先>]
```

- `--state-dir` は `bin/collect` が実機ツリーから自動解決するので、呼び出し側は指定しなくてよい（`ad logs` 自体は `config.toml` を読まない——読むのは `ad state-dir` の方だけで、`--state-dir` を渡さず `ad logs` を直接叩くと既定値を黙って読み0件を返す）
- `--split <分>` を付けると、採取したログを時刻でN個の `window-NN.jsonl` に分割する。**この分割は、段2で窓ごとにワーカーを1体ずつ割り当てて並行して目を通すためのもの**（窓1つ＝ワーカー1体）。分割しない場合は `window-01.jsonl` 1本になる
- 出力先は引数で指定する。省略した場合は一時フォルダの下に採取フォルダを作る

**止まる条件：** `--state-dir` の解決に失敗した、または指定した窓に1行もログが無かった場合、`collect` はエラーにせず「無かった」旨を出して空の `window-*.jsonl` を残す。**ここで諦めて即「無い」と結論づける前に、`--card` の値・`--since` の長さ・`--grep` の綴りを一度だけ疑い直す。** それでも無ければ、不変条件3のとおり「無い」を成果として段2・段4へ進めてよい。

### 段2：経路ごとに集計する

**誰がやるか：主**（既定）。ただし窓の数が多い、または1窓あたりの行数が多く生の中身にも目を通したいときは、**窓の数だけワーカーを並行起動し（1体に1窓）**、各ワーカーに担当窓の代表的な行（`narrow` の error/warn 一覧や、生JSONLの該当箇所）を持ち帰らせ、主が統合する。並行起動するワーカーは必ず `subagent_type: "general-purpose"` かつ `model: "sonnet"` で起動すること——これを省くと意図せず高いモデルで走り、読むだけの作業に見合わないコストになる。

```
bin/narrow <collectの出力フォルダ> [--card <ID>] [--top <N>] [--json]
```

`knowledge/paths.md` の表に沿って `target` を経路（ブラウザ／サーバ／セッションホスト／パーサ）へ分類し、経路ごとの件数・代表 target・error/warn の先頭N件を表にする。`--card` を付けると1枚のカードに絞った集計になる。

**止まる条件：** 経路の表が全経路0件だった場合、段1の採取条件（窓・カード・grep）を一度だけ見直して段1へ戻ってよい。見直しても0件なら、不変条件3のとおり「無い」を確定として段3・段4へ進む。**0件を確定させるために際限なく採り直さない**——1回の見直しで区切りを付ける。

### 段3：当たりを付ける（判断）

**誰がやるか：主**

段2の集計（と、あればワーカーの持ち帰り）から、次を判断する。

- **どの経路が怪しいか**（`narrow` の件数・error/warn の内容から）
- **再現条件は言語化できそうか**（同じ card_id・同じ時間帯・同じメッセージパターンが繰り返し出ているか）
- **段1へ戻るべきか**（窓の範囲がずれている・grep が的外れだった等） → 戻る場合は段1からやり直す（ループ可）
- **段4へ進んでよいか**

複数の経路にまたがっていて1つに絞れない場合、**無理に1つへ決め打ちしない**。複数経路のまま段4へ渡す。

**止まる条件：** 段1・段2を1往復し直しても手がかりが増えない場合、それ以上ループせず、分かった範囲（「無い」を含む）で段4へ進む。

### 段4：レポートの下書きを書く

**誰がやるか：主**（分担していた場合はワーカーの持ち帰りを主が統合してから書く。下書き自体は `bin/report-draft` を叩く1回の操作なので、通常はワーカーへ委譲しない）

```
bin/report-draft --title <タイトル> \
  --repro <再現条件> --path <経路> \
  --code <次に読むコードの場所（複数回指定可）> \
  --unconfirmed <確かめていないこと（複数回指定可）> \
  [--since <期間> --card <ID> --grep <語> --level <水位>] \
  [--out <出力先>]
```

`--since`／`--card`／`--grep`／`--level` のいずれかを指定すると、`report-draft` が内部で `ad logs --sanitize` を直接叩き、**サニタイズ済みの該当行**を「該当行」欄に埋め込む。伏せ字にできるのは `ad logs` の出力そのものだけなので、既に手元にある生ログを後から伏せる道は無い——貼りたい行があるなら、その行を再現できる条件（card/grep/since）で `report-draft` に取り直させる。

出力される下書きは「再現条件／経路／該当行／次に読むコードの場所／確かめていないこと」の枠を持つ Markdown 1本。**出力先は既定で一時フォルダ**——実イシューの `調査レポート/` へ置くかどうかは、このワークフローを使っている側（人間または上位のスキル）が判断する。このスキル自身は実イシューへ書かない。

**止まる条件：** 再現条件が言語化できない場合でも、分かる範囲を書き「確かめていないこと」へ明記すれば下書きとして完成とみなす。空欄のまま出すことを恐れない——空欄も「まだ分かっていない」という正確な情報である。

## §12-3　止まる条件（全体まとめ）

| 段 | 止まる条件 | 対応 |
|---|---|---|
| 段0 | 実機のプロセスが見当たらない | 対象が動いているか人に確認 |
| 段1 | state-dir 解決失敗／該当ログ0件 | 条件を1回だけ見直す→それでも0件なら「無い」を確定 |
| 段2 | 経路の表が全経路0件 | 段1へ1回だけ戻る→それでも0件なら「無い」を確定 |
| 段3 | 1往復しても手がかりが増えない | ループを打ち切り、分かった範囲で段4へ |
| 段4 | 再現条件が言語化できない | 空欄のまま出す。実イシューへ書くかは呼び出し側判断 |

**このワークフロー全体を通して、コードファイルの編集・実機への書き込み・`MyDocs/イシュー/` への書き込み・git commit は一度も行わない。**
