# 改善記録

このスキルの実行中に起きた、**手順どおりにやったのに期待どおりにならなかった事象**をここに記録する。

記録したら、対処が手順に落とせるものはその場で `mainflow.md`（または `knowledge/why-not-red.md`）へ反映すること。**ここに書いただけでは次回の失敗を防げない。**

---
<br/>
<br/>

## 記録する対象

- `bin/check-docs` の named test 存在チェックが、実在するテストを見逃した・存在しないテストを拾ってしまった（バッククォート抽出の誤検出／見落とし）
- `bin/check-docs` の「実行レポート.md の最終フェーズ」の切り出しが、実際の最終フェーズと違う範囲を拾った
- `bin/ledger-lookup` のパス解決が、意図した子イシュー／グループと違うものに一致した（前方一致のしすぎ・足りなさ）
- `bin/revert-check` の worktree 作成・ビルド・`our-servers count`・テスト実行のいずれかで、想定と違う終了コードや出力形式が返った
- `--strong` で指定した第二の壊し方が、実は第一の壊し方と同じ原因を踏んでいて、独立した確認になっていなかった
- `sandbox-dashboard`（`_shared/bin/`、フェーズ5-C で別途整備中）と `revert-check` の役割分担が、実際に両方使ってみたら想定と違っていた
- §9-4「配る版の検査」の判定が、タグ実在の確認方法（ローカル `git tag` とリモートの食い違い等）によってぶれた

---
<br/>
<br/>

## 記録しないもの

- 一度きりの偶発的なミス
- 外部要因（ネットワーク断、ディスク逼迫など）
- **手順を実行しなかったことによる失敗**（それは手順の問題ではない。ただし「守られない手順」が繰り返されるなら、それは書き方の問題なので記録する）

---
<br/>
<br/>

## ファイル名

`YYYY-MM-DD_何が起きたか.md`（日本語可）。**症状ではなく、そこから得た教訓が分かる名前にする。**

---
<br/>
<br/>

## 中身

1. **何が起きたか**（観測した事実。推測と分けて書く）
2. **なぜ起きたか**（分かった範囲で。分からなければ「未特定」と書く）
3. **どこを直したか**（`mainflow.md` や `knowledge/why-not-red.md` をどう変えたか。直していないなら「未対応」と理由）
