# ワークフロー：issue-close_verify

イシュー（またはイシューグループ）を閉じる前に、「閉じてよいか」を検収するスキル。**このスキル自身はイシューを閉じない。回帰台帳（`regressions.toml`）へは書き込まない（下書きの印字まで）。共有ツリーに対して `git stash`／`git checkout`／`git reset`／`git commit` を行わない。** `bin/revert-check` が一時的に作る `git worktree` だけが例外で、検査が終わったら必ず自分で消す。

判定はどのフェーズも「OK」か「不足」の2値で出す。**不足が出ても、このスキルはその場で直しに行かない。** 直すのは閉じる本人（または委譲された別のワーカー）の仕事であり、このスキルは最後まで検収に徹する。

対象がイシューグループ（`メタ.md` を持つフォルダ）か単一イシュー（`要件.md` を直下に持つフォルダ）かで、§9-2 と §9-3 の扱いが分かれる。イシューグループには専用の `計画.md` が無く、`テスト計画.md` のフェーズ表が作業計画を兼ねる。台帳の `issue` 列は、グループの場合は「子イシューごとのパス」で入っている（`クローズ/<グループ名>/<子イシュー名>` の形。グループの bare パスでは入らない）。

## §9-1：入力の受け取りとスコープ判定

**メインが行う。** テキスト処理だけの軽量な判定なので、委譲しない。

1. 引数で渡されたパスを `MyDocs/イシュー/` 配下で解決する（絶対パス・相対パス・フォルダ名のどれで渡されても解決できるよう、`bin/check-docs` と `bin/ledger-lookup` が内部で同じ解決ロジックを持つ）
2. 直下に `メタ.md` があればイシューグループ、`要件.md` があれば単一イシューと判定する
3. どちらも無ければ入力エラーとして即座に停止し、利用者へパスの確認を求める

**stop condition**：対象が一意に決まった時点で次へ進む。決まらなければここで止まる。

## §9-2：文書と実態の突き合わせ

**メインが `bin/check-docs` を直接呼ぶ。** grep ベースの軽量なテキスト処理なので委譲しない。

```bash
.claude/skills/issue-close_verify/bin/check-docs "<イシューまたはイシューグループのパス>"
```

何を確かめるか：

1. 実行レポート.md の**最終フェーズ**に「配る・手元」への言及があるか（プロジェクト CLAUDE.md の「計画とテスト計画の最終フェーズに、アップデートを含める」規約への準拠を、実行レポート側からも確認する）
2. 計画.md／テスト計画.md でチェック済み（`- [x]`）の項目が挙げる named test が、実際に `server/` または `web/` のコード中に存在するか（バッククォートで囲まれた語を拾い、grep の件数で確かめる。**これは存在の有無を見る簡易な検査であり、そのテストが実際に該当項目を守っているかまでは保証しない**——名前の一致だけを見ている点は、利用する側が承知しておくこと）
3. 【要人間】／【保留】の一覧を出す（直しはしない。存在を報告するだけ）
4. イシューグループの場合、グループ自身には `計画.md` を要求せず、`テスト計画.md` のフェーズ表を代用する。子イシューごとに 1〜3 を繰り返す

出力の先頭行は `判定：OK` または `判定：不足`。不足の場合は具体的な文書名・欠けている項目を列挙する。

**stop condition**：`bin/check-docs` の出力が確定した時点で次へ進む（不足が出ていても §9-3 には進む——最終判定は §9-5 でまとめて出す）。

## §9-3：回帰台帳の下書きと「戻すと落ちる」検査

### 手順1〜2：台帳の下書き

**メインが `bin/ledger-lookup` を直接呼ぶ。** 読み取りと印字だけなので委譲しない。

```bash
.claude/skills/issue-close_verify/bin/ledger-lookup "<イシューまたはイシューグループのパス>"
```

既存の行があればそれを列挙し、`tests[].file` が実在するかも確認する。行が無ければ、クローズ後のパス（POST-close path）を `issue` に持つ下書き雛形を印字する。

> ⚠ **このツールは台帳に一切書き込まない。** `_shared/bin/claim` も呼ばない——実際に台帳へ書くのは閉じる本人の仕事で、その際は本人が `claim` で札を取ってから書く。それはこのスキルの外側の作法である。

### 手順3〜6：「戻すと落ちる」検査（`bin/revert-check`）

対象の振る舞いを守っている（と主張する）コミットを戻したときに、名指しされたテストが実際に赤くなるかを確かめる。

**まず `--dry-run` で手順を確認する（メインが行う。印字だけなので軽い）：**

```bash
.claude/skills/issue-close_verify/bin/revert-check --dry-run \
  --commits <hash> [<hash>...] \
  --tests <file:name> [<file:name>...]
```

**実際に検査を回す（`--dry-run` を外す）ときは、Agent ツールで `subagent_type: "general-purpose"`、`model: "sonnet"` を明示してワーカーへ委譲する。** 理由：`make build-web build-debug` を伴うため数分単位で時間がかかり、メインのコンテキストと時間を消費させないため。委譲を省くと、エラーは出ないまま上位モデルがメインで直接重いビルドを回すことになり、費用だけ増える。

```bash
.claude/skills/issue-close_verify/bin/revert-check \
  --commits <hash> [<hash>...] \
  --tests <file:name> [<file:name>...] \
  [--strong]
```

`--strong` は、同じ振る舞いを壊す**別の壊し方**（`--commits` の部分集合や、別の1手）でも同様に赤くなることを追加で確かめる。二重に確かめたいときだけ付ける。

内部の流れ（`--dry-run` はこれを印字するだけで実行しない）：

1. スクラッチパッド配下に `git worktree add --detach` で一時 worktree を作る
2. `--commits` で渡された各コミットを `git revert --no-commit` で逆当てする（worktree の中でも `git commit` はしない——最大限保守的に、コミットという確定操作そのものを避ける）
3. worktree 内で `make build-web build-debug` を回す
4. `.claude/skills/_shared/bin/our-servers count --bin <worktree の実行ファイル>` で、自分が建てたバイナリが既に動いていないかを確かめる。0 でなければ、他セッションと衝突する可能性があるため**それ以上進まず中止**し、検出した PID を報告する（自動では殺さない）
5. `--tests` で渡された named test を実行する（`.rs` は `scripts/cargo test`、`.ts`／`.tsx` は `web/` 配下で `npx vitest run -t <name>`）
6. 各テストが赤くなっていることを確認する。赤くならなければ `bin/revert-check` は「不成立」として理由（§9-4 参照）とともに報告する
7. 成功・失敗を問わず、`trap` で必ず `git worktree remove --force` を実行してから終了する

> ⚠ **赤くならなかったとき**：`knowledge/why-not-red.md` の4項目の疑う順序に従って原因を切り分ける。このツールはその判定材料（何が緑のままだったか）を報告するところまでで、原因の特定や直しはしない。

**stop condition**：一時 worktree の後始末（`git worktree remove`）が完了するまでは終了しない（`trap` で保証する）。`our-servers count` が非0のときは、その時点で中止して報告する。

## §9-4：配る版の検査

**メインが行う（読み取りのみ）。** 重い操作を伴わないので委譲しない。

プロジェクト CLAUDE.md「イシューを1つ消化したら、サーバも手元もアップデートする」の4段表に照らし、**段1（配る）**が実在するかだけを確かめる。

- 対象イシューのクローズに対応する git tag（またはリリース）が実在するか（`git tag --contains <クローズのコミット>` 等）
- 実行レポート.md の最終フェーズが「配る・手元」に触れているか（§9-2 と重複する範囲は §9-2 の結果を参照し、ここでは**配布物側の実在**だけを見る）

**段2（サーバ）は既に廃止されているため検査対象外。** **段3（手元）・段4（効かせる）は、このスキルが実行することも要求することもしない**——段4は「人が頼んだときだけエージェント」という明示のルールがあり、このスキルの検収作業の範囲外である。段3の実機ビルドも同様に、このスキルは求めない（§9-3 の `revert-check` が使い捨て worktree で行うビルドとは別物であることに注意——あちらは検査用の使い捨て、こちらは配布物の実在確認）。

**stop condition**：タグ／リリースの実在が確認できれば OK。確認できなければ「不足：配る（段1）が確認できない」として理由を添える。ネットワーク越しの確認（GitHub 上のリリース確認等）ができない環境では、その項目を【保留】として扱い、判定を止めない。

## §9-5：出力

**メインが行う。** §9-2〜§9-4 の結果を次の形にまとめて返す。

```
## issue-close_verify 結果

対象：<path>
種別：単一イシュー ｜ イシューグループ
判定：OK ｜ 不足

### §9-2 文書と実態
<check-docs の判定と根拠（不足なら具体的な文書名・項目）>

### §9-3 回帰台帳
- 台帳の行：<あり／なし（無ければ下書き雛形を添える）>
- 「戻すと落ちる」検査：<未実施（--dry-run のみ）／確認済み（赤くなった）／不成立（赤くならなかった。理由）>

### §9-4 配る版
<OK／不足と理由>

### 【要人間】
<一覧。無ければ「無し」>

### 【保留】
<一覧。無ければ「無し」>
```

**判定ルール**：§9-2・§9-3・§9-4 のいずれかが不足なら全体は「不足」。3つとも揃って初めて「OK」。**この判定はあくまで検収結果の報告であり、このスキル自身がイシューを閉じたり台帳へ書き込んだりすることはない。**
