# memory_improvement — ui_verify の自己改善記録

このスキル自身の動作・判定基準に問題があったときの記録場所。SKILL.md の「自己改善ルール」から参照される。

---
<br/>
<br/>

## 記録する条件

- 実行中にエラー・想定外の挙動が起きたとき
- 利用者から指摘・修正依頼を受けたとき
- 外部ツール（`sandbox-dashboard`・`our-servers`・`browser_operate`）の挙動が変わったと分かったとき
- 稼働終了時に「無駄だった読み込み・往復」が1つでもあれば、**問題が起きなくても書く**（設計.md §4-3）。効率だけが落ちている回は、問題として現れないため

---
<br/>
<br/>

## 記録しない条件

仕様どおりに動いたのに、単発の操作ミス（手順を1つ飛ばした等）をしただけのとき。このスキル自体の動作に問題がない場合（プロジェクト側の問題だった場合）は、ここには記録しない（`~/.claude/CLAUDE.md`「スキル自己改善フックへの対応ルール」）。

---
<br/>
<br/>

## 書き方

1ファイル1件、ファイル名は `YYYY-MM-DD_<短い見出し>.md`。中身は3項目のみ。

- 何が起きたか
- なぜ
- どこを直したか（直さなかった場合は、その旨と理由）

<br/>
<br/>

## 自己進化の反映（設計.md §4-3）

起動時に自分の `PROPOSAL.md` の未完了行（`[ ]`）を読む。手順を1つ直せば済むものはその場で `mainflow.md` へ反映し `[x]` にして「変更ログ」へ1行足す。2つ以上の段に触るものは `proposal_maintain` の判断に任せる。

**`ui_verify` には現在 `PROPOSAL.md` が無い**（設計.md §4-1「無いときは作らない」）。したがって上記の「起動時に読む」手順は、`PROPOSAL.md` が実際に作られるまで適用対象が無い。誰かが `PROPOSAL.md` を作った時点からこの手順が有効になる。

## 記録先の分岐

判断の問い：「この改善は、このスキルが全く別のプロジェクトで使われた場合にも同様に必要か？」

| 判断結果 | 改善内容の性質 | 記録先 |
|---|---|---|
| YES | スキルの動作・ルーティング・プロトコル・ツール選択の問題 | このスキルの `memory_improvement/`（このファイルと同じ階層） |
| NO | PJT固有のワークフロー・文書同期ルール等 | PJTガイドライン（`.claude/docs/guideline.md`） |
| NO だが汎用性あり | プロジェクト横断的な教訓・パターン | ユーザースコープの適切なドキュメント（`~/.claude/docs/` 配下） |
