# mainflow — ui_verify の本体

設計.md §11-2 の8段をそのまま手順にしたもの。各段に「誰が」「何を」「止まる条件」を書く。ワーカへ渡す段は、そのたびに `subagent_type: "general-purpose"` と `model: "sonnet"` を明記する（設計.md §4-2。ドクトリンに書いてあっても、段ごとに重ねて書く。取りこぼしても誰も気づけない種類の指示だから）。

## 全体の原則（8段すべてに効く）

**直さない。** このスキルは合否と不足点を返すだけで、コード・DESIGN.md・画面のどれも書き換えない。不足が見つかったら「不足として書く」のが仕事で、「直す」のは別のイシューの仕事。

**「ださくないか」は【要人間】。** §34 のチェックリストは機械的に数えられる項目しか持たない。見た目の印象・センスの良し悪しは数で決まらないので、判定を保留し、検収ドキュメントに「【要人間】：ださくないかの判断」と明記する。

**スマホ実機は【要人間】。** 同じ Wi-Fi の LAN 直結であれば人が踏める（サーバを経由しない）。IP は日に何度も変わるので、そのつど `hostname -I` ではなく Windows 側の LAN IP を調べ直す（`hostname -I` は横流し先で外からは届かない）。このスキル自身はスマホを操作しない——【要人間】として検収ドキュメントに書くだけ。

**Playwright MCP で撮らない。** headless Linux Chromium は Windows Chrome とフォント・字幅・行送りが違うため、はみ出しや折り返しの検証結果が当てにならない（設計.md §11-3）。撮影は必ず `browser_operate` スキルに委譲する。`browser_operate` は対象プロファイルを判定して専任サブエージェント（`browser-a-operator` / `browser-b-operator`）へ委譲する——**このスキル・このスキルのワーカのどちらも、`browser-a-operator` / `browser-b-operator` を名指しで直接起動してはならない。** 必ず `browser_operate` を経由する。

**ワーカへ渡すときの必須事項。** 段2・3・4・6（探す側）・7・8でワーカへ作業を渡すときは、依頼のたびに `subagent_type: "general-purpose"` と `model: "sonnet"` を明記する。省くとエラー無しで上位モデルが使われ、費用だけ増える。

## 段1：DESIGN.md を読む

**誰が**：ワーカ（`subagent_type: "general-purpose"`, `model: "sonnet"`）。

**何を**：`bin/design-sections <触ったファイルのパス>...` を実行し、出力された節番号・行番号（§0.2→§4→§6→§8→§34、アイコンを触ったら+§16・§22、配置を触ったら+§39）の箇所を実際に読み、各節の要点を返す。§0.2 と §4 は飛ばさない（§0.4 が名指ししている）。判断は不要——読んで要点を返すだけ。

**止まる条件**：`design-sections` が「見出しが見つからない」を返したとき（DESIGN.md の見出しが変わった可能性がある）。そのときはメインへ報告し、メインが節番号を直接 grep で探し直す。§16・§22／§39 の追加判定はファイル名のキーワード一致によるヒューリスティックのため、誤判定に気づいたら `bin/design-sections` のキーワード一覧を直す。

## 段2：ビルドする

**誰が**：ワーカ（`subagent_type: "general-purpose"`, `model: "sonnet"`）。

**何を**：`make build-web build-debug` を実行する。両方を回す理由は設計.md §9-3 と同じ（web の焼き込みと debug バイナリの両方が新しくないと、見ている画面と検収の対象がずれる）。

**止まる条件**：ビルドが失敗したとき。ログをそのままメインへ返す（要約しない、判断しない）。

## 段3：残骸ゼロを確認してサンドボックスを立てる

**誰が**：ワーカ（`subagent_type: "general-purpose"`, `model: "sonnet"`）。

**何を**：`our-servers count` を実行し、`0` であることを確認してから `sandbox-dashboard up` を実行する。`up` は成功すると `http://127.0.0.1:<port>/` を1行で返す。

**止まる条件**：`our-servers count` が0以外を返したとき（先に残骸を片付けるまで新しいサンドボックスを立てない）。`sandbox-dashboard up` がエラーで終了したとき（`make build-web build-debug` が必要、または20秒待っても起動しない等）。

## 段4：撮る（`browser_operate` へ委譲）

**誰が**：ワーカ（`subagent_type: "general-purpose"`, `model: "sonnet"`）が、作法どおり `browser_operate` スキルを呼ぶ。

**何を**：`bin/capture-plan <サンドボックスのURL> ...` が出す4枚の計画（PJT専用画面 `/p/…` とセッション専用画面 `/s/…` の**両方**、PC幅と約400pxの**両方**＝合計4枚）に従い、`browser_operate` 経由で撮る。状態表示を含む画面を撮る場合のみ `knowledge/eight-states.md` を読み、撮る直前に対象の状態を作り直す。

**止まる条件**：4枚のうち1枚でも撮れなかったとき。**Playwright MCP へのフォールバックはしない**——`browser_operate` が使えない理由をそのまま記録し、その screen/幅の組み合わせを検収ドキュメントに【要人間】として書く。全体を止めずに、撮れた分だけで段5以降へ進んでよい（未達も記録の対象なので、止める必要はない）。

## 段5：床と天井を数える

**誰が**：メイン（ワーカへ渡さない。判断そのものが仕事だから）。

**何を**：撮った実サイズの絵を見ながら §34.1〜34.5 を数える。§34.4 の床6項目（§8 の必達要素）は実サイズの絵でのみ数える（縮小画像や説明文からの類推では数えない）。§34.5「暗いIDE化」8項目は1つでも該当したら不合格とする（§8.3 により、最後の2項目＝アイコン種別色抜け・ステッカー皆無は抑制のしすぎ側として扱う）。

**止まる条件**：段4で撮れなかった画面/幅があり、その組み合わせでしか数えられない項目があるとき。その項目は「数えていない」として不足点に明記し（「数えて未達」とは区別する）、他の数えられる項目は続けて数える。

## 段6：記録された違反を確かめる

**誰が**：ワーカ（`subagent_type: "general-purpose"`, `model: "sonnet"`）が探し、メインが数える。

**何を**：ワーカが `bin/violations-recorded` を実行し、コード側（`web/src/**/*.test.ts*` のテスト名）と DESIGN.md 本文側の両方で「記録された違反」（設計.md §35.1）を洗い出す。メインはその結果を見て、今回触った範囲に「記録の無い違反」が新たに増えていないかを数える。

**止まる条件**：`violations-recorded` の出力が空（該当なし）で、かつ段5で床割れ等の違反らしき挙動が見えているとき——記録の有無が食い違っているので、メインがその箇所を個別に確認する。

## 段7：検収ドキュメントを置く

**誰が**：ワーカ（`subagent_type: "general-purpose"`, `model: "sonnet"`）。

**何を**：撮った絵と段5・段6で数えた結果を、呼び出し元イシューの `参考/YYYY-MM-DD_<フェーズ>_<画面>_<幅>.png` と `参考/検収_YYYY-MM-DD.md` へ置く。**未達も書く**——「数えていない」（撮れなかった等で測定不能）と「数えて未達」（測定はできたが基準未満）を区別して書く。

**注記（このスキル自身の自己検証実行時のみ）**：このスキル自身の動作確認としてこのフローを回すときは、上記の出力先を呼び出し元イシューの `参考/` ではなく、与えられたスクラッチパッドへ置く。`MyDocs/イシュー/` 配下へは書かない。実運用（実際のイシューの検収）では、この注記は適用されず、通常どおりイシューの `参考/` へ置く。

**止まる条件**：出力先のイシューフォルダが特定できないとき（メインへ確認する）。

---

## 段8：サンドボックスを畳む

**誰が**：ワーカ（`subagent_type: "general-purpose"`, `model: "sonnet"`）。

**何を**：`sandbox-dashboard down` を実行する。続けて `our-servers count` を実行し `0` であることを確認する。

**止まる条件**：`down` の後も `our-servers count` が0以外を返すとき。メインへ報告し、残骸の内容（PID・コマンドライン）を添える。

## 出力形式（段7で作る検収ドキュメント）

- **合否判定**（§34.5 に1つでも該当なら不合格。それ以外は §8 の床6項目と §34.1〜34.4・34.5 の充足状況で判定）
- **不足点の一覧**（「数えていない」項目と「数えて未達」項目を区別して列挙。【要人間】項目もここに含める）
- **置いた画像のパス一覧**（`参考/YYYY-MM-DD_<フェーズ>_<画面>_<幅>.png` の実パス、4枚に満たない場合は撮れなかった理由も添える）
- **検収markdown自体のパス**（`参考/検収_YYYY-MM-DD.md`）
