# 門4つ

`version_release` は次の4つの門をすべて緑で通したときだけ配る。どれか1つでも赤なら、その場で配布を止め、理由を状態ファイルへ残す。門を飛ばして次の段へ進んではいけない。

---
<br/>
<br/>

## 段0で止まる条件

コードの変更を含むコミットが0件なら配らない（文書・テスト・CI だけの変更は次の版に相乗りさせる）。定期のときは静かに終わり、明示（`--now`）のときはそう報告する。

---
<br/>
<br/>

## 門の一覧

| 門 | どの段で通すか | 何を確認するか | 緑の条件 |
|---|---|---|---|
| 門1：テスト | §6-2（段1） | `make ci`（lint → test → build） | 全項目が緑で終わる |
| 門2：タグ整合 | §6-3（段2） | `bin/bump` 後の4ファイル（`server/Cargo.toml`・`server/Cargo.lock`・`docker/compose.yml`・`CHANGELOG.md`）の版番号が一致しているか | すべて同じ版番号を指している |
| 門3：サニタイズ | §6-4（段3） | `scripts/sanitize-fixtures.py` による機微情報の残存検査 | 「機微情報の残存なし」が返る |
| 門4：実機ビルド | §6-5（段4） | `bin/build-live` で建てた実行ファイルの版 | 段2で上げた版と一致し、ビルドが成功している |

## 赤のときの記録先

門が赤になったら、配らずに `_shared/state/version_release.json` へ次の形で残す。

```json
{
  "phase": 1,
  "version": "0.1.147",
  "red": "門1：make ci が失敗（test: web/src/x.test.ts）"
}
```

- `phase`：赤になった時点の段番号（1〜4。§6-2〜§6-5 の段番号と揃える）
- `version`：配ろうとしていた版。段2（門2）より前で赤になった場合は、まだ版が決まっていないので空文字を入れる
- `red`：どの門がどう赤だったかを、次に読む人が原因を辿れる粒度で1行にまとめる（テストなら失敗したテスト名、タグ整合ならずれていたファイルと値、サニタイズなら検出箇所、実機ビルドならビルドの失敗理由か版のずれ）

## クラッシュ復帰時の扱い

途中で中断してこのファイルが残っていた場合、`phase` の値だけを鵜呑みにしない。**git のほうが状態ファイルより正**——`phase` が2以上なら、実際にコミット・タグ・push が済んでいるかを `git log`・`git tag` で確認してから、済んでいる工程はやり直さずに次へ進む。
