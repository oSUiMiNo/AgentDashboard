## ここに書くこと
`version_release` 自身の動作・ルーティング・プロトコル・ツール選択に問題があったとき、その内容と直した内容を記録する場所。判断の問いは「この改善は、このスキルが全く別のプロジェクトで使われても同様に必要か」——YES ならここ、NO なら PJT ガイドライン（このスキルの動作自体に問題は無く、PJT 固有のワークフローが原因のとき）。

**何も壊れなかったが、無駄な往復が発生したときも書く。** 例：`claim` が終了3を返して待たされた、門の赤を見落として次の段へ進みかけた、`periodic` の入口判定を誤って二重に走らせかけた、など。壊れていないことと、改善の種が無いことは別。

### 2026-11-26：ship が push の途中で通信に失敗し、続け方を手で組み立てた
起きたこと：0.1.167 の `ship` で、コミットの後の `push origin main` が github.com の名前が引けずに失敗した（「tag はまだ作っていない」で終了1）。メインは続きを手で組み立て（`git push origin <コミット>:main` → `git tag` → `git push origin <タグ>`）、タグの push も1回目は同じ理由で失敗した。
なぜ起きたか：`ship` は HEAD が既に版のコミットなら、コミットを飛ばして push から続ける作り（`skip_commit`）になっているが、失敗の表示がそれを言っていなかった。表示から続け方が読めないので、手で組み立てた。
直した内容：`bin/ship` の2つの失敗の表示に続け方を足した（main の push で失敗したら、同じ `ship` をもう一度流す。タグの push で失敗したら `git push origin <タグ>` だけを流す。`ship` をもう一度流すとタグが既に在るので止まる）。
