## 案詳細（改善案提出スキルが必ず記載）

### 1
提案：`state-doc-update` のアンカー置換を、現況 doc に「実測欄」を1ブロック設けて丸ごと差し替える方式へ変える。
担当イシュー：PJTスコープに本PJT専用の開発効率化スキルを作成
背景：初回の本番（0.1.147）で、走行版・予約の値が doc 内に2箇所ずつあり「手で直す」で終了4になった。人が一度一意化すれば以後は当たるが、doc が手書きである限り同じことが再発しうる。
特記事項：doc は `render.py` の出力に見えるが元 JSON が無い。元を JSON に戻して `render.py` で描き直す道と、HTML に実測欄だけ持つ道のどちらかを決める必要がある。

### 2
提案：bin/state-doc-update が走行版・ディスクの版・PID・起動時刻・予約の有無の欄を毎回『アンカーが1箇所に定まらない』として何も書かず、いま動いているもの.html が版上げのたびに古いまま残る。アンカーを一意にするか、JSON から描き直す形に変える
担当イシュー：ファイルビュアにエディタ機能を追加
背景：2026-09-28、0.1.148 と 0.1.149 の2回とも同じ6欄が『手で直す』で止まり、文書は1度も更新されなかった
特記事項：無し

### 3
提案：bin/ship が作る版上げのコミットに署名行（Co-Authored-By）が付かない。他のコミットと揃うよう、ship のコミット文に署名行を足す
担当イシュー：ファイルビュアにエディタ機能を追加
背景：2026-09-28 の fc6e8dd（0.1.149）と 51f6a2b（0.1.150）はどちらも題名の1行だけだった
特記事項：無し

### 4
提案：mainflow.md は門1・段3・段4を Sonnet ワーカに渡す前提で書かれていて、利用者が委譲を禁じたときの扱いが無い。禁じられたらメインが同じ手順を前景で実行する、と1行足す（measure-run・ship・build-live はどれも前景で回せる）
担当イシュー：ファイルビュアにエディタ機能を追加
背景：2026-09-28、利用者が『ミドルワーカに委譲するのはやめて』と指示した回に、手順書どおりに渡すか自分で回すかを都度判断した
特記事項：無し

### 5
提案：段1で origin/main..HEAD と git status --short server/ web/ を見て、他のセッションの未 push のコミットや書きかけが乗っていたら、版を上げる前に知らせて止まる（相手に配ってよい区切りかを確かめる手順を mainflow に書く）
担当イシュー：ファイル閲覧の上限を設定から変え、大きいものは流し読みする
背景：2026-11-23 の 0.1.161 では、並行のセッションの作りかけ（未 push のコミット2件と server/ の書きかけ）が HEAD に乗っていた。ship は HEAD をそのまま push・タグし、門1の make ci も書きかけを含んだ結果になるので、黙って他人の作りかけを配りうる。今回は手で相手と連絡を取り、区切りの HEAD で版を上げた
特記事項：札 __版上げ__ は版上げどうしの排他で、相手のコミット・書き換えは止めない。版上げの間は相手に push・server/・web/ の書き換えを控えてもらう必要があった

### 6
提案：bump が CHANGELOG に入れるのはコミットの件名の一覧で、利用者向けの文（触って何が変わるか・戻せるか）への書き換えが毎回手で要る。mainflow の段2に、bump の後でその節を書き換える作業と見本（直前の版の節）を明記する
担当イシュー：ファイル閲覧の上限を設定から変え、大きいものは流し読みする
背景：CHANGELOG.md の冒頭は「利用者が読む場所なので、実装の言葉ではなく触って何が変わるかを書く」と決めているが、bump は件名の一覧と「（触って何が変わるかを1文で）」の空欄を入れるだけで、mainflow にも書き換える手順が無い。2026-11-23 の 0.1.161 では手で書き換えた
特記事項：dist がこの節をリリースの本文に載せるので、書き換えを忘れると件名の一覧（test・docs・proposal の件名を含む）がそのまま利用者に出る

### 7
提案：タグを打った後の GitHub Actions の Release の結果を見る手順を足す。段3の ship の後に gh run list でそのタグの Release を見つけて、終わるまで待つか、少なくとも次の段1で前の版の Release が緑かを gh run list で確かめ、赤なら版を上げる前に知らせる
担当イシュー：サイドバーにエクスプローラで開くボタンが欲しい
背景：0.1.161・0.1.162・0.1.163 の Release が全部止まっていて（Windows のビルドの失敗と、GitHub の macOS 14 の作業機の廃止）、リリース本体が3つの版で作られていなかった。version_release はタグを push したところで終わるので、0.1.163 を配った後の見直しで gh run list を見るまで誰も気づかなかった
特記事項：macOS の作業機の分はイシュー『リリースの組み立てでAppleシリコン向けのビルドが廃止された作業機を指して失敗する』で扱う。門1の make ci は Linux 向けしか建てないので、Windows でしか出ない失敗（std::os::unix を cfg なしで使う等）は Release でしか捕まらない

### 8
提案：門1は make ci だけで make e2e を流さないことを mainflow の門1の節に明記する（または、配る差分が web/ を触っていれば E2E のうち差分に関わる spec を流す）。イシューの作業役が『E2E は版上げの門が回す』と先送りすると、E2E が一度も流れないまま配られる
担当イシュー：サイドバーにエクスプローラで開くボタンが欲しい
背景：イシュー『サイドバーにエクスプローラで開くボタンが欲しい』のレビューの直しの3周が、どれも E2E を版上げの門1に先送りした。門1は make ci だけなので、12コミットの直しの後の E2E は、版を配った後の見直しで初めて流した（新しい赤は無かった）
特記事項：無し

### 9
提案：Release の組み立てが作業機の一時の不調で落ちたときの手順を足す：失敗の中身（DNS の失敗・作業機が割り当てられない等の一時のものか、コードか）を見てから gh run rerun --failed で組み立て直す。組み立て直した後は、リリースのファイル数を前の版と比べ、latest/download/dist-manifest.json が新しい版を返すかを確かめる。目録が落ちていたら、その回の成果物 artifacts-dist-manifest を取り、中身を前の版と比べてから gh release upload で足す
担当イシュー：サイドバーにエクスプローラで開くボタンが欲しい
背景：0.1.166 の Release は、1回目に Intel の Mac の作業機で github.com の名前解決が失敗し、2回目に macos-15 の作業機が15分割り当てられず中断し、3回目で全部緑になった。ところが host の段が同じ回で載せた dist-manifest.json を拾えず、リリースに目録が無かった（ダッシュボードの版の確かめが読む物）
特記事項：#7（タグの後の Release の結果を見る）と組にして読む

### 10
提案：門1（make ci）が既知の揺れで赤になったときの扱いを mainflow に書く。今は「赤なら止まる」だけで、既知の揺れ（MyDocs/イシュー/積み残し_運用 の項目13・14〈a2s の間隔の試験〉、cli_term、FileTabs など）でも止まる。落ちた本を単独で流して緑なら、負荷を見て make ci を流し直す、何回まで流し直すか、流し直しても緑にならなければ止まる、を決めておく
担当イシュー：サイドバーのフォルダ一覧をVSCodeのように展開と畳み込みで辿るツリーにする（0.1.167 の版上げ）
背景：2026-11-26、版上げの前の make ci が5回続けて赤（毎回別の1〜2本。どれも server/ を変えていない版で、単独では緑）。メインが積み残し_運用 の記録を探し当てて既知の揺れと判断し、流し直して緑を得るまで約1時間半かかった。門1の手順に既知の揺れの扱いが無いため、毎回メインが判断している
特記事項：根本は項目13の機構（interval の初回の時報がすぐ来る）を直すこと。こちらは別のイシューにする価値がある

### 11
提案：版上げの最後に、GitHub のリリースのファイル数（前の版と同じか）と、latest/download/dist-manifest.json が新しい版を返すかを毎回確かめる段を足す。無ければ、その回の成果物 artifacts-dist-manifest を取り、前の版の目録と形を比べてから gh release upload で足す
担当イシュー：サイドバーのフォルダ一覧をVSCodeのように展開と畳み込みで辿るツリーにする（0.1.167 の版上げ）
背景：2026-11-26 の 0.1.167 は、Release の組み立てが1回目で全部 success だったのに、リリースのファイルが15個で目録（dist-manifest.json）が無かった。目録はダッシュボードの『新しい版があります』の確かめが読むので、無いと配布物で入れた人の確かめが失敗する。#9 は組み立て直したときの話だけで、1回目の成功でも落ちることは扱っていない。今の手順はタグの後の Release を見ないので、定期の版上げでは気づかずに通る
特記事項：#9 と同じ段にまとめてよい
