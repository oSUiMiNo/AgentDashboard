## ここに書くこと
`proposal_maintain` 自身の動作・ルーティング・プロトコル・ツール選択に問題があったとき、その内容と直した内容を記録する場所。判断の問いは「この改善は、このスキルが全く別のプロジェクトで使われても同様に必要か」——YES ならここ、NO なら PJT ガイドライン（このスキルの動作自体に問題は無く、PJT 固有のワークフローが原因のとき）。

**何も壊れなかったが、無駄な往復が発生したときも書く。** 例：段2の削除・統合・修正・見送りの判断に迷って同じ行を2回見直した、`periodic tick` が `skip` を返したのに気づかず本処理を始めかけた、`apply-decisions` へ渡す decisions JSON の `action` 語彙を取り違えた、など。壊れていないことと、改善の種が無いことは別。

## 2026-09-17：スキル本体が書き換えられている最中の巡回を、過剰に見送った

### 何が起きたか
`bin/*` を一括で書き換えるワーカが走っている最中に巡回（`--tick`）が2回発火した。1回目は「編集中のスクリプトを読むと中途半端な状態を掴んで誤判定する」と考えて見送り、`tick` を打たずに次回へ回した。2回目も同じ判断をして見送った。

### なぜ起きたか
「編集中のファイルを読む＝黙って誤判定する」と考えたが、**この判断は過剰だった**。段1〜4の道具はすべて Python か bash で、壊れたファイルなら**構文エラーで明示的に落ちる**。黙って間違った結果を返す形にはならない。

### どう直したか
3回目に、先に `python3 -m py_compile` で道具の健全さを確かめてから巡回を実行し、問題なく通った。**見送るのではなく、道具が動くことを確かめてから進むのが正しい。**

`mainflow.md` の「止まる条件」へ、次を足す余地がある——**巡回の前に道具の健全さを確かめ、壊れているときだけ見送る**。見送るときは `tick` を打たないこと（打つと `last_run` だけが進み、記録上は「実行した」ことになる）。
