# ワークフロー：shared-tree_commit

このツリーは複数の Claude セッションが同時に触る。`git add -A`・`git commit -a`・`git stash` は、他人の未コミット分を巻き込む（実際に複数回起きている）。このスキルは「自分が触ったファイル」をセッションの記録（`~/.claude/projects/<slug>/${CLAUDE_SESSION_ID}.jsonl`）から機械的に引き、それだけを単位ごとに分けてコミットする。

事前に baseline を取る作法にはしていない。「セッションの最初に打つ」規則は守られないことがある（機械が止める約束だけが守られる）。記録から引く方式なら、コミットのときに初めて呼んでも成り立つ。

## Phase 1：触ったファイル一覧を引く

Agent ツールで `subagent_type: "general-purpose"`、`model: "sonnet"` を指定してワーカへ委譲する（省くとエラー無しで上位モデルが動き、費用だけ増える）。

```bash
.claude/skills/shared-tree_commit/bin/touched-files --session "$CLAUDE_SESSION_ID" --project-dir "$(pwd)" --porcelain
```

ワーカは出力の3群をそのままメインへ返す。

- 触った かつ dirty
- 触った が dirty でない（既にコミット済み等）
- dirty だが触っていない（他人のものの疑い。**消してはいけない**）

> **⚠ 「Bash由来（不確か）」の扱い**：
> `--porcelain` を付けない生出力には「確実（Edit／Write／NotebookEdit）」と「Bash由来（不確か）」の内訳がある。Bash 由来はヒアドキュメント・`tee`・`sed -i`・`mv`／`cp` を正規表現で拾う推測にすぎない（`grep`／`sed -n` だけの行は読み専用とみなして除外し、`CLAUDE.md` 等が誤って混ざるのを防いでいる）。**メインはこの一覧を鵜呑みにせず、Phase 4 のハンク確認で最終的に裏を取る**こと。

> **⚠ 記録が見つからないとき（§10-4）**：
> `touched-files` が終了コード 4（記録ファイルが見つからない）を返したら、機械的な突き合わせを諦める。**`git status` の汚れ全部を、メインが1件ずつ「自分か他人か」判定する**手動の道へ落ちる。この事実を Phase 6 の報告に書くこと。

> **⚠ NUL区切りを使わない理由**：
> `touched-files` はワーカからメインへコマンド本文を渡すとき、NUL区切りではなく1コマンド＝1行の base64 を使う。NUL区切りにしないのは、このプロジェクトのフックがスクリプト中の NUL バイトを書き換えることがあるため——行区切り（改行）だけで安全に分離する。

## Phase 2：他人の札を確認する

メインが行う。`.claude/skills/_shared/bin/claim` は `~/.claude/coord/*/claim` の薄いラッパで、`ls` サブコマンドで現在の保持状況を透過的に呼べる。

```bash
.claude/skills/_shared/bin/claim ls
```

終了コードで分岐する。

| 終了コード | 意味 | このスキルの振る舞い |
|---|---|---|
| 0 | 札の仕組みが在り、`ls` が読めた | 出力と Phase 1 の「触った かつ dirty」を突き合わせる |
| 3 | 札の仕組みが無い、または候補が複数で決められない | **警告して進む**（版上げ・台帳書き込みと違い、コミットは止まらない。設計 §5-3 の「呼ぶスキルが決める」に基づく） |

Phase 1 で「触った」と判定したファイルを、自分以外の名前が `claim` で握っていたら、そのファイルだけを対象から外すかどうかを利用者に聞く。

```
質問：<パス> は他人の作業として握られています（札：<保持者名>）。このファイルを除いて進めますか？

選択肢：
- 除いて進める
- このファイルも含めて進める（理由が明確なときだけ）
- 中止する
```

自分の名前で `claim take`／`free` を打つ場合は、`${CLAUDE_SESSION_ID}` の先頭8桁とスキル名を繋いだものを「自分の名前」として渡す（例：セッションIDが `a1b2c3d4-....` なら `a1b2c3d4-shared-tree_commit`）。

## Phase 3：作業単位に分ける

メインが行う。**1回でまとめてコミットしない**（利用者規則）。Phase 1 の「触った かつ dirty」一覧を、意味のある作業のまとまりごとに分ける。分け方の判断はメインが持つ——ワーカに委譲しない。

同じファイルでも、宣言・import・台帳の末尾追記などは別々の作業が集まっていることがある。ファイル単位で機械的に割るのではなく、何をしたかで割ること。

## Phase 4：ハンク単位でステージングする

作業単位ごとに、列挙はワーカ、判定はメインが行う。ワーカへ委譲するときは `subagent_type: "general-purpose"`、`model: "sonnet"` を必ず指定する。

```bash
git add <ファイル>
git diff --cached
```

**`git add -A` は禁止**。ファイルを名指しで積む。

ワーカは `git diff --cached` の出力をハンク単位で列挙してメインへ返す。メインは各ハンクが「この作業単位に対応する自分の編集か」を判定し、対応しないハンクがあれば `git reset -p` 相当（対話的に該当ハンクだけ unstage）で外す。同じファイルの中に自分の編集と他人の編集が混在することがある——**パスを名指ししても、同じファイルの他人の行は index に入ってくる**。

外したハンクは Phase 6 の報告のために控えておく。

## Phase 5：コミットする

ワーカへ委譲する。`subagent_type: "general-purpose"`、`model: "sonnet"` を必ず指定する。

```bash
git log --oneline -20
git commit -m "<message>"
```

メッセージの型は既存の `git log` に倣う（`feat(web): …` のような `<type>(<scope>): <日本語の説明>`）。本文が要る場合は続けて書く。

メッセージの末尾には、その時点の会話で指定されている署名行をそのまま付ける。特定のモデル名や書式を `mainflow.md` 側にハードコードしない——会話ごとに変わりうるため。

未検証の内容でも、コミットは止めない。「未検証」である事実はメッセージ本文に書いて残す（`ガイドライン/unreleased-work.md`）。**未コミットのまま止まると、セッションが閉じた瞬間に成果が宙に浮く。**
