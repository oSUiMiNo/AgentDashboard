## フィクスチャを採取するとき

### 本リポジトリは公開（PUBLIC）である
`fixtures/` に入れる実トランスクリプトは、そのまま世界に公開される。採取物は必ず `scripts/sanitize-fixtures.py` を通すこと（`make fixtures` は通す）。

### `type: "attachment"` のレコードは中身ごと落とす
Claude Code のトランスクリプトには、採取内容と無関係に**その環境の構成情報**を書き出す `attachment` レコードが混ざる。実際に確認された中身は次のとおり。

- `skill_listing` … 導入済みスキルの全一覧と説明（1万文字規模）
- `agent_listing_delta` … 定義済みカスタムサブエージェント
- `deferred_tools_delta` / `mcp_instructions_delta` … 接続中のMCPサーバとその指示文
- `hook_additional_context` / `hook_cancelled` … フックの内容とコマンド行

何が入るか事前に列挙できないため文字列置換では消せない。パーサ側では attachment は表示対象外として読み飛ばす種別なので、**中身を落としてレコードの形だけ残す**方式で対処している（`sanitize-fixtures.py` が自動実行）。この処理を外すと個人環境の構成が公開される。

### `type: "system"` のレコードも中身を落とす
`subtype: "stop_hook_summary"` の `hookInfos` に、**利用者のフックのコマンド行**（スクリプトのパスと名前）がそのまま入る。`attachment` とまったく同じ「採取内容と無関係に環境の構成情報が入る」種別で、`sanitize-fixtures.py` が自動で落とす。

`attachment` も `system` も**レコードごと消してはいけない**。どちらも `uuid`/`parentUuid` を持って親子の鎖に参加しており、消すと後続のレコードが置き場所を見失う。中身だけを落として形を残す。

### 追加採取はラベルを絞る
`./scripts/gen-fixtures.sh <ラベル>` で1つだけ採れる。引数なしの `make fixtures` は全部を採り直すが、**既存のフィクスチャを採り直すとゴールデンテストの期待値がずれて無関係なテストが落ちる**。増やしたいときは絞って呼ぶこと。

### 利用者定義のスキル名も伏せる
attachment を落としても、実際にスキルを起動していればツールコールと本文の両方に名前が残る。フックがセッション開始時にスキルを起動する設定になっていると、採取のたびに必ず混入する。`sanitize-fixtures.py` は Skill ツールコールからスキル名を**動的に抽出**して置換する（スクリプトに具体名を書くとそれ自体が公開情報になるため、ハードコードしない）。

### フィクスチャはヘッドレスで採るので、対話モード専用のレコードが入らない
`gen-fixtures.sh` は `claude -p`（ヘッドレス）で採取している。**対話モードでしか書かれないレコード type はフィクスチャに入らないため、ゴールデンテストをいくら通してもそこは検証されない**。

実例：`file-history-delta` は対話モードでファイルを1つ編集するたびに1件書かれるが、ヘッドレスでは現れない。パーサの分類から漏れていたことに気づけず、実運用では編集のたびに「不明なイベント」が履歴へ混ざっていた（`/rewind` の実測で本物のトランスクリプトを読ませて発覚）。

対策として、**レコード type に関わる実装を触ったときは、実物の対話セッションのトランスクリプトを1本パーサに通して `unknown_types` が空になることを見る**こと。`./scripts/rewind-probe.sh` が採取する記録がそのまま使える。

### 採取先はリポジトリの外。検査を通ったものだけを中へ置く
採取物をいきなり `fixtures/` へ書かせない。**外で採り、匿名化と残存検査を通り、そのあとで置く**（`record-terminal.sh` がこの順序）。順序が逆だと、後で消しても git の履歴に残る。

この順序は実際に効いた。端末録画の初回採取で、**残存検査がアカウントのメールアドレスを捕まえて設置を止めた**。

### claude の TUI はログイン中のアカウントを画面に出す
起動直後の枠に「Welcome back <表示名>」と**メールアドレス・所属**が出る。端末を録画すると必ず入る。表示名は OS のユーザ名とは別物なので、ホームパスやユーザ名の置換では捕まらない。

`sanitize-fixtures.py` は `~/.claude.json` の `oauthAccount`（`displayName` / `emailAddress` / `organizationName` / UUID）から規則を組み立てる。**規則をスクリプトに書き並べてはいけない**——書けばそれ自体が公開情報になる。残存を報告するときも、アカウント由来の値は伏せて置換先で示す（ログを貼るだけで漏れるため）。

### 生の端末バイト列は「文字列としての置換」が通用しない
2つとも実際に踏んだ。

- **置換を当てると壊れる。** `ESC[30G` の直後にアドレスが続くと、メールアドレスの正規表現が `30G...` から一致し、置換でカーソル移動の指定ごと消える。録画はイベントをデコードし、**エスケープシーケンスの外側だけ**を直す
- **検査はつなぎ直してから行う。** 同じ文字列がチャンクの境目で2つのイベントに割れると、どちらにも完全な形では現れず、置換も素朴な検査もすり抜ける。イベントを連結した版と、さらにエスケープを落とした版（TUI は文字列の途中でカーソルを動かす）の両方で検査する

## 本物の claude を実験やテストで起動するとき

### 利用者のグローバル設定を外すには `--setting-sources project,local`
`--settings` は「追加読み込み」なので、**利用者のグローバル設定（`~/.claude/settings.json`）のフックも一緒に動く**。セッション開始時にスキルを自動起動する設定になっていると、そのスキルが権限確認を次々に出し、こちらが TUI へ送ったキー入力が**権限確認の応答として吸われる**。`/rewind` の実測はこれで一度完走できなかった。

`--setting-sources project,local` は読み込む設定ソースから `user` だけを外すオプションで、次が成り立つことを実測で確認済み。

- 利用者のフック・スキルは動かない
- `--settings` で渡した独自フックは**そのまま動く**（9イベントすべて）
- 認証は通常どおり

**利用者の設定ファイルには絶対に触らない。** 起動フラグだけで隔離できる。

他の候補との違い：

| 手段 | 使えるか |
|---|---|
| `--safe-mode` | カスタマイズを一括無効化する。独自フックまで止まる可能性があるので、フックが要る場面では使わない |
| `--bare` | 認証が `ANTHROPIC_API_KEY` 限定になり OAuth を読まないので使えない |
| `--permission-mode bypassPermissions` | キー入力はメニューへ届くが、**背景で動く利用者のスキルが何をしても自動承認される**。採ってはいけない |

### ダッシュボード経由で試すときは実行ファイルを差し替える
製品コードに実験用のフラグを足さないこと。`AGENTDASHBOARD_CLAUDE_BIN` に「フラグを足して `claude` を exec するだけのラッパー」を指させれば足りる（実CLIテストで `--permission-mode manual` を足しているのと同じ手口）。

### 使い捨てセッションの後始末は、CLI が落ちきってから
CLI は**終了する間際にもトランスクリプトへ書く**。先に `~/.claude/projects/<...>` を消すと、その書き込みでディレクトリが復活して残骸が残る。プロセスの終了を待ってから消すこと。消す前に、対象が本当に `~/.claude/projects/` 配下かを必ず確かめる（空文字や `.` を掴むと事故になる）。

## セッションへ指示を送る経路を触るとき
本物の TUI が相手なので、**「正しいバイト列を作れたこと」と「TUI が受け取れること」は別**。純粋関数のテストだけでは足りない。詳細と実測値は設計§18。

### 送る経路は `Session::send_instruction` に集約する
`write_input` を直に呼んでバイト列を組み立て直さないこと。同じ壊れ方が別の場所で再発する。守るべき約束は3つあり、**どれか1つでも欠けると壊れる**。

1. 送る前に `Ctrl+U` で入力行を空にする（残っているものへ追記されるため）
2. 行数によらず bracketed paste で包む（長さで挙動が変わるため）
3. 確定の CR は**本文とは別の書き込み**で送る（貼り付けの処理に飲まれるため）

本文と確定の間の待ちを詰めてはいけない。2つの書き込みが1回の読み取りにまとまると元に戻る。

### 実CLIテストには「境目より長い単一行」を必ず入れる
TUI が貼り付けと判定する境目は 57〜64 バイトの間で、**日本語なら20文字ほど**で超える。短い文字列だけで試すと、実用上ほとんどの指示が届かない状態を見逃す。実際にフェーズ4の実CLIテストは複数行と `/exit`（7バイト）しか試しておらず、フェーズ6の受け入れテストまで気づけなかった。

### 空送信（本文なし）では入力行に触らない
`encode_parts("")` は CR だけを返す。これは TUI のメニューを確定させる用途なので、ここで `Ctrl+U` を送ると選択中のメニューに余計なキーを打ち込むことになる。

## 実 claude を起動して検証するとき（資源の使い方）
本アプリの検証は**本物の claude を PTY で起こす**ので、普通の開発より資源を食う。実測で claude 1本あたり RSS 約464MB。フェーズ6の作業中に WSL が停止しており、寄与した可能性を否定できなかった。

### 同時に走らせるのは1本まで
一覧やグループ化の確認でどうしても複数要るときだけ増やし、**終わったら即座に落とす**。開きっぱなしにしない。

### core を落とす前に、パーサが残っていないか見る
パーサには孤児化しないための見張りが入っているが、**即座ではない**（負荷があると数秒かかる）。落としたら `ps` で確認する習慣にする。

```
ps -eo pid,ppid,cmd | grep '[t]ranscript-parser'
```

### `pkill -f` でプロセスを探さない
`pkill -f 'target/release/agentdashboard'` はパターンが**自分のシェルのコマンド行にもマッチ**して、実行中のシェルごと殺す（実際に起きた）。待ち受けポートから PID を引くこと。

**`pgrep -f` も同じ罠を持つ。殺さないぶん、こちらのほうが見つけにくい。** 生き死にを
数えるつもりで `pgrep -f "agentdashboard-agent --config"` と書くと、**その文字列を含む
自分のコマンド行**が1件返り、止まっているものを「動いている」と読む（実際にそう読んだ）。
現に止まっていたセッションホストを、生きていることにしかけた。

見分ける手は3つある。**いちばん確かなのは、そもそも数えないこと**——待ち受けポートか、
控えておいた PID で見る。どうしても名前で探すなら、`pgrep -af` にして**返ってきた行を
読む**（`bash -c` が混ざっていればそれは自分）か、`| grep -v "bash -c"` で落とす。

同じ理由で、**プロセスの有無を `&&`／`||` で真偽だけ受け取ってはいけない。** 行を見れば
自分だと分かるものが、真偽に畳んだ瞬間に見分けられなくなる。

```
PID=$(ss -ltnp | grep 8787 | grep -oP 'pid=\K[0-9]+' | head -1)
```

### ビルドは必要なときだけ
Docker 内の release ビルドはメモリを大きく食う。「直した → すぐ実機で見る」を繰り返すと、ビルドが積み上がる。まとめて回す。

### Playwright MCP のスクリーンショットは出力先を指定する
指定しないと**起動時のカレント（＝リポジトリのルート）に書き出される**。本リポジトリは公開なので、気づかずにコミットされる。実際にフェーズ5で2枚入っていた。`.gitignore` でルート直下の画像を弾いてはいるが、置き場所はスクラッチパッドを指定すること。

## Rust のコマンドを実行するとき

### `cargo` を直接呼んではいけない
ホストに Rust ツールチェーンは入っていない。cargo / rustc / clippy / rustfmt / nextest はすべて Docker イメージの中にあり、`scripts/cargo` がその唯一の入口になっている。

```
scripts/cargo build --release
scripts/cargo nextest run
scripts/cargo tree -i tokio-tungstenite -e normal
```

`cargo: command not found` が出たら、ラッパーを経由し忘れている。Makefile も自己修復機構もこの1つの入口に集約する方針なので、新しい経路を作らないこと。詳細は `.claude/docs/knowledge/開発環境とツールチェーン.md`。

### web を変更したら core を作り直す必要がある
`agentdashboard` バイナリは `web/dist` を**コンパイル時に**取り込む。フロントを直しただけでは
バイナリの中身は古いままなので、動作確認は必ず `make build`（または `make e2e`）を通すこと。
`crates/server-core/build.rs` が `web/dist` の変更を cargo に伝えるようにしてあるので、ビルド順さえ
守れば自動で作り直される。

#### **E2E が使うのは debug ビルド。`make build` では効かない**
上を守っていても踏む。`make build` が作るのは **release**（`server/target/release/`）だが、
Playwright の `webServer` が起こすのは **`server/target/debug/agentdashboard`**
（`web/playwright.config.ts` の `serverBinary`）。**別のバイナリなので、release をいくら作り直しても
E2E には1バイトも届かない。**

症状が最悪の形で出る。**古い web が焼き込まれた debug バイナリで E2E が走る**ので、直したはずの
振る舞いが再現せず、しかも**製品コードもテストも正しい**。実際に、ブラウザ側の判定を足した回で
3本が落ち、「判定が効いていない」と読んで調査用のテストまで書いた——可視領域には判定に必要な
文字列がちゃんと入っており、**実装は最初から正しかった**。

`make e2e` は `build-web build-debug` を前置しているので、**素直にあれを叩けば踏まない**。
`npx playwright test` を直に呼ぶときは、先に `make build-web build-debug` を通すこと。

**「web を作り直した」ではなく「E2E が見るバイナリを作り直した」で考える。**

### ビルドの置き場所は青天井に育つ。ときどき嵩を見る
`cargo` は**古い成果物を自分では消さない**。このワークスペースは統合テストが多く、
テストの実行ファイル1本が数百 MB あるので、再ビルドのたびに別名のぶんが
`server/target/debug/deps` へ積み上がっていく。差分コンパイルのキャッシュ
（`incremental`）も同じように増える一方になる。

**放っておくと数百 GB に達する。** 実際に 335 GB まで育ち、WSL の仮想ディスクごしに
Windows の C: を満杯にして、Docker Desktop とターミナルを落とした（2026-08-09）。
`scripts/cargo` は Docker の上に乗っているので、**ここが詰まると開発が全部止まる。**

```
du -sh server/target     # ときどき見る。数十 GB を超えていたら減らす
make prune               # 次のビルドの大半を使い回せる形で嵩だけ落とす
make clean               # 全部消す（丸ごと作り直しになる）
```

**WSL で開発しているときは、消しても Windows 側の空きはすぐには戻らない。** 仮想
ディスクのファイルは自動では縮まないので、`wsl --shutdown` してから `diskpart` の
`compact vdisk` を掛ける必要がある。`wsl --manage --set-sparse` は Microsoft が
非推奨にしていて、`--allow-unsafe` を求められる——**利用者の全ソースが入っている
ディスクなので、その旗は立てない。**

### 本物の claude を使うテストは `make test-cli`
`make test` では走らない（`#[ignore]` 付き）。実行すると**本物の claude が起動し、利用者のアカウントのクォータを消費する**ので、明示的に叩くときだけにすること。ビルドはコンテナ、実行はホストという二段構えになっている理由は `.claude/docs/knowledge/開発環境とツールチェーン.md` を参照。

テストから実行ファイルの場所を求めるときは `CARGO_BIN_EXE_*` ではなく `testkit::binary_path()` を使う。前者はコンパイル時のパス（＝コンテナ内の絶対パス）が焼き込まれるため、ホストで実行した瞬間に壊れる。

### ビルドした成果物はホストで動かす
コンテナはツールチェーンの置き場所に徹しており、`agentdashboard` バイナリはホストで実行する。本アプリは PTY で本物の claude CLI を起動し、ホストの `~/.claude` とユーザのプロジェクトを触るのが本質のため。

### 絞り込んで走らせたテストは別バイナリを作り直さない
統合テストの一部は**別の実行ファイル**を子プロセスとして起動する（`transcript-parser` / `fake-claude` / `agentdashboard`）。`scripts/cargo nextest run --test <名前>` のように絞ると、それらのバイナリは作り直されない。**直したはずの挙動が変わらない**という追いにくい状態になるので、絞って走らせるときは先に `scripts/cargo build` を通すこと。`make test`（全体実行）では起きない。

### 日本語のテスト名でも、先頭は数字にできない
本 PJT はテスト名を日本語で書く慣習なので踏みやすい。`fn 3つ組として…()` は
`identifiers cannot start with a number` でコンパイルが通らない（Rust の識別子の規則は
文字種に関わらず効く）。**数を頭に置きたいときは漢数字にする**（`三つ組として…`）。

### 読点も使えない。**文字種ではなく「字か否か」で決まる**
`fn 運ぶのは生の行で、整えない()` は `unknown start of token: \u{3001}` で落ちる。
rustc は親切に「`、` は `\` に見えますが違います」と言うので、原因は分かりやすい。

使えないのは**約物**（`、` `。` `・` `（）` `「」`）で、漢字・かなは使える。識別子に
許されるのは Unicode の `XID_Start` / `XID_Continue` で、句読点はそこに入らない。
上の「先頭の数字」と同じ族の話で、**日本語で書けるからといって文として書けるわけでは
ない**。読点を打ちたくなったら、文を分けずに続ける（`運ぶのは生の行であって整えたもの
ではない`）。

### 正規表現に素の `(?i)` を書くと、コンパイルは通って実行時に落ちる
`regex` は **`default-features = false`** で入れてある（配布物を軽く保つため。理由は
`server/Cargo.toml` の当該行にある）。したがって **`unicode-case` を持っていない**ので、
`(?i)` は `Unicode-aware case insensitivity matching is not available` で
**`Regex::new` が `Err` を返す**。

定数の正規表現は `.expect("定数の正規表現")` で組み立てるのが本 PJT の作法なので、
**落ちるのはコンパイル時ではなく、その関数が最初に呼ばれたとき**になる。しかも
落ちるのは大文字小文字を無視したかった1本だけなので、**その経路を通るテストが
無ければ緑のまま出荷される**。

大文字小文字を無視したいときは **`(?i-u)`** と書く。`-u` で Unicode モードを外すと
ASCII の畳み込みになり、機能を足さずに済む。**機能を足して解決しない**——
`unicode-case` は `regex-automata` の表を引き込むので、配布物の大きさに直接効く。

### 日本語のテスト名に ASCII の大文字を混ぜない
同じ性質のもう1つ。`fn 割れない名前はNone()` や `fn 別のPCは引けない()` は
**`non_snake_case` で落ちる**（`-D warnings` なので警告ではなく失敗になる）。日本語の
部分は判定の対象外だが、混ざった `None` や `PC` が大文字として見える。

`#[allow(non_snake_case)]` を貼らないこと——**貼ると、以後この名前空間で本当に直すべき
命名も黙る**。名前のほうを日本語へ寄せる（`割れない名前は割らない` `別の機械は引けない`）。

型名や定数を名前へ入れたくなるのは、**その名前を確かめるテストだから**であることが多い。
本文（`assert` のメッセージ）に書けば、名前に入れなくても読む人には伝わる。

### 「`make ci` が通った」を `make test` で代用しない
`make ci` は **lint → test → build** の順で、lint（`rustfmt --check` と clippy）が先に走る。
つまり **lint で落ちる状態ならテストまで到達しない**ので、`make test` が通ったことは
`make ci` が通ったことの根拠にならない。

### `npx tsc --noEmit` は `make lint` の代わりにならない
同じ形の罠が web 側にもある。**`make lint` が叩くのは `npx tsc -b`**（プロジェクト参照つき）で、
手元で `npx tsc --noEmit` を打つのとは**拾う範囲が違う**。

実際に踏んだ。テストファイルの import 漏れ（`Terminal` の型）を `--noEmit` は1件も
報告せず、`make lint` が4件出した。**軽い代替で「通った」と読むと、ゲートで落ちてから
戻ることになる。**

**確かめるなら、ゲートが実際に叩くコマンドで確かめる。** Makefile を読んで同じものを打つか、
素直に `make lint` を通す。

### コードを書き終えたら、`make ci` の前に `make fmt` を通す
上の裏返し。**整形の差分1つで、4分の `make ci` が丸ごと無駄になる。** 落ちるのは lint
なので、テストもビルドも一度も走らないまま返ってくる。

**とくにテストを書いた直後が危ない。** `assert!` の引数やマクロの折り返し方は
rustfmt の考えと食い違いやすく、しかも人間が読んで違和感が無い形ほど食い違う。

実際に**2つのフェーズで続けて踏んだ**（1回目は `use` の並び、2回目は `assert!` の
折り返し）。どちらも `make fmt` の一発で消えるものだった。順序を
「書く → `make fmt` → `make ci`」に固定すれば、この往復は起きない。

### `make lint` が通っても、`cargo build` は警告を出すことがある
`make lint` の clippy は `-D warnings` で走るので「警告が1つも無い」と思いがちだが、
**`-D warnings` が効くのは名前を持つ lint だけ**である。字句解析の段で出る警告には
名前が無く、否定できない。

実際に踏んだ。同じ `make ci` の中で **lint は通り、そのあとの release ビルドが1件
警告を出した**。

```
warning: whitespace symbol '\u{3000}' is not skipped
```

文字列の `\` による行継続が飛ばすのは **ASCII の空白だけ**で、続く全角スペースは本文と
して残る。この PJT は日本語のメッセージを整形のために字下げすることがあるので踏みやすい。
**1つの文字列として書けば迷いようが無い。**

したがって、**ビルドの出力も読む**。`make ci` の最後を「生成物: …」だけ見て終わりに
しない。

### `make ci | tail` は、失敗を隠す
出力が長いので `make ci 2>&1 | tail -25` と書きたくなる。**そのパイプラインの終了コードは
`tail` のもの**なので、`make` が落ちていても 0 が返る。バックグラウンド実行の完了通知も
「exit code 0」と言う。

実際に踏んだ。テストが1件落ちて `make: *** Error 100` が出ているのに、通知は成功を
告げていた。**末尾25行に失敗が写っていたから気づけただけ**で、写らない位置で落ちていたら
「通った」と記録していた。

絞るなら `set -o pipefail` を付けるか、`tail` ではなく全体をファイルへ落として後から読む。
**「通った」と書く前に、`make` 自身の終了コードを見たかを確かめる。**

**終了コードを控えるつもりで、同じ罠へ入り直せる。** `make e2e > log 2>&1; echo "exit=$?" | tee -a log`
と書いたことがある。控えているのに、**ハーネスが報告するのは `tee` の終了コード**なので通知は
「exit code 0」になり、記録した `exit=` のほうは **2** だった（1本落ちていた）。控えた値を自分で
読み直すまで、通ったと思い込んでいる。

**パイプを挟まない形にする。**

```bash
make e2e > run.log 2>&1; echo $? > run.exit
```

実際にこれを踏んでいる——あるフェーズの実行レポートが「`make ci` 通過」と記録して
いたのに、そのコミットを取り出して `rustfmt --check` を走らせると**18箇所落ちた**。
崩れたまま積むと、次に触った人の差分に**無関係な整形が混ざる**（そして「なぜ自分が
触っていないファイルが出るのか」を調べるところから始まる）。

フェーズの終わりに書くのは、**実際に `make ci` を走らせた結果**にすること。

## ログを残すとき
**この道具は、人が見ていないところで動く claude を相手にしている。** 症状に気づくのは
いつも事後で、そのとき手元にあるのは残っていたものだけになる。だから「出すかどうか」は
迷わない——**極力何でも残す**。迷うのは「どこには入れないか」のほうである。

読む口・書く場所・伏せ方は README（利用者向け）にある。ここに書くのは**書く側の約束**。

### 1. 無言で失敗する道を作らない
結果を捨てるなら、`server/crates/core/tests/swallowed.toml` へ**理由ごと**書く。台帳と
実コードが食い違うと `make ci` が落ちる。**理由を書けないものは書けない**という形にしてある。

捨てること自体は禁じていない。禁じているのは、**捨てたことが誰にも見えない**状態である。

### 1-2. 台帳へ足す場所は `path` の辞書順。**中身が合っていても、並びが違えば落ちる**
`swallowed.toml` は走査側が `Key`（`path` / `fn` / `expr`）の順で並べたものと突き合わせるので、
**台帳もその順で保たれている必要がある**。同じファイルの項目が固まっているように見えるが、
それは辞書順の結果でしかない。

食い違うと落ちるのは正しいが、**失敗の見た目が「巨大な2つの配列の差分」**になる。
中身は1件も違わないので、原因が並び順だと気づくまでに時間がかかる。実際に
`transcript-parser/src/tail.rs` の項目を `cli.rs` の並びに続けて書いて踏んだ
（`session.rs` < `tail.rs` なので、`session.rs` の**後ろ**が正しい位置だった）。

**足す前に、`path` を辞書順で見て入る場所を決める。**

### 2. 外の世界と接するところには必ず1行残す
ファイル・プロセス・ネットワーク・子プロセス・crate 境界。ここを跨ぐ操作が失敗したとき、
**何をしようとして何が返ったか**を1行にする。制御の流れは変えない——捨てていたものは
捨てたまま、失敗したときだけ行が増える形にする。

### 3. 1件ごとに回る場所には入れない
バイト単位・フレーム単位・ノード単位で回るところに行を置くと、いちばん読みたい行が
そこで埋まる。**名指しで禁じてある経路**は次のとおり。

| 経路 | 代わりに出すもの |
|---|---|
| `session/pty.rs` の `read_loop`（PTY の読み取り） | 起動・EOF・停止・一時停止の遷移だけ |
| `session/mod.rs` の `coalesce_loop`（出力の合流） | 何も出さない |
| `server-core/src/gateway.rs` の `deliver_screen`（画面の配信） | 購読の開始と終了だけ |
| `transcript-parser/src/cli.rs` の `emit`（ノードごとの書き出し） | 書けなかったときだけ |
| `logging.rs` のファイル層（ログを書くこと自体） | 何も出さない（捨てた件数だけ数える） |

**経路を増やしたら、この表にも足す。**

### 4. 相関キーを載せる
`card_id` があるだけで、その行は `agentdashboard logs --card <ID>` で串刺しにできる。
無ければ、出ていても後から辿れない。既存の書き方（`card_id = %session.card_id`）に揃える。

| 欄 | 何に紐づくか |
|---|---|
| `card_id` | セッション1本 |
| `agent_id` | 繋いでいる PC |
| `account_id` | アカウント（セルフホストのみ） |
| `request_id` | 問答1往復 |
| `parser_pid` | パーサの子プロセス |

`ts` / `level` / `target` / `proc` / `pid` / `run_id` / `msg` の7欄は**どの行にも自動で載る**。
同じ名前を自分で渡すと `f_<名前>` へ退避されて二重に出るので、渡さないこと。

### 5. 標準出力へ書いてよいのは、サーバを起こしたときだけ
消す道（`scripts/uninstall.sh`）が `agentdashboard state-dir` の出力を**そのままパスとして
使う**。1行でも余計なものが混ざると、消す先が狂う。ログは標準エラーへ出す。

### 6. 原因を追うときは、コードを読む前にログを読む
そこに無かったら、**ログを足すのが最初の変更**になる。読んで当てを付けてから直すのでは、
同じ症状を次に踏んだ人がまた同じところから始めることになる。

### 7. 経路を新しく足したら、検査にも足す
`web/e2e/logs.spec.ts` の経路の表が「どの入口を通っても痕跡が残る」ことを見ている。
書き手を増やしたらここへ1行足す。**足さないと、増えた経路だけが無言のまま残る。**

## パーサ（transcript-parser）を触るとき

### 標準出力は IPC 専用。ログは標準エラーへ
core とは stdout の JSON Lines で会話している。1行でも他のものが混ざると core の行パースが壊れ、「繋がっているのに何も届かない」という沈黙になる。デバッグ出力を入れるときは必ず `eprintln!` を使う。

### `tracing` を持たせない
この crate は**丸ごと、無人の claude が書き換えてよい範囲**にある。`tracing_subscriber::fmt()` の既定の書き出し先は stdout なので、修復が1行足しただけで上の沈黙が生まれる。しかも修復のテストゲートは stdout の汚れを見ない。行は `eprintln!` で標準エラーへ出し、親（`session-host-core/src/parser.rs`）が拾って合流させる。`crates/core/tests/dependencies.rs` が依存そのものを機械で禁じている。

### 再開位置は core が持つ。パーサは覚えない
どこまで読んだかは core が `offsets.json` へ書く。パーサ側に状態を持たせると、自己修復でバイナリを差し替えた瞬間に失われる。パーサは「ここから読め」と言われた位置から読むだけにする。

### ノードIDに URL で意味を持つ文字を使わない
ノードIDは履歴の遡り（`?before=<id>`）でクエリ文字列に載る。`#` を入れるとフラグメント扱いで値が切れる。区切りが要るときは `.` や `:` を使う。

### 「表示しない」と「捨てる」は別
`attachment` / `system` は表示しないが `uuid` を持ち、親子の鎖に参加する。捨てるとその先のレコードが置き場所を見失う。**表示しないが鎖は繋ぐ**という扱いが要る。捨ててよいのは `uuid` を持たない種別（`queue-operation` / `ai-title` 等）だけ。

## 自己修復（selfheal）を触るとき
本物の claude を**無人で起動して自分のソースを書き換える**機能なので、他のどこよりも慎重に扱う。

### 外の世界へ出る操作は必ず `SelfhealOps` 越しにする
cargo・git・本物の claude を直接呼ぶコードを増やさないこと。**Rust のテストは
`scripts/cargo`（= `docker run`）の中で走るので、その中からもう一度 docker は呼べない。**
差し替えられない場所に外部コマンドを書いた瞬間、その経路は自動テストで一切踏めなくなる。

### worktree はリポジトリの中（`.selfheal/`）に置く
`scripts/cargo` はリポジトリだけをコンテナへマウントする。外に作るとコンテナから見えず、
worktree の `.git` が指す親も辿れない。cargo の作業場所は
`AGENTDASHBOARD_CARGO_DIR`（リポジトリ相対）で切り替える。入口は増やさない。

### worktree の土台は、勝手に古くなる。**見た目では分からない**
`prepare_worktree` は作業場所が既にあれば使い回し、`git reset --hard HEAD` を掛けるだけである。
そこでの `HEAD` は**修復用の枝の先端**で、その枝は作られた日の本体から生えている。つまり
**作業場所は、最初に作った日の木のまま何か月でも据え置かれる**。

実際に踏んだ（2026-08-19）。7月30日に作られた作業場所で修復が走り、**8月10日に直したはずの
輪（毎秒34万回の `read`・毎分 420MB）を持つパーサが差し替えられて**、機械が落ちかけた。
**本体で直したことは、修復の成果に何の影響も与えない。**

見分け方は次の3つ。**どれも一目では気づけない**ので、自己修復まわりを触るときは必ず当てる。

```bash
git log -1 --format='%h %ad' --date=iso "$(git merge-base main dashboard-maintenance)"  # 土台の日付
git merge-base --is-ancestor <直したコミット> "$(git merge-base main dashboard-maintenance)"
ls .selfheal/worktrees/dashboard-maintenance/server/crates/          # 構成が今と違えば古い
```

**版の数字も当てにならない。** 差し替えたパーサが名乗る `parser_version` は古い木の
ワークスペース版（例：`0.1.0`）で、本体（例：`0.1.29`）と食い違う。**食い違いを見ている
場所がいまは無い**ので、ログの「transcript-parser 0.1.0 と接続しました」という1行だけが
証拠になる。ここを読み流さないこと。

同じことが**モデル別名表の見直し**（`dashboard-maintenance-models`）にも起きる。あちらは
`web/src/lib/models.ts` を書き換えるので、古い木から作ると**古い表を「最新」として採用する**。
症状が静かなぶん、こちらのほうが気づきにくい。

### `cargo build -p <ライブラリだけのパッケージ>` は、成功して何も作らない
実行ファイルの入口は**パッケージを移ることがある**（本PJTでは3本まとめて `crates/dist` へ移した）。移ったあとに `-p <元のパッケージ>` のまま作ると、**ライブラリだけが出来て cargo は終了コード0で返る**。

失敗は「ビルドした◯◯が見つかりません」という、**置き場所の話に見える形**で出る。**まず作る先のパッケージを疑うこと。**

```bash
ls .selfheal/target/<枝>/release/
  libtranscript_parser.rlib     # ← 実行ファイルが無い。これが答え
```

**古い作業場所では通ってしまう**のが厄介で、入口を移す前の木にはまだ `main.rs` があるため、**土台を追いつかせた瞬間に初めて表に出る**（2026-08-19 に踏んだ）。実行ファイルを作る呼び出しを書くときは、**それを持っているパッケージを実物の `Cargo.toml` から読んで突き合わせる検査**を一緒に置くこと。

### worktree に `.gitignore` されたものは存在しない
git が持ってくるのは追跡しているファイルだけ。`node_modules/` のようにビルドや検査へ
**必要なのに追跡していないもの**は、worktree では自分で用意しないと無い。用意し忘れると
ゲートは「実行できなかった」ではなく**「落ちた」**として現れ、原因が見えにくい。

用意する手段にシンボリックリンクを選ぶ場合、`.gitignore` の書き方に注意する。git は
リンクをディレクトリとして扱わないので、**末尾に `/` を付けたパターンでは無視されない**。
無視されないと変更範囲の検査に引っかかり、`git clean -fd` でも消える。

### 通していない経路は「動く」と書いてはいけない
上の不具合が出荷まで残ったのは、**別名表の見直しの流れを一度も通していなかった**ため。
契機（CLI の版が上がったとき）を擬似 claude では踏めないことが、そのままテストの空白に
なっていた。踏めないなら**入口を公開してテストから直接呼ぶ**。契機が再現できないことは、
流れを確かめない理由にならない。

### `bypassPermissions` と `--setting-sources project,local` は必ず組で使う
バイパスだけだと、利用者のグローバル設定のフックやスキルまで**自動承認で**走る。
爆発半径をパーサ修復の外へ広げないために、利用者の設定は読み込ませない
（利用者の設定ファイルには触らない。起動フラグだけで隔離する）。

### 修復の合否は「言葉」ではなく「機械」で決める
プロンプトに「パーサだけ直して」と書くのは必要だが、担保にはならない。触った範囲は
`git status --porcelain` で検査し、合否は core が独立に実行したテストだけで決める。
セッションホストの自己申告は使わない。

### 「直す」より先に「戻す」を考える
差し替えたあとに異常が出たら、直しにいくのではなくロールバックする。ここで修復へ進むと、
悪いパーサを載せたまま何度も直そうとする。あわせて**版に関わらない全体のクールダウン**を
必ず通すこと。どのパーサでも読めないデータが混ざっていると、率の検知は版に関係なく
何度でも発報するので、これが無いとカナリアと修復セッションが止まらずクォータを使い切る。

### フィクスチャを増やす場所は決まっている
`fixtures/<版>/<ラベル>/session.jsonl` に置けば、発見型のゴールデンゲートが自動で拾う。
テスト側にパスを直書きしないこと（書くと、足したサンプルが検証されないまま
「対応済み」と記録される）。**意図的に壊したデータを `fixtures/` へ置いてはいけない** —
ゲートが常に落ちるようになる。壊れたデータが要る訓練は、worktree の中に置く。

## サーバ⇔ブラウザのメッセージを増減するとき
WebSocket のメッセージ型は Rust と TypeScript で**手書きで二重に定義**している。片方だけ直すと
コンパイルは通るのに動かない、という追いにくい状態になる。1つ増減するたびに次の4箇所を揃えること。

| 直す場所 | ファイル |
|---|---|
| Rust の型 | `server/crates/protocol/src/ws.rs` |
| Rust の往復テスト | 同ファイルの `tests` モジュール |
| TypeScript の型 | `web/src/lib/protocol.ts` |
| TypeScript の突き合わせテスト | `web/src/lib/protocol.test.ts` |

両側のテストは「同じ JSON 文字列になること」を確かめている。ここが唯一のズレ検出手段なので、
種別を増やしたら必ずテストにも足す。

設計に無いメッセージを足す場合は、**設計.md §4 の表にも追記**する。実装と設計が食い違ったまま
次のフェーズへ進むと、どちらが正なのか判断できなくなる。

## セッションに注入するフックを触るとき

### `--settings` は「置き換え」ではなく「追加」
利用者のグローバル設定（`~/.claude/settings.json`）は書き換えないが、**そちらのフックも同時に動く**。
ダッシュボードが起動したセッションでも、利用者のフック（セッション開始時のスキル自動起動など）は
そのまま発火する。「ダッシュボードが注入したものだけが動く」と考えて設計すると食い違う。

### 観測専用のフックは標準出力に何も書かない
UserPromptSubmit / SessionStart 系のフックは「終了コード 0 のときの stdout を Claude への
コンテキストとして注入する」仕様になっている。`hook-post` がここに何か出すと、ダッシュボードが
利用者の会話へ勝手に文字列を差し込むことになる。`{}` すら返してはいけない。

### 失敗しても終了コードは 0
ダッシュボードが落ちていることが CLI の動作を妨げてはならない。宛先不達・URL 不正・stdin 異常、
どの経路でも黙って 0 で終わる。

### 成功したときは何も書かない
`hook-post` には `<state_dir>` へ到達する手段が構造的に無い（設定を読まないことが存在条件で、
環境変数も絞ってある）。素直にログを持たせると `HOME` の下を開き、**テストが開発者の実運用
ディレクトリへ書く漏れ**を、機械検査の届かない場所に作ることになる。だから**フックは自分では
記録しない。** 届かないことの検知は受け手（`session-host-core/src/hooks.rs`）の仕事で、
あちらが一定時間1件も来ていないことを見て、材料を並べた1行を出す。

## テストから自分のサーバを叩くとき

### ブロッキングHTTPはテストのスレッドで待ってはいけない
`#[tokio::test]` の既定はスレッド1本のランタイムで、そこに `axum::serve` を相乗りさせている。

`tokio::task::spawn_blocking` で専用スレッドへ逃がすこと。`common::TestServer` の
`post_hook` / `get` は既にそうなっている。新しい入口を足すときも同じ形にする。

`http://127.0.0.1:<port>/hook/...` が書き込まれるため、後からポートが変わると届かない。

## ローカルイシューのドキュメントを編集するとき

### イシューのフォルダは**作業の途中で動く**。パスを直書きしない
グループへまとめる操作でフォルダごと移る。**作業の最中に動くことがある**——実際、`make ci` を
回している数分の間に、触っていたイシューが新しいグループの下へ移された。

症状は「**フォルダが消えた**」に見える。移動と削除は、**片方のパスだけを見ていると区別が付かない。**

- **消えたと読む前に、親を開いて全体を見る。** `ls MyDocs/ローカルイシュー/` で、増えたグループごと目に入る
- **イシューのドキュメントに、自分の置き場所を直書きしない。** 隣のファイルは名前で参照する
  （`設計.md` §N）。書いてあると、移動のたびに全部が嘘になる
- 移動されたら、**グループの `メタ.md` を読んでから続ける。** 個別に消化するのか1つの設計として
  解くのか、順序に依存があるのかが書いてある。読まずに続けると、他のイシューの前提を壊す

### `MyDocs/` は git 管理外。コミット対象にならない
`.gitignore` に `/MyDocs/` が入っている。ローカルイシューのドキュメントをいくら書いても
`git status` には出ないので、**「作業別にコミットする」の対象に数えてはいけない**。
実装作業の計画にドキュメント更新を含めるときは、その分をコミット単位から外すこと。

リモートへ渡る経路は git ではなく `issue_sync`（後述）だけである。手元に残す唯一の
控えでもあるので、消す方向の編集には別の注意が要る（後述の「情報量を減らす方向の編集」）。

### 機械で書き換えるなら、先に控えを取る。終端に「どこにでもある文字列」を使わない
`MyDocs/` は git 管理外なので、**壊したら復元手段が無い**。チェックボックスの一括更新の
ような機械的な書き換えでも、走らせる前にスクラッチパッドへ控えを取ること（後述の
「情報量を減らす方向の編集」は要約や統合を想定しているが、**危険は書き換えの機械性の
ほうから来る**）。

節を切り出すときの終端に、`---` のような**文書のどこにでもある文字列**を使わない。

```python
a = text.index(見出し)
b = text.index('---')          # ← 先頭の区切り線に当たる
text[:a] + 直した節 + text[b:]  # b < a なので節が複製される
```

実際にこれで `テスト計画.md` が 271行から 508行へ膨らみ、フェーズ1と2が3重になった
（節の並びから復元できたが、それは運が良かっただけ）。**切るなら見出しで切る**——
「次の `##` か `###` が現れるところまで」を範囲にすれば、この壊れ方は起こらない。

書き換えたあとは**行数と項目の総数を数える**。総数はどこかに書いてあることが多い
（`計画.md` の整合表など）ので、突き合わせれば複製にも欠落にも気づける。

### 設計.md の節番号は振り直さない
`MyDocs/ローカルイシュー/初期実装/設計.md` の `## N. 見出し` という節番号は、`計画.md` と `テスト計画.md` から `§N` の形で参照されている。既存節の番号を振り直すと参照が一斉に壊れるため、節の追加は**末尾への追加のみ**とする。削除や並べ替えがどうしても必要な場合は、参照元2ファイルの `§` 表記を同時に修正すること。

### テスト側のドキュメントの名前は `テスト計画.md` に統一する
利用者が「テスト方針」と呼ぶことがあるが、**ファイル名は `テスト計画.md`** にする。クローズ済みの4イシューがすべてこの名前で、`設計.md` の未決事項節が「テスト計画フェーズ1で解消する」の形で名指ししているため、名前が揺れると**設計からの参照が過去のイシューと揃わなくなる**。

中身の型も既存イシューから動かさない——**原則は6フェーズ**（1 前提の検証／2 単体／3 統合／4 実CLI／5 フロントエンド／6 受け入れ）、項目は `- [ ] 〜こと`、末尾に「設計との対応」表を2枚（設計→フェーズ／要件の一文→フェーズ）。呼び名が違っても指しているものは同じなので、**依頼の言葉づかいではなく既存の並びに合わせる**。

**ただし「固定」ではない。** 全8本を数えると、この6本の並びちょうどは3本（`権限確認省略モード`・`CICD`・`ログ整備`）で、ほかは5本・7本・8本と割れている。**本当に揃っているのは3つだけ**である。

- **フェーズ1が「前提の検証」**——設計の未決事項節が「テスト計画フェーズ1で解消する」と名指しするので、ここがずれると参照が壊れる
- **最後が「受け入れ」**
- **巻末が `## 設計との対応（抜けが無いことの確認）`**

中間のフェーズはイシューの中身で変わってよい。**原則のフェーズ数そのものも、今後の進化で変えてよい。**

### 該当が無いフェーズは、落としても「該当なし」と書いてもよい
どちらも認める。選ぶときの目安は次のとおり。

| 書き方 | 向いている場面 |
|---|---|
| **フェーズごと落として番号を詰める** | 落とすフェーズが複数あるとき。冒頭の前置きで理由を1〜2文書く（`イシューグループ_2026_0804_2219` が「このイシューは実 claude を一度も起こさない」と宣言して2つ落としている） |
| **節を残して「該当なし」と理由を書く** | 落とすのが1〜2個で、番号を過去と揃えたいとき。`設計§N` の「テスト計画フェーズ1で解消する」のような名指しがぶれない |

**どちらでも、理由は必ず書く。** 「無い」とだけ書くと、次に読む人が「忘れたのか、要らないのか」を判断できない。

### 文書を書き終えたら、文書間の整合を機械で確かめる
`要件` → `方針` → `設計` → `テスト計画` → `計画` は互いを参照し合うので、**目で読んで整合していると思っても抜ける**。書き終えるたびに次を通す。実際にこの4つとも一度ずつ踏んでいる。

| 何を確かめるか | 落ちていた例 |
|---|---|
| **方針の各節が設計のどこかに落ちているか** | 方針にしかない節が1つ残り、設計はそれを `§13` として参照していた（§13 は別の節） |
| **`§N` の参照先が実在するか** | 存在しない節番号への参照 |
| **裸の `§N` が自文書内を指しているか** | 他イシューを指すつもりの `§25` が2箇所。他イシューは `セルフホスト化設計§25` のように**名前を前置する** |
| **設計とテスト計画が同じことを言っているか** | 設計が「印は要らない」と決めた経路を、テスト計画が「印が立っていること」と書いていた |
| **設計の全節が計画のどこかで実装されるか** | — |
| **テスト計画の全項目が⛳でちょうど1回消化されるか** | — |

最後の2つは参考計画（`クローズ/セルフホスト化・マルチテナント対応/計画.md`）が巻末の整合表で守っている不変条件なので、**表そのものを機械で突き合わせる**のが早い。

### 追補ドキュメントは統合・削除済み
`〜 追補：〜.md` は 2026-07-28 に本文（`方針.md` / `設計.md` / `計画.md`）の巻末節へ統合し、**ローカルファイルは削除済み**。以後は本文が正。本文には訂正前の旧記述も併記してあるため、経緯を追いたい場合は本文の巻末節を読めばよい。

**リモート側の追補3コメントも削除済み**（2026-07-28 のフェーズ1同期時に確認）。イシューのコメントは `方針` / `設計` / `テスト計画` / `計画` / `実行レポート` の5件のみで、ローカルファイルが復活する余地は無くなった。

## ドキュメントの情報量を減らす方向の編集をするとき
統合・要約・整理などで既存ドキュメントを書き換える場合は、次の手順を踏むこと。

1. 編集前に対象ファイルをスクラッチパッドへ退避する
2. 編集後に `diff` で「削除・変更された行」だけを抽出し、意図した変更と一致するか1行ずつ照合する
3. 統合元がある場合は、統合元の全非空行が統合先に存在するかを逐語検索で確認する

**理由**：`MyDocs/` は git 管理外でありロールバック手段が無い。退避と差分照合が唯一の復元・検証手段になる。

### 逐語照合が通らない行は、行き先を1つずつ割り当てる
手順3は**丸ごと通ることのほうが稀**である。見出しを畳む・語を実態へ直す・判断そのものが覆る、のいずれかが必ず混ざるため。

そこで通らなかった行を「重要な断片は残っている」でまとめて片付けてはいけない。**それは照合の放棄**で、落とした行と落ちた行を見分けられなくなる。代わりに次を行う。

1. 通らなかった行**すべて**に、分類と**行き先の文字列**を1つ割り当てる
2. その行き先が統合先に実在することを、機械で確かめる
3. 割り当てられない行が1つでも残ったら、それが**気づかずに落とした行**

分類のうち「**判断が覆った**」ものは、覆ったこと自体を統合先に書き残す（「採らなかった案」の節など）。書かないと、次に読む人には**最初からそう決めていた**ように見え、なぜ変えたのかを問い直せない。

## ブラウザ側のストアを触るとき

### 「接続済み」と「一覧が出ている」を同じ意味にしておく
一覧の受信は `requestAnimationFrame` でまとめてから反映する（バーストで届くため）。ただし
**`GET /api/sessions` のスナップショットだけは束ねてはいけない**。接続1回につき1度しか
来ないので束ねる意味が無く、束ねると「接続済みと表示されているのに一覧はまだ空」という
隙間ができる。

この隙間は、テストの後片付けが「カードは0枚」と早合点して切り上げる形で表に出た。残った
カードが次のテストへ漏れ、**落ちるテストが実行のたびに変わる**という追いにくい壊れ方になる。

### E2E の後片付けは画面ではなくサーバに聞く
小窓の数を数えると「まだ描かれていないだけ」と「もう無い」を区別できない。`GET /api/sessions`
を直接読み、消す相手もIDで名指しすること（`.first()` だと消したい相手と押した相手がずれうる）。

### 動きを付けてよいのは低頻度の更新だけ
PTY のバイトと履歴の追記の経路にアニメーションを入れてはいけない（体感速度の生命線）。
一覧の小窓に `layout` を付けるのも禁止 — 並びが変わるたびに小窓が動き、**押そうとした瞬間に
的が逃げる**。一覧は「押して開く」ための画面なので、見栄えより狙いやすさを優先する。

### flex の中で `truncate` を使うなら `min-w-0`
flex の子は既定で中身の幅より小さくならないため、`truncate` を付けても縮まない。長い作業
ディレクトリのせいで隣の状態ラベルが縦に割れる、という形で表に出た。**縮んでよい要素にだけ
`min-w-0`、その他には `shrink-0`** を付ける。

### 端末の見た目は xterm のオプションでしか変えられない
WebGL レンダラを載せているので、カーソルも文字も **canvas に描かれる**。CSS を書いても届かない。
指定する場所は `TerminalPane` の `TERMINAL_OPTIONS` 1箇所に集約してある。

既定値をそのまま使うと**意図と違う見え方になることがある**。実例：`cursorStyle` の既定は
`block` で、カーソル位置の文字を塗り潰すため「上書きモードで打っている」ように見える
（実際の行編集は CLI 側の責務で、挿入モードのまま）。**振る舞いは正しいのに見た目だけが
嘘をつく**ので、動くかどうかのテストでは絶対に見つからない。

### xterm に口があるかは、型定義と**バンドルの中身の両方**で確かめる
「上流に口があるならそちらを使う」は正しいが、**同梱されている＝使える、ではない**。
実例：スマホのタッチで端末を遡れない件を調べたところ、VS Code 由来の `Gesture`（タッチを
スクロールへ変える部品）は `lib/xterm.js` に**丸ごと入っていた**。ところが対象を登録する
`addTarget` は**定義1件・呼び出し0件**で、型定義にも出ていない。**入っているだけで、誰も
使っていない。**

見る順序を決めておく。3つとも別のことを答える。

| 見るもの | 答えるもの |
|---|---|
| `typings/xterm.d.ts` | **公開されているか**（無ければ、こちらから呼ぶ手段が無い） |
| `lib/xterm.js` の定義と呼び出しの数 | **配線されているか**（定義だけなら死んでいる） |
| 入口となるイベントの**購読の数** | **その経路が生きているか** |

3つ目がいちばん効いた。`.xterm-viewport` は CSS で `overflow-y: scroll` かつ全面に敷いて
あるので「ブラウザにスクロールさせれば動く」と読めるが、**`scroll` の購読がバンドル全体で
0件**だった。つまりあの箱をどれだけ動かしても端末は1行も動かない。**CSS で直す道は
原理的に無い**と、実装を始める前に確定できた。

```bash
grep -c 'addTarget' web/node_modules/@xterm/xterm/lib/xterm.js   # 定義と呼び出しの合計
grep -o 'addDisposableListener([^,]*,"scroll"' …                  # 購読の数
```

**「無いこと」を確かめずに自前で書くと、上流に口があった場合に版が上がるたび擦れる。**
逆に、確かめずに「上流にあるはず」と設計すると、実装で行き止まりになる。どちらの損も
grep 数本で消える。

### 寄せる指定は、出たり消えたりする要素に付けない
`ml-auto` のような「並びを決める指定」を条件付きで描かれる要素に付けると、**その要素が
出ないときに寄せ先ごと消えて並びが崩れる**。実例：右端へ寄せる指定をモデルのバッジに
付けていたため、モデルが不明の間ずっと隣のバッジが左へ詰まっていた。

並びを決める指定は**必ず描かれる入れ物**のほうへ持たせる。入れ物ごと消える場合も、
「中身が1つも無ければ入れ物も出さない」と書けば余白だけが残ることもない。

### Enter の割り当ては、端末と入力欄で必ず揃える
**Enter と Shift+Enter が改行、Ctrl+Enter が送信。** 判断は `lib/keys.ts` に集約してあり、
端末（`TerminalPane` → `terminalKeyOverride`）と入力欄（`Composer` → `isComposerSubmit`）の
両方がここを見る。

**片方だけ直してはいけない。** セッション専用画面には入力口が2つあり、しかも同時に見えて
いる（入力欄はタブの外側に常設）。押し分けが食い違うと、同じキーの結果が「いまどちらに
焦点があるか」で変わることになり、**打っている本人には原因が分からない**。実際に、端末側
だけを先に読み替えて入力欄が取り残された状態が出荷されている。

送るものは2つで違う。**端末はバイト列**（改行 `ESC+CR` / 送信 `CR`）、**入力欄は素の
テキストに改行が入るだけ**で、包むのはサーバの仕事（`session/input.rs`）。判断だけを
共有し、送り方は各自が持つ。

#### 端末側（読み替え）の注意
xterm は Enter に修飾キーを見ておらず、Shift+Enter でも素の Enter と同じ CR を送る。
受け取る CLI から見れば**同じバイト列**なので区別のしようがない。読み替えは
`attachCustomKeyEventHandler` 1箇所で行う。実装するときの注意が2つある。

- **`term.input()` を通す。** `sendPtyInput` を直に呼ぶと送信口が2つになる
- **`event.preventDefault()` も要る。** xterm は隠しテキストエリアで入力を受けており、
  止めないとそこへ入った改行が別の入力として送られる（実際に、こちらが送った
  ESC+CR の直後に改行が届いて結局そこで確定した）

送るべき並びは推測しない。**CLI のバイナリが `/terminal-setup` で書き込む keybinding**
に答えが入っていることがある（改行は `\x1b\r` だった）。

#### 入力欄側の注意
素の Enter では **`preventDefault()` を呼ばない**。textarea の既定がそのまま改行になり、
`<form>` の中でも textarea の Enter は submit を起こさない。押し分けの判断材料
（`EnterKeyState`）に `shiftKey` を**入れていない**のも同じ考えで、見えないものは効かない。

### 端末を自動操作するときは Enter で送信できない
上の割り当ての結果、**選択ダイアログの確定も Ctrl+Enter になる**（実測：フォルダ信頼の
確認で素の Enter は無反応、Ctrl+Enter で確定した）。E2E の `typeLine` も Ctrl+Enter を
押している。ブラウザ越しに端末を操作するコードを書くときは、素の Enter を送っても
改行が入るだけで先へ進まないことに注意する。

**入力欄に何か残っている状態で送信すると、意図しないプロンプトになる。** 実 claude で
検証していて2回この形でターンを消費した。送る前に入力欄が空であることを画面で確かめる
（`❯` の行だけになっているか）。`Ctrl+U` は当てにしない — 消えたように見えて残ることがある。

### タッチの操作を確かめるときは、CDP でしか測れない
Playwright には3通りあるが、**使えるのは1つだけ**である。

| 手段 | リスナーへ届くか | ブラウザの既定動作が起きるか |
|---|---|---|
| `page.touchscreen.tap()` | 届く | タップのみ。**なぞりは作れない** |
| **CDP `Input.dispatchTouchEvent`** | 届く | **起きる** |
| `page.dispatchEvent('touchmove', …)` | 届く | **起きない**（合成イベントなので信頼されない） |

**`dispatchEvent` を使ってはいけない。** リスナーは呼ばれるので「動いた」ように見えるが、
パンも互換のマウス操作も一切起きないため、**握れているかどうかを一度も確かめないまま
緑になる**。`test.use({ hasTouch: true })` は**ファイル単位で効く**ので、土台（project）を
増やす必要は無い。

### `touchmove` を握るなら、**1回目から**握る
`preventDefault()` が効くのは `event.cancelable` が真のあいだだけで、**1回目の `touchmove`
で握らないと2回目から偽になる**。実測（`touch-action` 3通り × 握り方3通り）の結果が下記。

| `touch-action` | 一度も握らない | 1回目だけ握る | 毎回握る |
|---|---|---|---|
| 未指定 | 1回目だけ | **2回目まで** | 全部 |
| `none` ／ `pan-x` | 1回目だけ | **全部** | 全部 |

**「しきい値を超えてから握る」は成立しない。** しきい値は複数回の `touchmove` にまたがって
判定するので、超えたころには握れなくなっている。**握るかどうかは1回目に決め、しきい値は
「実際に動かすかどうか」にだけ使う。** あわせて `touch-action` を指定する（未指定だと、
1回目に握っても3回目から落ちる）。

**握らなかった場合も測ること。** 「毎回握る」だけを測ると `cancelable` が全部真になるので
「効いている」と読んでしまう。効いているのか、そもそも何も起きていないのかは、
**否定側を測って初めて区別できる**。

### 見た目の崩れはテストでは捕まらない
描画自体はされているので、要素の存在を見るテストは通ってしまう。差分の色が付いていない
（フェーズ3）・状態ラベルが縦に割れる（フェーズ4）は、どちらも**実物を目で見て**初めて
分かった。画面に手を入れたら、ビルドした単一バイナリを起動して Playwright MCP で見ること。

**壊れている状態を設定で再現できることがある。** 実例：`inject_status_line = false` に
するとモデルは永久に不明のままになるので、「片方のバッジだけが出る」状態をそのまま作れた。
直す前・直したあとを並べて撮ると、崩れているかどうかを推測せずに言える。

### テストの既定値が壊れた状態だと、全テストが崩れたまま緑になる
テストのデータを作るヘルパの既定値は、**そのまま「検証される状態」になる**。既定が
`model: null` だったので、小窓のテストは全部モデル不明＝崩れた状態で通っていた。

**片方が無い状態を既定にするなら、その状態の見た目を1本は検査する。** そうでなければ
「よく通る道」ではなく「誰も見ていない道」を全テストが通り続けることになる。

## 利用者が打つ・貼る値を受け取るとき
本アプリは **WSL の上で動き、利用者は Windows 側から値を持ってくる**。パスなら `\` 区切り、
`\\wsl.localhost\...`、`"` で囲まれた「パスとしてコピー」の形が普通に来る。開発者が打つ形
（きれいな絶対パス）だけを想定すると、実運用の初手で弾かれる。

### 入力を書き換えず、解釈を並べて先頭から当てる
「`\` を `/` に置換する」のような**破壊的な正規化はしない**。Linux では `\` もフォルダ名に
使える文字なので、実在のフォルダを開けなくする。`session/cwd.rs` のように
**入力そのままを先頭に置いた候補の列**を作り、最初に当たったものを採ること。
これなら従来の解釈が一切変わらないまま、受け取れる形だけが増える。

### 解釈した結果はエラーに書く
読み替えが効かなかったのか、読み替えた先が無いのかは、利用者からは区別できない。
「見つからない」と言うときは**何として読んだのか**を添える。

## 端末の表示を読んで判断するとき
初期実装§10 が定めた「構造化ビューは ANSI を解析しない」は今も守る。ただし
**「キーを送ってよい画面か」「いま TUI が何を表示しているか」を確かめる用途**では
端末を覗く（自己修復のフォルダ信頼の確認、権限モードのフッタ読み取り）。その際の約束。

### 読む対象は画面ではなく生のバイト列
`tmux capture-pane` はレンダリング後の画面を返すが、ダッシュボードが持っているのは
PTY から流れてきた**生のバイト列**である。この2つは同じではない。

実例：TUI のフッタは語ごとに別々に書かれ、間はカーソル移動で埋められる。画面では
`⏵⏵ accept edits on` と見えるが、生の並びは `⏵⏵accepteditson` で**語間の空白が無い**。
画面で見えている形のまま照合すると、単体テストは通るのに実物では永久に一致しない。

**目印を照合するときは、制御シーケンスを落としたうえで空白も取り除く。**
折り返しで語が行をまたいで割れても同じ理屈で拾える。

### 実測するときは、使うときと同じ対象を見る
上の件は、前提の実測を tmux（＝画面）で行い、実装は生のバイト列を読んでいたために
起きた。**測るときと使うときで読む対象が違えば、測った値はそのまま使えない。**
画面で確かめたことは、生のバイト列でも成り立つかを別に確かめる。

### 画面を語で照合するなら、その語が画面の別の場所にも出ないかを疑う
実CLI のテストで実際に踏んだ。信頼確認の有無を裸の `trust` で判定したら、**起動後の
welcome 画面の What's new**（"added a workspace **trust** prompt …"）に一致し、
welcome を信頼確認と読み違えて分岐が180秒回り続けた。症状は「画面が進まない」なので、
照合の側を疑うまでに時間がかかる。

**その画面にしか出ない並び**（ダイアログの文言 `do you trust` など）で照合する。
リリースノートやヒントの欄は毎版入れ替わるので、「いまは出ない」ことは根拠にならない。

### 動き続けるものに「落ち着いた状態」を仮定しない
claude の TUI は考えている間スピナーを回し続ける。**「もう動かない画面」という状態が存在しない。**

これを知らずに「操作してから N 秒後の画面が、描き直しが終わった後の画面と一致するか」を実測の指標にすると、何秒待っても一致せず、数字だけを見て「N 秒では足りない」と読み違える。実際にそう読み違えた（正しい問いは「その操作に対する**描き直しが N 秒の中で終わったか**」だった）。

**指標を作る前に、比べようとしている状態が対象に存在するかを確かめる。** 存在しないなら、比較ではなく所要時間を測る。

### 端末を待ち合わせるなら「出力が途切れたこと」が使える
逆に、動き続ける性質は待ち合わせに使える。考えている間は出力が止まらないので、**一定時間ぴたりと出力が無いこと**がそのままターンの完了を意味する。画面を読む必要がないので、端末エミュレータを持っていない場所（＝エミュレータそのものを検証している場所）でも使える。

### スクロールバック全体を毎回コピーしない
1秒周期の見張りから呼ぶような場所では、`Session::scrollback_text()`（既定 1MiB）を
使うとセッション数だけ無駄が積み上がる。末尾だけ読む `scrollback_tail` を使う。
フッタのように「更新のたびに書き直されるもの」は末尾に必ずある。

## 擬似 claude（fake-claude）を触るとき

### 行編集を切ってあるので、制御シーケンスは自分で解釈する
Shift+Tab（`ESC[Z`）のように**改行を伴わないキー**を受け取るため、起動時に
`stty -icanon` で行編集だけを切っている（エコーは残す。ブラウザの端末に打った文字が
出るのはエコーの働きで、既存のテストがそれを見ている）。

その結果、それまで端末が処理してくれていたものを自分で扱う必要がある。

- `Ctrl+U`（0x15）は入力行を消す
- CSI は**終端バイト（0x40〜0x7E）まで読み切る**。途中で止めると残りが本文へ紛れ込む

### 本物の挙動に合わせる。合わせられないなら、そう書く
擬似 claude は「課金なしで毎回通せる」ことに価値があるので、**本物と違う形にした瞬間に
テストが嘘になる**。フッタの語句・巡回順・フックが運ぶ値は実測に合わせてある
（ローカルイシュー「権限確認省略モード」設計§11）。

### 起動完了の合図（`ready`）を出す位置に気をつける
確認の画面を出しているあいだは `ready` を出さない。先に出すと、受諾より前に届いた
指示が黙って捨てられ、「フックが飛ばない」という分かりにくい形でしか表に出ない。

### 同じ種類のフックを2回撃つときは、`fire_hook` の印では待てない
`Watcher::wait_for` は**溜まった出力に印が含まれていれば即座に返る**（`tail` に対する
`contains`）。したがって `fire_hook(…, "SessionStart", …)` を2回呼ぶと、**2回目は1回目の
印で通り抜ける**——撃ったつもりで、届く前に判定へ進む。

`/resume` や `/clear` の再現は同じイベントを2回撃つので、ここを踏みやすい。実際に
「呼び戻したのにトランスクリプトが張り替わらない」という**製品側の不具合に見える形**で
現れた（実際は製品は正しく、テストが早すぎただけ）。

**効果そのものを待つ。** 状態なら `wait_for_status`、それ以外は上限付きの巡回で
「変わったこと」を待つ。印を待つのは、その種類を**その回だけ**撃つときに限る。

### 擬似 claude の `transcript_path` は、payload の `session_id` を上書きしても動かない
場所は**起動時に渡した ID** から組み立てられる（`fake-claude.rs` の `transcript_path()`）ので、
`hook SessionStart {"session_id":"…"}` を撃っても控えは変わらない。本物の `/resume` と同じく
**フックに新しい場所を名乗らせる**（`{"transcript_path":"…"}`）のが正しい再現になる。

## 利用者のグローバル設定（`~/.claude/settings.json`）を触るとき
`config.toml` はこのダッシュボードの持ち物だが、`~/.claude/settings.json` は**利用者と
他の claude プロセスの持ち物**である。同じ「設定を書き戻す」でも扱いが違う。

### 書いてよいキーを型で縛る
「このファイルを書く関数」ではなく「**このキーだけを書く関数**」にする。他のキーを
渡せない形にしておけば、あとから範囲が広がる余地がなくなる。

### 解析して書き直さず、その場を差し替える
`serde_json` で読んで書き直すと、**キーの並びが辞書順に変わりインデントもこちらの都合に
なる**。生のテキストから対象キーの値の範囲を見つけて差し替えれば、触らなかったバイトは
1つも動かない（`settings.rs` が `toml_edit` でやっていることの JSON 版）。

### 読めなければ書かない。作りに行かない
無い・壊れている・権限が無い、いずれの場合も何もしない。利用者の設定ファイルを、
ダッシュボードが勝手に生やしてよい理由が無い。

### 対象がプロセスに1つしかないなら、ロックもプロセスに1本
セッションごとに持つと、2本が同時に書いたときに元の値が永久に失われる。
「読んだ時点と違ったら書かない」という自衛だけでは、**汚染を防ぐのではなく汚染を固定する**。

### 長く持つロックの手前では、待たせずに断る
そのロックを持つ処理が数十秒かかるなら、**行列に並ばせた時点で他の利用者まで巻き込む**。
利用者が連打しただけで、無関係なカードの操作が数十秒後になる。

「待たせて順番に叶える」より「その場で断って選び直してもらう」。ロックを取る前に
専用の印で権利を1つだけ取り、取れなければ即座に理由を返す。

**画面に見せる状態を排他の印に流用しない。** 「送った」ことを示す値は送ったあとに
立つので、送る前の隙間を2本目が通り抜ける。見せる状態と排他は別に持つ。

### 戻した値がそのまま残るとは限らない
CLI が起動時に綴りを正規化することがある（`opus` → `opus[1m]` を実測）。意味が同じなら
追いかけない。「戻したのに一致しない」を異常として扱わないこと。

### テストと E2E は本物のファイルを相手にしない
差し替え口（`claude_settings_path`）を設定に持たせ、テストは必ずそちらを指す。
環境変数を書き換える方式にすると、並行して走る他のテストを巻き込む。
`state_dir` を差し替えられるようにしてあるのと同じ理由。

## `trap` で後始末を書くとき

### `exec` があると `trap` は走らない
`exec` はシェルごとプロセスを置き換えるので、`EXIT` の trap は**実行されない**。
終了コードを持ち越して `exit` する形にする。

```sh
STATUS=0
"${TARGET}" "$@" || STATUS=$?
exit "${STATUS}"
```

`scripts/test-cli` でこれを踏み、利用者のグローバル設定が汚れたまま残った。

### 足しただけでは走らない。走ることまで確かめる
偽の対象ファイルを相手に「失敗しても戻る・終了コードは持ち越す・バックアップは片付く」を
一度通しておく。後始末は**壊れたときにしか使わない**ので、壊れる前に確かめないと
壊れたときに初めて壊れていたと分かる。

## 長く生かしたいプロセスを起こすとき

### 起こしたら・落としたら・張り替えたら、その場で「いま動いているもの」を直す
常駐するものは**セッションをまたいで残る**。次に触る人はその存在も版も知らないので、書いておかないと必ず取り違える。

対象は4つ。**常駐するものを起こした／落とした／起こし直した**、**トンネルを張った／張り替えた**、**外に何かを立てた／壊した**、**ログの出力先や設定の場所を変えた**。書き先は `.claude/docs/knowledge/いま動いているもの.html`。

書くのは「何が・どこで・どの版で・どう起こしたか」の4つだけでよい。経緯は実行レポートにあるので繰り返さない。

### ここは「いま」だけを持つ。履歴を積まない
**残す基準はひとつ。「次に触る人がこれを知らずに動くと事故るか」。** 是なら書き、否なら書かない。

したがって**終わったことは消す**。落としたものの行、壊した環境の項、戻した設定の注記——役目を終えたものは、その場で**消すか、いまの姿へ書き換える**。「前はこうだった」は残さない。それは実行レポートの仕事。

判断に迷ったら、**分量で気づく**。ここが増える一方になっているなら、実行レポートに書くべき粒度が混ざっている合図。1枚を開いて数十秒で現状が掴めなくなった時点で、書きすぎている。

書く契機は「大きな作業が一区切りついたとき」でよい。作業の途中経過をここへ流さない——動いている最中の状態を書いても、次に読む人が見る頃には嘘になっている。

**トンネルは、URL とその先を必ず対にして書く。** ここが最も間違えやすい——同じ機械に `--url http://127.0.0.1:8788` の転送が動いていると、`ps` の表示だけで「あの URL は 8788 だ」と読めてしまう。実際には別の機械の転送が作った URL だった、ということが起きる。

### 症状を断定する前に、いま何を見ているかを疑う
「画面に出ない」「更新されない」の原因を、キャッシュや実装の不具合に置きたくなる。だが**見ている先が思っている先とは違う**、という形がいちばん多い。

順番を守る。**まず同じものを2つの経路から取って突き合わせる**（前段越しと直接、など）。結果が食い違えば、その時点で「相手が違う」と分かる。一致してから初めて、キャッシュや実装を疑う。

やってはいけないのは、確かめる前に利用者へ強制リロードを試させること。**外れたときに何も分からないうえ、原因から遠ざかる。**

### 「配った」と「入った」は別
リリースを出しても、誰の機械にも自動では入らない。とくに**ソースビルドで動かしているものは、リリースと無関係**——`git pull` → `make build` → 起こし直す、をしない限り何も変わらない。

「リリースしたのだから最新のはず」は、実機で最も時間を溶かす思い込み。版を確かめるのは、起動ログの1行か `--version`。

### 版を上げたら、**繋いでいる側も**起こし直す
ダッシュボードを新しくしても、**セッションホストは起こしたときの版のまま走り続ける**。ファイルを置き換えただけでは効かない。

両者の版が食い違うと、**新しいサーバが古いホストを正しく断る**——それ自体は設計どおりだが、画面には「この PC は版が古い」と出る。**ダッシュボードのヘッダには新しい版が出ている**ので、「更新したのに使えない」に見える。実際に踏んだ。

版を上げる作業は、**配る → サーバを入れ替える → 繋いでいるものを入れ替える**の3段で1組と数える。2段目で止めると、症状が「機能が使えない」の形で出るので、原因が版のずれだと気づきにくい。

起こし直すと**抱えている claude は道連れになる**ので、落とす前に何が子として走っているかを数える。なお `agent_id` はペアリングトークンから決まるため、起こし直しても**同じ PC のまま**——PC に紐づく記録が孤児になることはない。

### 別の実行ファイルで動く子は、親と別の版になりうる
「走っているのは起こしたときの版」は**その実行ファイルの中身についてだけ**成り立つ。子が
**別の実行ファイル**なら、落として立て直した時点でディスク上の新しいものが起きる。

これは事故ではなく**逃げ道**になる。`transcript-parser` は親（セッションホスト）が
`spawn` し直す作りなので、**子だけを PID 直指定で落とせば、抱えている claude を道連れに
せずに新しい版へ入れ替わる**。監視は保存済みの位置から張り直るので履歴も欠けない
（`parser.rs` の `run()` と `pump()` の冒頭）。実際に、修正前の版のまま走っていたパーサが
12.9GB まで肥大したとき、この形で 11.7MB へ戻した——**親は 0.1.11 のまま、子だけ 0.1.12** に
なった。

したがって**版を語るときは親子を分けて書く。** 「このホストは 0.1.11」とだけ書くと、次に
読む人は子も同じだと読む。`いま動いているもの.html` にも分けて書くこと。

### 「繰り返し切れる」の前に、誰の子として起こしたかを見る
外の機械へ張った転送や常駐が繰り返し落ちるとき、原因を回線や相手側に置きたくなる。だが**ツール呼び出しの子として起こしていると、呼び出しの終了やタイムアウトで巻き添えで殺される**。症状は「また切れた」で、回線の問題と見分けが付かない。

見分け方は簡単で、**張り直しの回数を数える**。保険の再起動が一度も発動していないのに落ちているなら、落としているのは外ではなく自分の側にある。

### 出力先はリポジトリの外に置く
起こし直すときにログを `>> dashboard.log` のようにリポジトリの中へ向けると、**作業ツリーに追跡外のファイルが増える**。次に触る人が `git status` を見て「何か中途半端に残っている」と誤解するし、追跡外のまま育つ。

常駐させるものの出力先は、リポジトリの外（例：`~/<アプリ名>-run.log`）にする。走り出してからでは向け直せない（開いた fd は差し替えられない）ので、**起こす前に決める**。

## 現物の状態を数えるとき
「いま何があるか」を数え損なうと、**その上に立てた計画ごと間違える**。しかも数え損なった側は正常に見える。

### `cd` はセッションに残る。以後の相対パスは別の場所を指す
1つの呼び出しの中で `cd` すると、**次の呼び出しの作業ディレクトリもそこになる**。ドキュメントを読むために深い場所へ移ったあと、`ls server/target` のような相対パスで現物を確かめると、**存在するものが「無い」と出る**。

実際に踏んだ。`MyDocs/ローカルイシュー/…` へ移ったまま `du -sh server/target` を打ち、「`make clean` 済み・フルビルドが要る」という前提で計画を1枚書いた。実際はビルド済みで、debug ビルドは15秒で終わった。

**リポジトリの現物を数えるコマンドは、必ず絶対パスで書く。** 「無い」と出たときこそ、まず `pwd` を疑う。

**そもそもサブディレクトリへ `cd` しない。** この罠は「絶対パスで書く」を守っていても抜ける——移った側と、後で相対パスを使う側が**別の呼び出し**だからである。実際に4回踏んでおり、3回目は `./scripts/cargo: No such file or directory` として出た（`server/crates/…/src` へ移った次の呼び出しでラッパーを叩いた）。読むだけなら移らずにパスを渡せば済む。移る必要が本当にあるときは、**その呼び出しの中で完結させる**（`(cd X && …)` のように括る）。

**4回目は「読むため」ですらなかった。** `MyDocs/` のチェックボックスを更新する python を `cd <イシューのフォルダ> && python3 …` で走らせ、その次の呼び出しで `./scripts/test-cli` が 127 で即死した（WSL 落ちイシューの段5。同じイシューの段4 でも踏んでいる）。**書き込みでも移動でも、`cd` が残ることに変わりはない。**

**5回目は「1つの返信に並べた2つの呼び出し」だった。** 独立した用事なので同時に投げたが、**作業ディレクトリは呼び出しをまたいで共有されている**。先に走ったほうの `cd MyDocs/ローカルイシュー` が、もう一方の `cd MyDocs/ローカルイシュー/クローズ && ls` に効いて `No such file or directory` で落ちた。**並べたから独立、ではない。** 並列に投げるつもりなら、`cd` を含む呼び出しを混ぜないこと。

**6回目は「括るのを1つだけ忘れた」だった。** 同じ作業の中で `(cd web && npx …)` と括った呼び出しをいくつも投げていたのに、控えを取る1つだけ `cd web && cp … && python3 …` と裸で書いた。**そこから先の呼び出しが全部 `web/` を作業ディレクトリにし**、次の `grep … web/e2e/helpers.ts` が「そんなファイルは無い」で落ちた。**括る癖が付いていても、1つ抜ければ同じところへ落ちる**——だから「気をつける」ではなく、`cd` を書いたら必ず括る、を形にすること。

**7回目は「同じ相対パスへ二度入ろうとした」だった。** イシューを数えるために `cd MyDocs/ローカルイシュー && ls` と裸で書き、**十数回あとの呼び出し**で同じ `cd MyDocs/ローカルイシュー && …` を書いて `No such file or directory` で落ちた。既にそこに居るので、その下にもう一段は無い。**症状が「フォルダが消えた」に見える**点が厄介で、上の「イシューのフォルダは作業の途中で動く」と**まったく同じ顔**をする。**移動と削除と『既にそこに居る』の3つが、片方のパスだけを見ていると区別できない。** 落ちたら `pwd` を1回打つ。

したがって、規則は「読むときは移らない」ではなく**「`cd` を裸で書かない」**である。ヒアドキュメントで python やスクリプトを流し込むときほど `cd X && …` と書きたくなるが、そこが次の呼び出しへ効く。

```bash
# 悪い：この cd は次の呼び出しにも残る
cd MyDocs/… && python3 - <<'PY' …

# 良い：括って閉じ込めるか、パスをスクリプトへ渡す
(cd MyDocs/… && python3 - <<'PY' … )
```

**見分け方**：終了コード 127（`No such file or directory`）が出たら、まず `pwd` を疑う。127 は「走って落ちた」ではなく「**走っていない**」なので、クォータを使うコマンドなら被害は無い——が、走ったつもりで結果を読むと取り違える。

### 行を数える正規表現は、実物の1行に当ててから使う
ログの行数を数える正規表現を推測で書くと、**取りこぼしが「そういう形の行が少なかった」に見える**。

実例：`target` を `[^:]+` で拾うと、`agentdashboard_core::cli` のような**`::` を含むターゲットだけが丸ごと落ちる**。151行のうち142行が該当していたのに、集計は「tracing の行は54行」と出た。**落ちた側は行数にしか現れない**ので、値が小さいこと自体からは気づけない。

当てる前に、**実物から1行コピーして単体で照合する**。合計が元のファイルの行数と一致することも併せて見る（分類の総和が全体になっているか）。

### 検査は、正解と分かっているもので較正してから当てる
上の裏返し。**書いたばかりのものへ最初に当てると、落ちたのが中身なのか検査なのか区別できない。**

実際に踏んだ。テスト計画の項目が `- [ ] 〜こと` の形かを「行の末尾が `こと`」で測ったところ、111 件中 **48 件が違反**と出た。だが実際は違反ではなく、**この PJT の作法では「こと」で言い切ったあとに説明を続ける**（クローズ済みのテスト計画も同じ形）。検査の側が間違っていた。

気づけたのは、**同じ検査を既存の（正しいと分かっている）ファイルへ当て直した**からである。あちらは 38 件中 5 件しか末尾が「こと」でなく、**13% しか通らない検査**だと一目で分かった。「含むか」で測り直すと両方とも 100% になる。

したがって、文書や台帳の形を機械で見るときは順序を決めておく。

1. **既存の正解データへ当てる**（クローズ済みのイシューの同じ種類のファイル）
2. **ほぼ 100% 通らなければ、検査のほうを直す**
3. そのあとで、新しく書いたものへ当てる

**この順序を飛ばすと、自分の書いたものを疑って直しにいくことになる。** 直す必要が無いものを直すのは、時間だけでなく**正しかった形を壊す**。

### 対照実験は、変数を1つだけ動かす
使い捨ての口を立てて「こちらは通る」を見せるのは強い手だが、**ついでに別のものまで変えると、
結論がまるごと外れる**。

実際に踏んだ。Windows のブラウザから 8787 が `ERR_CONNECTION_RESET` で開けず、
**使い捨ての HTTP サーバを立てて Windows から叩いたら通った**ので「アプリ固有の問題だ」と読んだ。
ところが**使い捨て側は別のポート（18787）で立てていた**。真の原因は
**ポート 8787 に紐づく Windows 側の `netsh portproxy`**（行き先の WSL 側に誰も居ない）で、
**ポートを変えた時点で、疑うべきものを実験から外していた**。

そのまま「listener が古いから転送の対応付けが腐ったのだろう」という仮説へ滑り、
**無関係な起こし直しを1回行った**（生きたカードが0枚だったので無害だっただけ）。

**決め手は、変えずに見ることだった。**

```
netstat.exe -ano | grep ':8787'      # その番号を Windows 側の誰かが握っていないか
```

規則は2つ。

- **疑っている変数以外を動かさない。** 使い捨てで対照を作るときほど、ポート・パス・利用者を
  「ついでに」変えたくなる。**変えた瞬間、その実験は別の問いに答えている**
- **「こちらは通る」が出たら、何を変えたかを数え直す。** 1つなら結論してよい。2つ以上なら、
  **通った理由はまだ分かっていない**

### `git diff` は「誰も触っていない」の証拠にならない
**コミット済みの変更は差分に出ない。** だから `git diff` がきれいでも、「自分が読んでから誰も触っていない」とは言えない。

実際に踏んだ。Edit が `the file had been modified on disk since you last read it` と言ったので `git diff` を見たところ、**自分の追記15行だけ**（削除ゼロ）だった。そこで「外部変更は起きていない」と結論したが、**間違いだった**——別のセッションが同じファイルを直して**コミットまで済ませていた**ので、差分には自分のぶんしか現れなかったのである。

`git diff` が答えるのは「**いま未コミットの変更は何か**」であって、「**自分が読んでから何が起きたか**」ではない。問いと道具が食い違っている。

**読んだ時点の commit からのログを見る。**

```bash
git log --oneline <読んだ時点のHEAD>..HEAD -- <ファイル>
```

そして**相手の変更が生き残っているか**は、差分ではなく**中身**で確かめる。相手のコミットが足した見出しを拾い、それが今もファイルに在るかを見ればよい。

```bash
git show <相手のコミット> -- <ファイル> | grep '^+###'
```

**このプロジェクトは複数のセッションが同じリポジトリを同時に触る。** とくに `.claude/docs/guideline.md` は全セッションが追記する共有の置き場所なので、**ここを編集するときは毎回この状況が起こりうる**。あの注記が出たら、まず本物だと思って確かめること。

### 数えた結果で、実際に止まる形にする
数えるだけ数えて、**その結果と無関係に次の行が走る**書き方をしてしまうことがある。守っているつもりで何も守っていない。

実際に踏んだ。実機を起こし直す前に「生きたセッションが無いか」を数えたが、`kill` は同じコマンド行の後ろに `;` で繋いであり、**数えた結果を一度も見ていなかった**。たまたま全部終わっていたので無害だったが、**生きた claude を道連れにする経路がそこに開いていた**。

```bash
# 悪い：数えるだけ数えて、結果に関係なく落とす
生きている数を数える; kill "$PID"

# 良い：数えた結果で止まる
N=$(生きている数を数える)
[ "$N" -eq 0 ] || { echo "生きているセッションが $N 本あるので止めます"; exit 1; }
kill "$PID"
```

**「確かめてから壊す」は、確かめた値が分岐に入って初めて成立する。**

### API が返す欄を、形を見ずに文字列と決めつけない
`/api/sessions` の `status` は文字列ではなく `{"kind":"ended","ok":true}` という入れ子である。文字列として読む前提で書くと、**全部が「知らない値」に落ちて、判定が黙って一方へ倒れる**。

上の失敗の原因もこれで、`isinstance(status, str)` が偽になり**全カードが「生きている」と数えられた**。落ちた側は例外を投げないので、数字が出ている限り気づけない。

**1件を丸ごと出してから絞り込む。** `curl … | python3 -m json.tool | head -40` の一手を惜しまない。

## プロセスの生き死にを測るとき

### `ps` の `-e` は `-p` に勝つ
子孫を追うつもりで `ps -eo ... -p <PID>` と書くと、**`-e`（全プロセス）が勝って全部出る**。PID で絞るときは `-e` を外す。気づかないと数万行の出力から目視で探すことになる。

### シグナルの効き方は、起こし方で変わる
同じ実行ファイルでも、**シェルスクリプト経由で `&` を付けて起こした場合と、直接呼び出した場合で SIGINT の結果が変わった**（前者では届かず、後者では死んだ）。「このプロセスはシグナル X で死ぬ」を測るときは、必ず `/proc/<PID>/status` の `SigIgn` / `SigCgt` を併せて読み、**無視・捕捉されていないことを確かめてから**結論を出す。

判定に使うなら **SIGTERM か SIGKILL**。この2つは起こし方に左右されない。

### 親を落として子が死ぬかを見るときは、まず構造を1枚撮る
`ps -o pid,ppid,pgid,sid,tty` を落とす前に撮る。**プロセスグループやセッションが親と同じかどうかで、シグナルが届く経路がまるごと変わる**。擬似ターミナル越しに起こした子は `setsid` されて別セッションになっていることがあり、その場合プロセスグループ宛のシグナルは届かない——それでも親の死で制御端末が切れて道連れになる、という別経路が効く。**「届かない」と「死なない」は別物。**

### 親を先に消しすぎない。**子が「起動時の親」を撮る前に消えると、永久に孤児にならない**
「親が消えたら子が自分で終わるか」を測るとき、親役を**起こしてすぐ**終わらせてはいけない。

子の側は起動処理のどこかで自分の親IDを控える（パーサなら `spawn_ticker` の `born_under`）。
**その1行が走る前に親が消えていると、控えられるのは既に再親付けされたあとの親**になる。
以後どれだけ待っても「起動時の親」と「今の親」は一致し続け、**判定が一度も真にならない。**

```bash
# 悪い：親役が子の起動より先に消えうる
bash -c "子 & echo \$! > pid"

# 良い：親役を数秒生かしてから消す（子が親を控える時間を与える）
bash -c "子 & echo \$! > pid; exec timeout 3 tail -f /dev/null"
```

症状は「**子が終わらない**」なので、製品のほうを疑うことになる。実際に疑いかけた
（WSL のイシュー 段3 の裏取り）。**控えた値そのものを確かめる**か、上のように親役の寿命を
明示するかのどちらかにする。

### プロセスが消えるのを待つのに `sleep` は要らない
`tail --pid=<PID> -f /dev/null` はその PID が消えるまで待つ。`timeout` と組めば
**「N 秒以内に消えたか」がそのまま終了コードで返る**（0 なら消えた・124 ならまだ居る）。
決め打ちの `sleep` と違って、早く消えればその場で返るので測定が速い。

### 後始末は PID 直指定でだけ行う
`pkill -f` を使わない理由は別節のとおり。測定で起こしたプロセスは**起こした時点で PID を控え**、その PID に対してだけシグナルを送る。同じ機械で実機や他セッションが動いている前提で書く。

### 「動いているか」を数える2つの罠。**どちらも黙って逆の答えを出す**
1つのやり取りの中で両方を踏んだ。**数字が出るので、間違っていることに気づけない。**

| 書き方 | 何が起きるか |
|---|---|
| `ps -eo cmd \| grep -c "[a]gentdashboard-agent"` | **自分のコマンド行を数える。** `[a]` の細工はコマンド行に**パスとして**同じ文字列が入っていると効かない（`~/agentdashboard-agent/agent.toml` を同じ行で参照していた）。止まっているのに **3** と出た |
| `ps -eo comm \| grep "^agentdashboard-ag"` | **`comm` は15文字で切られる。** `agentdashboard-agent` は `agentdashboard-` までしか出ないので一致しない。動いているのに **0** と出た |

`pgrep -f` / `pkill -f` の自己一致（別節）と根は同じで、**現れ方だけが違う**。

**実行ファイルの位置で照合する。** 名前の断片ではなく、起こしたときのパスと引数で見る。

```bash
ps -eo pid,etimes,args | awk '/release\/agentdashboard-agent --config/ && !/awk/ {print $1}'
```

待ち受けているものなら、**ポートから引くほうが確かである**（`ss -ltnp` の `pid=` を読む）。プロセス表を文字列で撫でるより、**そのポートを実際に掴んでいる者**を見るほうが問いに近い。

## 擬似 claude に新しい挙動を足すとき

### 「本物がやらないこと」もやらせない
本物より**気を利かせてはいけない**。例：本物は `/model` でモデルを変えても `statusLine` を
走らせない。擬似が走らせてしまうと、楽観更新と確定という経路が一度も試されないまま
「動いているように見える」テストになる。

### 本物が持っている抑制も真似る
デバウンスや間引きを省くと、擬似のほうが**重くなる**。300ms のデバウンスを省いたせいで
1行ごとに子プロセスが起き、行を多く送るテストが軒並み重くなって、資源を取り合う
別のテスト（コアレッシングの測定）が巻き添えで落ちた。

## 負荷に左右される数値をテストにするとき
「比なら機械の速さに左右されない」は**成り立たないことがある**。他のテストと資源を
取り合うと、比較対象の側も一緒に詰まって比が縮む。

そういう項目は `#[ignore]` を付けて `make perf` 側へ寄せる。Makefile が
「数値を合否にしないのは、他の作業の負荷で落ちるテストは役に立たないため」と
書いているとおり。

### 寄せるだけでは足りない。判定が残っていると、他の実測値まで採れなくなる
`make perf` は落ちた時点で打ち切られる。**記録を採るための入口に判定を残すと、
1本落ちただけで残りの数値が採れなくなる**（比を守るために、記録という目的のほうを
失う）。判定は「明らかに壊れたら落ちる」水準まで緩め、値そのものは印字にする。

例：コアレッシングの「フレーム数が半分以下」は、この開発機では境目に張り付いており
**変更の前後どちらでも5回中5回落ちた**。「合流したほうが確かに少ない」まで緩めても、
合流が丸ごと効かなくなったことは捕まる。

### 疑ったら、変更前のツリーで同じ回数だけ測る
**テストを増やしたら、既存の測定が落ちるようになっていないか確かめる。**
変更前のツリーで通ることを確認すれば、自分が原因かどうかは切り分けられる。

1回ずつ比べても分からない。散る値なので、**前後それぞれ複数回**測って分布を見る。
変更前のコミットは `git worktree add` で別の場所へ展開し、`scripts/cargo` の
`AGENTDASHBOARD_CARGO_DIR` / `AGENTDASHBOARD_CARGO_TARGET_DIR`（どちらもリポジトリ相対）
で向ければ、いまの作業ツリーを触らずに測れる。`web/dist` は自分で作る必要がある。

## 直した不具合に回帰テストを書くとき

### 直す前のコードで落ちることを確かめて、初めて回帰テストになる
通ることだけを見ると、**何も検証していないテストを緑のまま抱え込む**。直したコードを
一時的に元へ戻し、書いたテストが落ちること・失敗メッセージに現物が出ることまで見る。

### 壊し方が空振りしたら、**テストが壊す対象から期待値を作っていないか**を見る
定数を壊す形の検査（「回数を1にする」など）は、テスト側が同じ定数から回数を組み立てていると**一緒に動いて通ってしまう**。番人にするなら、**その1本だけは数を字で書く**こと。

### 落ちるはずのテストが通ったら、テストではなく「戻し方」を疑う
同じ変更で複数の仕掛けを入れていると、**片方を戻しても、もう片方が旧挙動の再現を
邪魔する**。実例：学習の条件から語幹の判定を外しただけでは、同時に入れた別の分岐が
先に弾いていて、旧挙動にならなかった。

戻すのは「その不具合を生んでいた判断そのもの」まで。関係する分岐を全部たどること。

### 新しく足した口には「直す前」が無い。**壊し方のほうを、テストごとに用意する**
不具合の修正なら「直す前のコードで落ちる」を見れば済むが、**口を1つ足す**種類の変更には
直す前が存在しない（その口自体が無かったので、テストはコンパイルすら通らない）。

代わりに**壊し方を作って落とす**。ただし1通り壊して全部落ちることを見ても足りない。
**テストごとに、そのテストが狙っている壊し方で落とす**こと。

実際に踏んだ。見張りの解除（`DirWatcher::retain`）へテストを2本置き、まず「解除も
一覧の間引きもしない」形へ壊したところ、**落ちたのは1本だけだった**。もう1本
（「外したディレクトリは張り直せる」）は、見張りが残っているので張り直す必要が無く、
追記すれば当然合図が来て**通ってしまう**。狙っていた壊れ方（解除はするが一覧から
落とし忘れる）で壊し直して、初めてそちらが落ちた。

**1通りの壊し方で全部落ちるなら、それはテストが1本ぶんの働きしかしていない合図**でもある。
落ちる組み合わせが分かれて初めて、2本が別々の性質を見ていると言える。

なお、**壊し方を作れないテストもある**（不変条件を固定する純関数のテストなど。引き算の
実装へ書き換えるのは1行の反転では作れない）。**その場合は「確かめていない」と書く。**
確かめた1本と確かめていない1本を、同じ顔で並べない。

#### **どの壊し方でも落ちないテストは、書いた直後にできる**
「壊し方を当てる」は不具合を捕まえるためだけの手順ではない。**書いたばかりのテストが
何も確かめていないことを見つける手順**でもある。

実際に、純関数へ21本置いて9通り当てたところ、**2本がどの壊し方でも落ちなかった**。

| 空振りしていた形 | なぜ通ったか |
|---|---|
| 端数の持ち越しを見るテスト | 測り方の都合で**余りが偶然0**になっており、持ち越しを捨てる実装でも同じ結果になった |
| しきい値を見るテスト | しきい値（8px）が**1単位（15px）より小さい**ので、しきい値を無視する実装でも「1単位に満たないから動かない」だけで通った |

どちらも**境目の値を、確かめたい性質が現れる大きさに取り直す**と落ちるようになった。
**当てなければ、2本とも「確かめたつもり」のまま出荷していた。**

#### 逆に、**1本が全部の壊し方で落ちたら、そのテスト自身が壊れている**
上を直した拍子に、期待値だけ古いままのテストを作ってしまい、**素の状態でも落ちる**
ようになった。気づけたのは、当てた9通り**すべて**でその1本が落ちたからである。

**「全部で落ちる1本」と「どれでも落ちない1本」は、どちらも中身を見る合図。** 前者は
テストが壊れており、後者は何も確かめていない。

### 待ち時間は「確かめたいことだけを確かめる経路」で消せる
タイムアウトを待つ処理を素直になぞると、テスト1本が数十秒になり `make ci` 全体が
引きずられる。**何を確かめたいのかまで戻る**と、待たない経路が見つかることがある。

実例：「切替が終われば次を受け付ける」を、実際にもう1回切り替えて（＋15秒）確かめて
いた。見たいのは権利が返っているかどうかだけなので、**わざと弾かれる値**を渡して
「排他で断られた」以外の理由で落ちることを見る形にしたら、待ち時間が消えた。

### 待ち合わせを検証するテストには、その待ち合わせ自体の上限を持たせる
「合図を待ってから動くこと」を確かめるテストは、壊れた実装（合図を待たない）を
相手にすると**落ちるのではなく固まる**ことがある——順序が崩れた瞬間に、テスト側の
待ち合わせも成立しなくなるため。固まるテストは何も教えてくれず、打ち切られるまでの
時間も奪う。

実例：Hello を待ってから送ることの壊し検証で、スタブの覗き見が壊れた実装の早すぎる
送信を食ってしまい、スタブの報告が永久に来なかった。**報告の受け取りに上限と
「来ないなら何が壊れているか」の言葉**を付けて、固まりを速い失敗に変えた。

### テストバイナリ間でヘルパを写すなら、削らずそのまま写す
統合テストのバイナリどうしは import できないので、小さなヘルパは写すしかない。
このとき**「最小限」へ削りたくなるのが罠**——削った部分が実は要件だったとき、
写した先だけが壊れ、原因は元との差分を見るまで分からない。

実例：保管庫へ偽の版を置くヘルパを写すとき、`transcript-parser` だけ IPC の hello で
版を名乗るという特別扱いを落とし、「版を聞けません」で落ちた。写すなら丸ごと写し、
**出所をコメントで名指しする**（元が変わったときに気づけるように）。

## テストが実環境へ書き込んでいないか確かめるとき
`Config::default()` をそのまま使うと、`resolved_state_dir()` は**利用者が普段使っている
場所**（`~/.local/state/agentdashboard`）を指す。テストがそこへ書くと、実運用と状態を
共有することになる。

差し替え口を設定に持たせ、テストは必ずそちらを指すこと。E2E は `state_dir` を、
モデルを扱うものは `claude_settings_path` を差し替えている。環境変数を書き換える方式に
すると、並行して走る他のテストを巻き込む。

**新しく「外の状態」を持ったら、同時に差し替え口も作る。** あとから足すと、それまでに
書き込んだぶんは残ったままになる（実際に実CLIテストが1件書き込んでいた）。

### 差し替え口を作るだけでは足りない。「未指定のとき」が本物へ落ちる
テストごとに差し替えても、**指定しなかったテストは既定の入口＝本物**へ落ちる。
書き込みは各テストで塞いだのに、読み込みがそこから漏れていた実例がある。

共通ヘルパの側で「明示が無ければ使い捨てへ」に倒すこと。個々のテストの心がけに
任せると、新しく書いたテストが必ずまた漏らす。

### 差し替え先が空だと、書き込みは防げても検査が空振りする
存在しないファイルを指した E2E は、読めないので何もせず、**注入も回復も一度も
動かないまま緑**だった。実装を丸ごと消しても通る状態になっていた。

差し替え先は**中身まで用意する**。しかも「動かなかったときの値」と違う値を置く。
同じ値だと、効いたのか何も起きなかったのかを結果から区別できない。

### 「本物ではないこと」は、避けたい相手を名指しして確かめる
`$HOME` の配下でないことで判定すると、`HOME` が `/` の環境（コンテナ）で
一時領域まで巻き込んで落ちる。避けたいのは1点（`discover()` が指す先）なので、
そこと直接比べる。**範囲で否定せず、対象を名指しする。**

### 実バイナリを起こす経路は1つに集めて、既定で塞ぐ
外の状態を読むのが**ライブラリとしての実行時**ではなく**起こした実行ファイルの中**の
場合、差し替え口を設定に持たせても効かない（子プロセスは自分で解決し直す）。
**起こし方そのものをヘルパへ集約し、危ない既定をそこで塞ぐ。**

塞ぐ相手は2種類ある。**読む側**（開発者の実環境を読んで別物を試してしまう。失敗の形が
「テストが落ちる」ではなく「別物を試していた」になるので追えない）と、**書く側**
（起こすたびに実行ファイルを控えるなど、重い副作用が走る）。

ホストで実行ファイルを起こす経路（Playwright・`e2e-*` スクリプト）は**箱の中と違って
実環境と地続き**なので、そちらにも同じ指定を置くこと。

## 開発環境でだけ通る差分に気をつける

### 「値が無いから起きない」は、値がある環境で起きる
テスト用の設定が**存在しないファイル**を指していると、そこから読む値は `None` になる。
`None` の経路しか通っていないコードは、値がある実環境で初めて別の道を通る。

実例：起動引数の `--model` と注入設定の `model` が重なる不具合。開発環境では注入する値が
無かったので出ず、**実機でだけ出た**。テストが緑でも安心できない類の差分である。

差し替え口を用意するときは、**値がある場合と無い場合の両方**を通しておくこと。

### 実機で落ちたら、まず「開発環境と何が違うか」を並べる
仮説から入ると外す。実際、上の件を疑って直したが原因ではなかった（直したこと自体は
正しかったが、症状は変わらなかった）。差分を並べてから絞るほうが速い。

## crate の境界を跨ぐとき（セルフホスト化フェーズ1 以降）
`session-host-core`（PC 側）と `server-core`（サーバ側）は、**互いを知らない**のが存在理由。
どちらかがもう一方を `Cargo.toml` に足した瞬間に、この分け方は意味を失う。

### 境界は「使ったら落ちる」では守れない。依存の宣言そのものを検査する
コンパイラが止めてくれるのは**使ったとき**で、依存に1行足しただけでは何も起きない。
`crates/core/tests/dependencies.rs` が禁じ手の一覧を持っているので、**新しい荷物を
入れたらここへ足す**（SeaORM・redis 等）。集めておかないと、配布物が重くなったことに
誰も気づけない。

検査は **`cargo metadata` の通常の依存だけ**を辿ること。`Cargo.lock` の依存一覧は
dev-dependencies と混ざっており、testkit が擬似 claude を PTY で起こすために
`portable-pty` を dev で持つので、混ぜて数えると誤検知する。

### テストのハーネスは `#[path]` で共有する。コピーしない
セッションを相手にするヘルパ（擬似 claude の起動・PTY の監視・状態待ち）は
`session-host-core/tests/common/mod.rs` にあり、ブラウザ配信まで通す側は `#[path]` で
それを読み込んで「待ち受けるサーバ」のぶんだけを足している。

**素直に写すと 150 行のコピーができ、片方だけが古くなる。** crate をまたぐが
テストのソースを直に読む形なので、製品の依存は増えない。

### 製品コードが使わなくなった依存は dev-dependencies へ落とす
crate を割ると「製品では要らないがテストは使う」依存が出る（core にとっての
`portable-pty` / `uuid`）。通常の依存に残すと上の検査をすり抜けるので、
**dev へ移す**。逆に、足し忘れるとマクロが展開されないまま「lifetime が合わない」と
いう遠いエラーになる（`async-trait` で踏んだ）。

### 設定を2つに割るとき、`#[serde(flatten)]` は使わない
**flatten を使うと `deny_unknown_fields` が効かなくなる。** 「知らないキーを書いたら
エラー」は打ち間違いを黙って無視しないための約束なので、静かに失うわけにいかない。
読み込みは1つの構造体のまま残し、そこから各側へ**射影**する
（`Config::agent()` / `Config::server()`）。

射影は写し忘れると**そのキーだけ黙って既定値に戻る**。利用者から見ると「設定したのに
効かない」で、原因が設定側か実装側かも分からない。**全キーに既定と違う値を入れて
両側へ運ばれることを見るテスト**を必ず持つこと。

## DB を相手にするとき（セルフホスト化フェーズ2 以降）
記録の真実は DB にある。ローカルは SQLite・セルフホストは PostgreSQL で、**スキーマも
コードも共有する**のが前提。

### 片方の DB だけで書いたコードは、もう片方で落ちる
型の厳密さ・JSON の扱い・主キーの制約は、**片方でしか出ない**。実際に踏んだもの：

- **主キーに NULL は置けない**（PostgreSQL）。ユニーク索引へ逃がしても NULL 同士は
  互いに別物と扱われ、同じキーが二重に入る。「未指定」を表したいなら**番兵の値**を使う
- **複合主キーでは自動採番が使えない**（SQLite の自動採番は単一の INTEGER 主キー限定）。
  書き込み側で振ること

`server-core/tests/common/mod.rs` が両方へ同じテストを通す足場で、`make test-compose` で
PostgreSQL 側も走る。**新しいテストは必ずこの足場に乗せる**（片方だけで書くと、
セルフホストで初めて壊れる）。飛ばしたときに黙らない作りにしてあるので、
「両方通した」と「片方しか走っていない」を見分けられる。

### 並びを決める番号は、上書きのときに振り直さない
同じIDのノードは上書きされる（upsert 契約）。そのたびに採番し直すと、**結果が届いた
だけの古いツールコールが列の末尾へ飛び、画面の並びが動く**。

### 耐久データは書いてから配る
順序を逆にすると、画面には出ているのに再読み込みで消える（嘘になる）。**書けなかった
ものは配らない**——代わりにエラーを配ってバナーに出す。

### 非同期の経路を1つ足したら、その間に届いたものの扱いを決める
「消す」と「消えたことを知る」の間には時間がある。カードを外したあとも、待ち行列には
まだそのカードの報告が残っている（切替の結果配信・見張りの1周・処理中のフック）。
素直に取り込むと**消したはずのものが戻ってくる**。

戻さないための門は、メモリ側と DB 側の**両方**に置くこと（片方だけだと再起動で戻る）。

### 実環境へ書き込ませない口が1つ増えた
テストと E2E は `database_url` を必ず使い捨ての場所へ向けること。既定は
`state_dir` の隣＝**利用者が普段使っている場所**なので、指定しないと実運用の記録を
読み書きする（`state_dir` や `claude_settings_path` と同じ性質の漏れ）。

## テストで「待つ先」を選ぶとき
経路が1段伸びると、**どこを見るかで結果が変わる**。セッションホスト（実体）の状態が
変わっても、記録（DB とサーバ側の写し）へ渡るのはそのあと。

### 確かめたいことが、どちら側の性質かで決める
| 確かめたいこと | 待つ先 |
|---|---|
| ブラウザから見える形（一覧に出るか・履歴が読めるか） | 記録層（`registry` の一覧・配信） |
| 実体の判断（差分で足りるか、全体を送り直すか） | セッションホストの配信（`manager.subscribe_events()`） |

実体の判断を記録層で見ると、DB を挟むぶんの遅れで**直前の別の報告が窓に入り込む**。
逆に、ブラウザの見え方を実体で見ると、まだ保存されていない状態を通してしまう。

### Playwright は webServer を globalSetup より先に起動する
`globalSetup` でサーバが掴んでいるファイルを消すと、SQLite が
「attempt to write a readonly database」（`SQLITE_READONLY_DBMOVED`）を返し続ける。
**消す側と開く側の順序は、同じコマンド行に並べて初めて保証できる**ので、
掃除は `webServer.command` の先頭に置く。

## ネットワークを跨ぐ経路を足すとき（セルフホスト化フェーズ3 以降）
同じプロセスの中で繋がっていたものを線で隔てると、**それまで「同じ物」だったから成立していた前提**が一斉に表に出る。

### 注入するコマンドは「その実行ファイル自身」を指す
セッションへ焼き込むフックのコマンドは `current_exe()` から作られる。実行ファイルを分けたら、**分けた先にも同じ転送の口が要る**。持っていないと「注入したコマンドが存在しない」となり、フックが1つも届かないのに起動も操作も普通に動く、という切り分けの難しい形で出る。

### 「流れていないこと」を確かめる検査は、空振りしていないかまで見る
WebSocket の**クライアント→サーバ方向は payload がマスクされる**（XOR）。線の上のバイト列を素朴に文字列検索すると、平文はそもそも現れないので、**何も流れていなくても通る検査**になる。

否定を確かめるテストには、必ず**肯定側の裏取り**を添える（「生の行は無い」だけでなく「構造化されたものは確かに観測できている」まで見る）。

### 境界の検査には2種類ある
- **到達可能性**：その crate から辿り着けてはいけない（例：サーバ側が PTY を持たない）
- **宣言そのもの**：辿り着けるのは避けられないが、**自分で使ってはいけない**（例：サーバ側が WebSocket クライアントを持たない。axum の ws 機能が実装を引き込むので、到達可能性では必ず落ちる）

禁じたいのが「同じ木に居ること」なのか「使うこと」なのかで、書く検査が変わる。

### 口を作る順序は、循環したら2段に割る
「A が B を受け取って作られる」のに「B は A を知っている必要がある」という組み合わせは分離で必ず出る。**口だけ先に作り、後から相手を差し込む**形にする（`attach` を分ける）。パーサの世話役が元からその形なので、迷ったら同じにする。

### 保証をモードで食い違わせない
片側だけを強くすると、**弱い側でしか出ない壊れ方**が残る。「ローカルでは緑なのにセルフホストで欠ける」は、原因が実装ではなく**経路の違い**にあるので、テストを増やしても見つからない。

新しい保証（ack で位置を進める等）を入れるときは、**両方の経路へ同時に通す**。

### 分離してから初めて言えることは、目で見ないと分からない
「一覧に出ているカードを開いた瞬間に『見つかりません』と言われる」——動作は正しく、言い方だけが嘘をついていた。**動くかどうかのテストでは絶対に捕まらない**ので、2プロセスを起こしてブラウザから触ること。

## 画面を運ぶとき（セルフホスト化フェーズ4 以降）
バイト列そのものではなく「いまの画面」を運ぶと、**受け取る側の意味論**が効いてくる。並びどおりに繋げば動く、と思える箇所ほど静かに欠ける。

### 落ちうる経路から拾わない
エミュレータへ食わせるバイトは、**落とさない側**から取る。溢れたら捨てる作り（リングバッファ・配信の待ち行列）の後ろから拾うと、落ちたぶんだけ状態機械が壊れ、**画面が徐々にずれていく**——どこで壊れたのか後から辿れない形になる。

### 見た目だけを運ぶと、入力の作法が落ちる
端末の状態には、画面に見えるもの（文字・色・カーソル）と**見えないもの**（カーソルキーの送り方・括弧付き貼り付け）がある。生バイトを受け取っている側は後者を自分で学べるが、画面だけを受け取る側は学べない。

**運ぶのは「見えるもの」だけで足りるか**を、入力の側から確かめること。矢印キーが効かないメニューは、画面が正しく出ているぶんだけ原因が見えにくい。

### 差分だけを送っている間、受け手には履歴が積まれない
差分は**可視領域を描き直す**形なので、押し出された行はどこにも残らない。受け手（xterm）の
スクロールバックは**1行も増えない**——実測では、約650行を2回出しても `buffer.active.length`
は画面の行数のままだった。

**増えるのは全画面フレームが届いた瞬間だけ**で、そのとき一度にスクロールバックぶんが入る
（実測 1023 行）。つまり全画面フレームは「遡り位置を壊すもの」であると同時に、
**受け手が遡れるようになる唯一の機会**でもある。

したがって「リモートでも N 行まで遡れる」と書くときは、**送っている量**と
**受け手に積まれている量**を分けて考える。前者だけを見ると、実際には遡れないものを
「遡れる」と書くことになる。

### 作り直しの指示は、その場の全体とセットでしか意味を持たない
取りこぼした相手に**古い全体**を渡すと、その上に新しい差分が乗って「途中まで古い・途中から新しい」という壊れ方をする。手元に新しい全体が無いなら、**一度消して、作り直しを頼む**のが唯一正しい。

### 「消してから描く」相手に、前置きは残らない
画面を作り直す出力は、たいてい**消してから描く**。その前に書いたものは、画面に残っているぶんだけ消える。前置きを残したいなら、**先に画面の外へ押し出しておく**（スクロールバックへ送るなど）。

### 視聴者は人数ではなく識別子の集合で数える
「開いた／閉じた」を数で数えると、**開き直し**（同じ相手が2回開く）で1つ多くなり、閉じても誰かが見ていることになる。誰も見ていないのに配信が続く形は、止まっていることに気づけない。

## 入口に鍵をかけるとき（セルフホスト化フェーズ5 以降）
それまで素通しだった口を塞ぐと、**「通れないこと」が新しい失敗の形として増える**。動くかどうかのテストは、断られたことと壊れていることを区別しない。

### 鍵をかけるのは中身のある口だけ
画面（web アセット）と「認証が要るかどうかを答える口」は素通しにする。画面ごと 401 にするとログイン画面を出す手段が無くなるし、**認証の要否を知るのに認証が要る**という循環もできる。扉は開けて、中身を返さない。

### 起動待ちに鍵の向こうの口を使わない
「まだ起きていない」と「まだ通っていない」が同じ 401 になり、**永久に待つ**。待ち合わせには鍵の外側の口を使う。

### 判定を通らずに答えを出す道を作らない
経路ごとに条件を書くと、REST・WS・画面の3箇所で必ず食い違う。判定は1箇所へ集め、**「どの対象への操作か」は網羅の match で数え上げてから**通す。分岐ごとに書くと、口を1つ足したときに付け忘れる——付け忘れは、他人のものを操作できるという形でしか表に出ない。

### 断り方で存在を教えない
「他人のもの」と「知らないもの」に同じ言葉を返す。言い分けると、IDを総当たりして存在だけを調べられる。**認証の失敗も理由を分けない**（「その名前は無い」と「パスワードが違う」を呼び分けると、実在する名前を総当たりできる）。

### 免除は接続そのもので決める
`X-Forwarded-For` のようなヘッダで代用すると、**偽装ヘッダ1行で鍵が無効になる**。接続元を渡す形（`into_make_service_with_connect_info`）で待ち受け、テストのハーネスにも同じ形を入れること——テストの接続元は必ず 127.0.0.1 になるので、そのままでは**免除される側しか踏めない**。

### 変えられないものを画面に並べない
「読めるが触れない」設定は、触れないことを画面にも書く。並べただけだと「設定したのに効かない」になる。意味を持たない項目（別の構成のためのもの）はそもそも出さない。

### 帰属が変わると、テストの前提も変わる
アカウントで区切ると、**違うアカウントで繋いだものは正しく見えなくなる**。テストからは「動かない」としか見えないので、既存のテストが使っているアカウントを揃えること。

### 遅いハッシュは専用のスレッドへ逃がす
argon2 は意図的に遅い（100ms 前後）。async の上で直接回すと、その間そのワーカーの上にある全部が止まる。

### 通ったら入館証のIDを振り直す
入る前に持たされた Cookie をそのまま使い続けると、先にIDを仕込んでおいた相手がログイン後の入館証を手に入れられる。

## 画面が「サーバに聞いてから描く」ようになったとき
出す画面をサーバの応答で決めるようにすると、**最初の1描画では何も決まっていない**。ここを踏まえないテストは、実行環境の速さ次第で通ったり落ちたりする。

### 数える前に「どちらかが出る」まで待つ
`count()` は待たない。聞いている間は 0 が返るので、**分岐を飛ばして先へ進む**。単体では通るのに通しで落ちる、という一番たちの悪い形になる。

### 同期の取得は、聞き終わるまで成立しない
`getBy*` は待たない。`findBy*` へ変えるか、待ち合わせを1つ挟む。**その1描画が遅れることは仕様**なので、テストの側を合わせる。

### モジュールに1つのストアは、テストごとに戻す
前のテストで通った状態が残ると、「聞く前から入れている」テストができてしまう。

## テストが「たまたま通っている」ことに気づく
全部まとめて走らせると通るのに、**単体で走らせると必ず落ちる**テストがあった。逆もある。どちらも「合否が実行環境の速さで決まっている」状態で、そのテストは**壊れたことを教えてくれない**。

### `expect.poll` を「変化を待つ」つもりで使わない。**1回目で通ったらそこで終わる**
`expect.poll(…).toBeGreaterThan(0)` は、**最初の評価で条件を満たせばその場で通る**。したがって
「何かを起こしてから、その結果を `poll` で見る」と書くと、**起きる前の値を見て通ってしまう**。
待っているつもりで、何も待っていない。

実際に踏んだ。リモートの画面を作り直させてから「遡り位置が保たれること」を `poll` で見たが、
**作り直しの仕掛けを丸ごと外しても落ちなかった**——全画面フレームが届く前の値で通っていた。

**「起きたこと」を先に待ち、そのあとで測る。** 順序を2段に割る。

```ts
await expect.poll(() => 起きた回数()).toBeGreaterThan(前)   // ← 起きるのを待つ
expect(測りたい値()).toBeGreaterThan(0)                     // ← そのあとで測る
```

**待てる合図が無いなら、作る。** 上の件では観測する手段が無かったので、`terminal-status`
（元から E2E が読むためだけに在る `sr-only` の要素）へ数を1つ足した。**数えるのは効果が
出たあと**にすること——起きた瞬間に数えると、また同じ隙間ができる。

### テストの土台で、プロセス共通の環境変数を立てない
`std::env::set_var` は**プロセス全体**に効く。同じテストバイナリの中で**あとから走るテストにも残る**ので、そのテストが別の経路（設定ファイル・ポインタ・引数）を確かめようとしても、**環境変数が探索順の先頭に居座って踏めなくなる**。

しかも**壊れ方が「テストを1本足したら、無関係なテストが落ちた」**という形で出る。順序が変わって初めて表に出るので、増やした側の変更を疑って時間を溶かす（2026-08-19 に踏んだ。単独では通り、通しでだけ決定的に落ちた）。

土台が場所を名指しする必要があるなら、**そのテスト専用の置き場所**（設定・ポインタ・引数）で渡すこと。`cargo test` はスレッドで並べるので、**nextest がプロセスを分けてくれることを当てにしない**。

### 再接続を試すなら、繋ぎ直せない状態を作る
指数バックオフは**失敗してから**効く。線を切っただけでは1度目の繋ぎ直しが即座に成功するので、「切れている状態」を観測できるかどうかが実行環境の速さ次第になる。**繋ぎ直しごと塞いで**から観測し、観測できたら開ける。

### ブラウザの役をするテストは、本物の画面と同じ当て方をする
一覧の情報は1つのメッセージでは来ない（全体の upsert と、状態の差分）。片方だけを見ていると、**製品は正しいのにテストだけが落ちる**。当てる側のコード（`stores/` のリデューサ）と同じ扱いを書くこと。

### 数えて取り出す実装は、作った文字列だけで固めない
「N 番目の項目を取る」形の実装（`/proc/<pid>/stat` の22番目、区切りの N 個先、など）を、**自分で組み立てた入力だけ**でテストすると、実装とテストが**同じ数え間違いを共有する**。両方ずれていても緑になる。

作った入力は「数え方が正しいこと」を示すために使い（値＝項目番号にしておくと、ずれが読める形で出る）、**そのうえで実物からも1回読む**。実物は値が分からないので単体では判定に使えないが、**作った入力とは違うずれ方をする**ので、組にすると思い込みごと固まるのを防げる。

### 環境の設定に委ねると、確かめたい経路を踏まないことがある
権限確認は、利用者のグローバル設定が `defaultMode: auto` だと**読み取り専用に見える操作では出ない**。「出るはずのものが出ない」ときは、まず**設定を読み込ませない形**（`--setting-sources project,local`）にして、確かめたい経路を確実に踏ませる。

### cargo の出力は色付きなので `grep '^error'` で絞れない
`scripts/cargo` は `CARGO_TERM_COLOR=always` を渡す。行頭に見えるものの前にはエスケープが入っているので、**行頭を固定した検索は必ず空振りする**。絞るなら固定しないか、`tail` で末尾を見る。

## サーバを2台以上並べるとき（セルフホスト化フェーズ6 以降）
1台のうちは「同じプロセスに居るから届く」で済んでいたものが、全部**頼まないと届かない**に変わる。壊れ方は「動かない」ではなく「片方だけ古い」なので、症状から原因へ辿れない。

### 自分が出したものは自分にも返ってくる
pub/sub は購読していれば自分の publish も受け取る。発信元の印を入れておかないと、受けた側がもう一度配り直し、それがまた返ってきて**止まらなくなる**。

### 持ち主は名前で決める。中身を信じない
チャネル名にアカウントを入れたなら、**受け取る側は名前の方を正とする**。封筒の中身を信じると、届いた先で「実は別のアカウント宛て」と言えてしまい、名前で分けた意味が無くなる。

### 新しい経路を足したら、既存の門も同じ数だけ要る
「外したカードを後から届いた報告で戻さない」ような門は、経路ごとに要る。片方にしか無いと、**もう片方から同じ事故が起きる**。しかも一覧をメモリで持っていると、DB では外れているのに画面には出続けるという食い違いになり、原因が2箇所に分かれる。

### 「相手が居る」と「それが生きている」は別
接続の在席と、その接続が抱えている個々の対象の生死は違う。前者で後者を代用すると、**死んだものを生きていることにして、後始末を頼む相手が居なくなる**。生死を知っているのは持ち主だけなので、聞きにいく手段を用意する。

### 立ち上げ直した側は、待っていても何も知らない
永続化してあるのは「存在する」ことだけで、「いま動いている」は持ち主のメモリにしかない。動きの無い対象は自分から名乗らないので、**こちらから名乗り直しを頼む**経路が要る。

### 種別の名前がぶつかると、書けるのに読めない
外側の封筒と中身の型が同じ名前で種別を持っていると、内側が外側を上書きする。**エラーは出ず、届かないだけ**という形で出る。入れ子にするなら種別を「隣」に置くか、名前を変える。往復のテストを1本置けば即座に分かる。

### 待たせる相手が増えたら、列を分ける
稀で重いもの（DB を引く）と、頻繁で軽いもの（画面）を同じ列で捌くと、前者1件の処理で後者が止まる。**性質が逆のものを同じ順番待ちに並べない。**

## docker compose で複数台を立てるとき
1台構成では踏まないものが、2台目を足した瞬間に出る。どれも**本物を相手にするまで一度も表に出なかった**。

### 起動時のマイグレーションは同時に走ると衝突する
「まだ当たっていないものを当てる」形なので、同時に読むと両方が当てにいき、後から着いたほうが**起動ごと失敗する**。助言ロックで1台ずつに直列化する。取るのは**トランザクションに紐づく側**——明示的に解く形にすると、落ちた瞬間にロックが残って他の全台が起動できなくなる。

### 検証用の DB を tmpfs にすると、止めた瞬間に消える
「DB が落ちて戻った」を試したつもりが「まっさらになった」を試すことになる。スキーマは起動時にしか当たらないので、**表が無いまま誰も直せない状態**で固まる。止めて起こす検証をするなら、名前付きの置き場所にして片付けは `down --volumes` に任せる。

### healthcheck は外から叩ける口で見る
プロセスが居ることと、外から届くことは別。**鍵の外側にある口**を選ぶこと——鍵の向こうを叩くと「まだ起きていない」と「通っていない」が同じ応答になり、永久に待つ。

### Playwright は走る前に出力先を消す
立ち上げ側が置いた控えは、`test-results/` の下にあると**実行の直前に消える**。テストが起こすもの（`webServer`）は消えたあとに置くので踏まないが、先に立ち上げる構成では踏む。

**落ちたテストを流し直す前に、証拠を退避する。** 失敗すると Playwright は `error-context.md` やスクリーンショットを `test-results/` へ残すが、**次の実行の冒頭で消える**。「たぶん揺れだろう」と確かめに流し直した時点で、**揺れかどうかを判断する材料ごと消える**。実際にそうして1回ぶん失った。順番は「退避 → 流し直す」。

### `webServer` は project を選んでも全部起こされる
docker で立てた相手に繋ぐ project を足すときは、**印を付けて空にする**。要らないだけでなく、同じ道具とポートを取り合って落ちる。

## 配布物を作るとき
「動くものを作る」と「配れるものを作る」は別の仕事で、後者は**配ってからしか気づけない失敗**を持っている。

### 道具の制約が設計を決めることがある
cargo-dist は**パッケージの境界を跨いでバイナリを1つのアーカイブへ入れられない**。同じ名前の bin を2つのパッケージへ置くと cargo が衝突するので、「2つの実行ファイルの隣に同じ相棒を置く」は crate を分けたままでは成立しない。

設計どおりに作れないと分かったら、**手を動かす前に利用者へ選択肢を出す**。ここでは3案（1本にまとめる／片方だけ配る／別々に配って置き場所を揃える）を出して決めてもらった。

### 境界の証明が効かなくなったら、範囲を狭める
配布用のパッケージは両側へ依存するので、依存グラフによる「引き込んでいない」の証明が効かない。**入口を呼び出しの1行だけに限り、そこへロジックを書けないことを機械で見る**形に置き換えた。境界の外に立っているのが1行なら、そこに書ける間違いも1行ぶんしかない。

### コンパイル時に埋め込むものは、CI でも先に作る
画面を実行ファイルへ焼き込む構成では、**ビルドの前に画面を作る手順が要る**。無いと「起動はするが真っ白」なバイナリができあがり、ビルドもテストも通る。配ってから気づく。

### 差し込む手順は、読み直されて埋め込まれる
道具が生成する CI へ手順を差し込むとき、**知らないキーは黙って落ちる**（`working-directory:` が消えた）。差し込んだら**生成物のほうを読んで確かめる**こと。

### 手順書は、動いているファイルを載せる
設定例を貼り付けると必ず腐る。**実体をリポジトリへ置き、検証がその同じファイルを読む**形にすれば、動かない設定例は原理的に書けない。名指ししているものの実在も機械で見る——切れたリンクは書いた本人には見えない。

### 案内の文が名指しするコマンドも、実在を機械で見る
同じことが**実行時のメッセージ**にも要る。「見つかりません。`X` で調べてください」と書いた
とき、`X` が存在しなくても**製品は何も落ちない**。困るのは、その案内どおりに打った人だけ。

実際に踏んだ。置き場所が見つからないときの案内を、実行ファイルの名前から
`<名前> state-dir` と組み立てた。**`agentdashboard-agent` に `state-dir` の口は無い。**
しかも名前を借りて `agentdashboard state-dir` と言うのも誤りで、あちらは別の設定ファイルを
読むので、答えが違う。

**実行ファイルごとに案内が違うなら、実行ファイルごとに確かめる。** そして「案内した
コマンドが実在すること」も1本置く。これを入れる前に書いたテストは、**文字列が出ている
ことだけを見ていたので、製品が嘘をついたまま緑だった**。

### 手順書を書くと、実装の理解違いが表に出る
「合言葉は設定ファイルに書く」と思って書きかけて、実際は画面から登録して DB へ置くものだと分かった。**手順を最後まで書くこと自体が検査になる。**

### 道具の版は、揃える場所を数えておく
隔離イメージ・生成物の設定・ツールチェーンの指定と、同じ版を書く場所が増える。**イメージのタグも一緒に上げる**と、古いイメージで動かしたときに落ちて気づける。黙って古い道具で動くほうが分かりにくい。

## 検収条件・手順書を消し込むとき（セルフホスト化フェーズ8 以降）

### 「誰の手元で通るか」を先に決めて読む
検収条件は、**開発者の手元にあるものを前提に読むと通ってしまう**。フェーズ8 で2件出た穴はどちらもこれだった。

| 条件の文面 | 開発者の立場 | 利用者の立場 |
|---|---|---|
| `docker compose up -d` で起動する | リポジトリもビルド済みの実行ファイルもある → 立つ | 献立表1枚しかない → **立たない** |

自動テストは基本的に開発者の立場で立てているので、**この差はテストを増やしても見つからない**。条件を読むときに「利用者の手元にあるものは何か」を先に書き出す。

### 配るものに「作る」を残さない
献立表（compose）に `build:` が残っていると、Docker は箱が無いとき自分で作ろうとする。材料を持っているのは開発者だけなので、利用者はそこで詰まる。**配る側の設定に、手元の資産を前提にした指定を残さない。**

### 配布物は、作ったあとに必ず一度起こす
ビルドが通ることと、起動することは別。土台と実行ファイルで OS の共通部品の版がずれると、**ビルドもテストも通り、起動した瞬間だけ動かない**。`--version` を叩くだけでも、配ってから気づく事故はほぼ消える。

### 手元で動かせない設定ファイルは、せめて食い違いを見る
常駐の設定（systemd 等）は CI で動かせない。それでも「手順書が案内している起こし方と食い違っていないか」なら機械で見られる。**動かせないことと、何も守れないことは違う。**

### 棚に置いたものは、他人として取れるか確かめる
コンテナレジストリは初回が非公開になることがある。**置いた本人のブラウザからは普通に見える**ので、こちらのテストは全部通り、困るのは他人だけになる。公開の切り替えは手順として残す。

## E2E の土台を増やすとき

### 増やすと、既存の潜在的な競合が表に出る
ハーネスを1つ足したら、無関係に見えるテストが1本落ちた。個別に流すと通る。原因は**元からあった競合**で、実行環境が少し遅くなるだけで出る類のものだった。

「たまに落ちる」で片付けず、**土台を増やした直後に落ちたものは、増やしたせいではなく元から壊れていた**と考えて原因まで辿る。

### 数えるものは、画面ではなく真実に聞く
一覧へ移った直後は小窓がまだ描かれておらず、そこで数えると 0 が返る。**「まだ描かれていない」と「もう無い」を読み違える**と、`.nth(0)` が別のカードを掴み、症状は「起こしたばかりなのに前の値を持っている」になる。原因まで辿るのが難しい部類。

### 聞く相手は「いま見ている画面が話している相手」
真実に聞く形にしても、**聞く先を baseURL に固定すると跨いだときに壊れる**。前段（リバースプロキシ）越しに別のインスタンスを見ていると、画面と違うサーバへ聞くことになる。2台は記録を共有していても**届く順までは揃わない**。

### 画面の前提が変わる構成は、土台を分ける
繋がっている PC が2台以上になると、起動フォームに「起動する PC」の選択が現れる。**同じ土台へ足すと、選ばずに押している既存のテストが軒並み落ちる。** 画面の前提が変わるなら、テストを直すのではなく土台を分ける。

### 壊す系のテストは、落ちても環境を戻す形で書く
サービスを止めるテストは、**止めてから戻すまでの間に断言を置くと、落ちたときに戻し損ねる**。共有の土台では後続の全テストが巻き添えになり、1本の赤が5本の赤に化けて「どのテストの問題か」が読めなくなる（実際に踏んだ）。止める→確かめる→戻す、の「確かめる」を try/finally で包み、戻すことを失敗と無関係にする。

あわせて、**健康な環境を前提にする読み書きのテストは、壊す系より前に置く**。後ろに置くと、壊す系の戻し損ねを全部かぶる位置になる。

## よそが書いたスクリプトを子プロセスとして呼ぶとき

### 親の環境をそのまま継承させない
`env_clear()` してから、要るものだけを積み直す。**「使わないと決めた設定は、渡さなければ
効かない」は成り立たない**——相手が読むのは自分の判断であって、こちらの意図ではない。

実例：配布インストーラは入れる場所を決める環境変数を2つ見ており、**こちらが避けたい
ほうを先に見る**。使わないと決めていても、**親の環境に1つ残っていればそちらが勝つ**。
残っていた場合の結果は「利用者の共有設定ファイル6本と控えが書き換わる」で、しかも
成功して終わるので気づけない。

`scripts/cargo` が `AGENTDASHBOARD_*` を箱へ転送する（除外は一部だけ）ことも効く。
**開発者が手元で export した値が、テストにも製品の経路にも混ざる。**

### 渡す環境と引数は純粋関数で組み立て、門を置く
組み立てを関数に切り出して、**混ぜてはいけないものが入っていないこと**を単体テストで
固定する。「危ないものを渡していない」は目視では守れない——渡す側のコードは
条件分岐で育つので、いつの間にか1本増える。

同じ理由で、外部へ取りに行く引数には**検証を切る指定（`--insecure` の類）が
含まれていないこと**も門にする。

### 実物の出力の形を、推測で設計に書かない
外部ツールが吐く JSON やスクリプトの挙動は、**1回取ってきて読む**。読まずに書くと、
実装のときに前提が変わって設計を書き直すことになる。

あわせて**同じものを既に読んでいるコードが無いか先に探す**こと。実例：配布物の
献立表の読み方は `crates/dist/tests/artifacts.rs` が既に正しく持っていたのに、
推測で書いてから直した。

### docker が要らない土台は、既定の E2E に含める
走らないテストは腐る。docker が要るもの（compose 系）だけを別ターゲットにし、それ以外はふだんの E2E と一緒に流す。

## リリースを実際に出すとき

### 打つのは**タグだけ**。リリースは `dist` が作る
`gh release create` を使ってはいけない。**リリースを作るのは `host` ジョブの仕事**で、先に作っておくと

```
a release with the same tag name already exists: v0.1.6
```

で落ちる。**3 OS 分のビルドが全部成功したあとの最後の1歩で落ちる**ので、気づくまでに10分以上かかり、しかも失敗の見た目は権限の問題と区別が付かない。

正しい打ち方は `git tag v<版>` → `git push origin v<版>`。**過去のリリースの作者を見れば確かめられる**——`gh release view <版> --json author` が `github-actions[bot]` を返すなら、そちらが作る仕組みになっている。

踏んでしまったら、**リリースだけ消してタグは残し**（`gh release delete <版> --yes`。`--cleanup-tag` を付けない）、`gh run rerun <ID> --failed` で落ちたジョブだけ回し直す。ビルド成果物は残っているので、**3 OS 分を作り直さずに済む**。

### 差し込む断片を `.github/workflows/` に置かない
そこは **GitHub がワークフローとして登録する場所**。`on:` を持たない断片を置くと、**プッシュのたびに失敗が1件積み上がる**。リリースそのものは動くので気づきにくいが、失敗の一覧が常に赤いと**本当に見るべき失敗が埋もれる**。1つ上へ置いて相対パスで参照すればよい。

### リポジトリの既定権限は、ワークフローの指定より強い
ワークフローに `permissions: contents: write` と書いても、**リポジトリの Actions 既定権限が read-only なら上限に抑えられる**。症状は `HTTP 403: Resource not accessible by integration` で、権限を書いたはずの側だけを見ていると原因に辿り着けない。

```
gh api repos/<owner>/<repo>/actions/permissions/workflow
```

### タグは、そのブランチの**先端**に打つ
権限を直しても 403 が消えないときは、**タグの位置**を疑う。`gh release create --target <コミット>` は、指すコミットがブランチの先端でないと Actions のトークンでは通らない（[cli/cli#9514](https://github.com/cli/cli/issues/9514)）。**症状は権限エラーと見分けが付かない**ので、権限だけを見ていると延々と直らない。

タグを打ったあとに main へ commit を足すと、この状態になる。**タグを打つ直前に「これが最後の commit か」を確かめる**か、足したなら打ち直す。

### 同じ版でタグを打ち直してよい
リリースがまだ作られていないなら、タグを消して同じ版で打ち直せる。**先に「何が作られてしまったか」を確かめてから**消すこと。

### 403 が出たら、切り分けは2段階
1. **ジョブの冒頭ログ**（`GITHUB_TOKEN Permissions`）を見る。ここが `Contents: read` ならリポジトリの既定権限の問題
2. `write` なのに 403 なら、**自分のトークンで同じ API を叩いてみる**。通るならリポジトリ側は無実で、Actions のトークン固有の制約（`--target` 等）を疑う

### 「タグを打つまで分からない」は本当に分からない
3 OS 分のビルドも、CI 上で画面が焼き込まれるかも、箱が棚へ置けるかも、**手元の検査では一度も通らない**。予定の一覧（`dist plan`）が正しくても、実物の並びが違うことがある（配布アーカイブには先頭にディレクトリが付く。一覧はそう読めない書き方をしている）。

**決め打ちで書かず、実物から探す形にしておく**と、この差で落ちない。

### リリースが走っている間は、そのブランチを進めない
タグより先へ commit を積むと、走行中のリリースの `--target` が先端でなくなり、**完走目前で 403 になる**。落ちた理由がタグ側にあるとは思いにくいので、原因を探す時間が丸ごと無駄になる。

## 入れる側を触るとき（消す側も一緒に直す）

### 置き場所は、消す側に組み立てさせない
入れる側と消す側が**別々に同じ場所を組み立てる**と、片方を直したときに黙って食い違う。症状は「消えない」ではなく「**消したつもりで残っている**」なので、誰も気づかない。

**実行ファイルに聞く形にする。** 解決後の場所を印字する口を1つ用意し、消す側は消す前にそこへ聞く。設定や環境変数で変えた場所も、これなら勝手に拾える。聞けないときの控えは持つが、**落ちたことは必ず言う**——黙って既定を消しに行くと、変えていた人が「消えたはず」と信じてしまう。

### OS で分けると、その OS の CI が無い側は永久に確かめられない
`cfg(windows)` で書くと、Linux の CI では**その道ごと消える**。実装からその道を削っても検知できない。

**環境変数の有無だけで決める形**にすれば、どの OS の上でも全部の道を通せる。分岐が必要に見えても、たいていは「何が設定されているか」で書き直せる。

### 一時領域を既定にしてよいのは、消えても困らないものだけ
記録の DB のように**消えると戻せないもの**を、OS が掃除する場所へ置いてはいけない。`HOME` が無い環境（Windows）へ落ちる道が一時領域に繋がっていないか、既定を決めるときに確かめる。

### 消す側が触ってよいのは、入れる側が作ったものだけ
`~/.local/bin` は、同じ仕組みで配られたツールが**みんなで使う場所**。そこに置かれた `env` や、シェルの設定に足された1行も同じ。**自分のものだけを消す**——巻き添えにすると、消した人が「なぜか別のツールが動かない」ことになり、原因まで辿れない。

ただし**アプリ名そのもののファイル**は共有ではない。入れる側が作ったなら消す側も消す。「共有だから触らない」を機械的に適用すると、**自分の置き土産まで残す**ことになる（fish の `conf.d/<アプリ名>.env.fish` で実際にそうなった）。

触らなかったものは**印字して伝える**。消したい人が自分で判断できる形にしておけば、親切と安全を両立できる。

### 消す道は、誰も通らないまま腐る
入れる道は使うたびに通るので、壊れれば気づく。**消す道はそうならない。** 壊れていても、消そうとした人以外には何も起きない。そして腐り方は「消えない」だけでなく「**消してはいけないものを消す**」もありうる。

だから、次のどれかを触ったら**同じコミットで消す側も直す**。

| 触ったもの | 消す側で直すところ |
|---|---|
| 配る実行ファイルの顔ぶれ | 消す対象の一覧 |
| 入れる場所（`install-path`） | 既定の置き場所 |
| 記録の置き場所の既定 | 消す対象の場所 |
| 控え（receipt）の名前や場所 | 読む先と消す先 |

**気づく仕掛けは機械にしか置けない。** 置き場所は実装と配布設定から引いて突き合わせ、**片方を直したらもう片方が落ちる**形にしておく。

### 消す検査は、実際に走らせて数える
読むだけの検査では「消える」ことも「消えない」ことも確かめられない。**偽のインストール一式を作って走らせ、残ったものを数える。**

### 戻せない操作は、明示の指定でだけ起こす
`curl … | sh` で走る道具は、標準入力が端末ではないので**確認を聞けない**。安全側を既定にして、戻せない操作（記録を消す等）は引数で明示させる。

## 本物の claude を使うテストに、利用者のグローバル設定を持ち込まない

### 原則
本物の claude を起こすテストは **`--setting-sources project,local` を渡す**。利用者の `~/.claude/` には自動化（セッション開始で発火するフック・スキル・CLAUDE.md の指示）が積み上がっていき、それが**テストの知らない割り込み**を作る。

### 実際に踏んだ形（2026-08-11・v2.1.227）
サブエージェント検知のテストが「指示は記録されるのに assistant の応答が1件も無い」顔で落ちた。実機で同条件を CLI から再現して画面を取ると、**利用者設定が持ち込んだセッション開始の自動スキルの許可ダイアログ**がターンを塞いでいた——**acceptEdits はスキル使用を自動許可しない**ので、権限モードを緩めたつもりでも止まる。

### なぜ「注意」ではなく「原則」か
利用者側の自動化は今後も増える。持ち込む形のテストは、**テストが変わっていないのに利用者の設定変更で落ちる**——落ちた瞬間には何が変わったのか分からず、追跡に本物の claude の再現（クォータ）が要る。遮断しておけばこの族は丸ごと出ない。

### 見分け方
落ちた回のトランスクリプトに user 行だけがあって assistant が無いなら、まずこの族を疑う。**画面を取れば一発で分かる**（許可ダイアログが写る）。

## 環境変数を読む関数を、テストから呼ぶとき
設定の読み込み（`from_toml_str`）は**環境変数を当ててから**組み立てる。したがって、
ただ読むだけのテストも**環境変数の影響を受ける**。

`make test-rust` は nextest で**テストごとにプロセスを分ける**ので、この競合は表に出ない。
一方、素の `cargo test` は1プロセスにテストを同居させるため、上書きを試すテストが立てた
環境変数を、無関係なテストが掴んだまま読む。**「単体で走らせると通るのに、まとめて走らせると
たまに落ちる」**という形でしか現れない。

- 環境変数を**書く側だけ**をロックで守っても足りない。**読む側も同じロックを取る**
- テストを絞って確かめるときも `make test-rust` 相当（nextest）を通す。素の `cargo test`
  で出た1本の失敗を、製品の不具合と読み違えない

## リポジトリ全体を機械で書き換えるとき
一括置換やスクリプトでファイルを走査するときは、**除外する場所を先に決める**。

### `.selfheal/worktrees/` を巻き込まない
自己修復の作業場所は**別の git worktree** である。`.gitignore` に入っているので
**main 側の `git status` には出ない**——巻き込んで書き換えても気づかないまま進む。
実際に走査へ入り込み、修復中のブランチ2本を丸ごと書き換えていた（気づいたのは
スクリプトが出したファイル一覧を読んだから）。

戻すときは、そのワークツリーへ入って `git checkout -- .` する。main から戻せない。

**書き換えだけでなく、走らせるものも巻き込む。** `npx vitest` を**リポジトリのルートから**
打つと、`.selfheal/worktrees/*/web/src/**` にある**同名のテストまで拾って落ちる**
（あちらには `node_modules` が無いので import で落ちる）。症状は「直したはずのテストが
知らない場所で落ちる」なので、パスを読むまで何が起きたか分からない。

`cd` はセッションに残る（別節）ので、**バックグラウンド実行のあとに作業ディレクトリが
戻っていることに気づかず**踏みやすい。`(cd web && npx vitest …)` と括る。

### 自分自身を書き換えない
**言い換えの表を持つファイル（`.claude/CLAUDE.md`）を置換の対象に入れない。**
「旧名 → 新名」の表が置換されると、旧名の欄まで新名になって表の意味が消える。
実際に「コーディングエージェント」が「コーディングセッションホスト」になり、
表が「セッションホスト → セッションホスト」になった。

### 守る語は、置換の前に伏せ字へ退避する
同じ綴りで**別の意味**を持つ語がある。除外ではなく退避で守ると、1文の中に
両方が出てきても取り違えない。

```
守る語を \x00N\x00 へ置き換える → 目的の置換をする → \x00N\x00 を戻す
```

「自分自身を書き換えない」には**これから作る置換先の定義**も含まれる。呼び出し側を
`helper(…)` へ一括置換すると、`helper` の定義の中にある同じ形の行まで置き換わって
**再帰**になる（実際になった）。置換対象に定義側が含まれるファイルでは、1件ずつ見る。

### 走らせたあと、機械で確かめる
- **触ってはいけない識別子の出現数を、作業前に控えておく。** 減っていたら壊している
- 走査したファイル一覧を出力させ、**予定していない場所が混じっていないか**を読む

## コードレビューの指摘に着手するとき

### 直す前に、全件が**いまも成立するか**を確かめる
レビューは書かれた時点のコードを見ている。着手するころには、別の作業で消えている指摘・行番号がずれている指摘が混じる。

- **確かめてから着手すると、消えている指摘を追いかける空振りが起きない**
- 行番号は**直した瞬間にずれる**ので、文書には「これは書いた時点のもの」と明記する
- 誤りを見つけたら**先に文書を直す**。直す作業の途中で「文書が違う」と気づくと、どちらが正しいのか分からなくなる

### 「使われていない部品を消す」に従う前に、規則の番人を探す
消える部品のドキュメントやテストが、**まだ生きている規則**を1箇所で押さえていることがある。部品と一緒に消すと、規則だけが誰にも見張られない状態で残る。

- 消す前に、その規則が**新しい入口の側にテストとして在るか**を確かめる
- 無ければ**先に移してから**消す。「doc は移っているがテストは無い」は実際に起きる

### 型で表せる約束は、テストではなく型へ移す
「`None` を渡してよいのは片方だけ」のような約束を注釈で書くと、実装のたびに同じ防御が増える。型を分ければ防御もテストも要らなくなる——**そのとき消えるテストは、消すのが正しい**（同じことを型が言っている）。

## 参照される側を先に置く
ファイルを組で書くとき、**参照する側を先に書くと、その瞬間に読まれて「参照先が無い」状態で確定する**ことがある。

擬似 claude はセッションの JSONL を書いてから `<セッションID>/subagents/` を写していた。パーサはその隙間で起きうるので、**子の無い木がそのまま画面まで届く**。順序を入れ替えれば隙間そのものが無くなる。

- **待ち時間を伸ばして誤魔化さない。** 順序で消せる race は順序で消す
- 症状は「通しでだけ、たまに落ちる」になる。単独で再現しないものは、**書き込みの順序**を疑う

## 共有のサーバを使うテストの、後片付けの待ち時間
E2E は全テストで1台のサーバを共有する。片付けは**混んでいる時間に走る**ので、既定の5秒では往復が収まらないことがある。

- 片付けの待ちは**製品の主張ではない**ので、実態に合わせて長く取ってよい
- 逆に、**製品の主張の待ちを伸ばすのは最後の手段**。そこを伸ばすと「遅くても通る」を認めたことになる

## ファイル監視（notify）を足すとき
**読む行為そのものが通知を起こす。** notify 8.2.0 の既定マスクには `WatchMask::OPEN` が入っており、
`IN_OPEN` は `open(2)` のたびに上がる。したがって「通知が来たら読む」を素直に書くと、
**自分の読み取りで自分を起こし続ける輪**ができる。

実際に踏んだ（ローカルイシュー「ダッシュボードでセッションを動かすと WSL が落ちやすい」の調査）。
`transcript-parser` が毎秒 5〜50 万回の `read` を回し、**セッション2本以上で毎分 340〜500 MB を
無制限に食った**。セッションを畳んでも、親を落としても止まらなかった。

### 通知は必ず合流させる。1件を1件のまま運ばない
受け手が「とにかく見に行く」形（冪等な `Poke`）なら、**溜まっているぶんは1回に畳んでよい**。
畳まないと、生産が消費より速い状態がそのまま無制限の行列になる。

### 行列に上限を置く。冪等な合図は捨ててよい
`std::sync::mpsc::channel` は上限が無い。冪等な合図には `sync_channel` を使い、
**満杯なら捨てる**。捨てても定期の巡回が拾う。

### 制御メッセージを、合図と同じ列に並べない
**FIFO は「止める」も待たせる。** `Stop` や `Watch` を `Poke` と同じ列へ入れると、
育った行列の後ろで埋もれる。実測では、40秒ぶん育てただけで

- stdin の EOF で送った `Stop` が **60秒経っても届かない**（その間も嵩は増え続ける）
- 後から届いた `Watch` の処理が **45秒遅れる**（＝そのセッションの履歴が出てこない）

**制御は別のチャネルに分け、`recv` で先に見る。** 「止める手段を持っている」ことと
「止められる」ことは別である。

### 直したかどうかは、claude を起こさずに確かめられる
パーサは stdin/stdout の JSON Lines で喋るので、**単体で駆動できる**。
`~/wsl-probe/repro*.sh` がその形（クォータを1回も使わない）。`repro3.sh 2` が
「±0 MB/分」になれば輪は止まっている。

## WSL の外（Windows 側）を測るとき
**WSL の中だけを見ると、いちばん見たい瞬間が丸ごと採れない。** 実測では、WSL の中の
`PSI memory some` が全区間 0.0 のまま、Windows の `Pages/sec` が 82,941 まで跳ねていた。
**苦しんでいたのは Windows のページングのほうだった。**

### 見張りは「切り離して」起こす
`powershell.exe` を WSL から普通に起こすと、標準出力の中継が WSL 側にある。
**WSL が固まると記録も止まる**——固まった瞬間を残したいのに、そこが空白になる。
`Start-Process` で切り離し、**Windows 側のファイルへ直接書かせる**。

### PowerShell 5.1 の `-Encoding UTF8` は BOM を付ける
BOM（`\xef\xbb\xbf`）は空白ではないので `strip()` では落ちず、`json.loads` が失敗する。
**エラーは出ない。** 値が欠けたまま最後まで測り終わるので、**1回目に「値が入っているか」を
目で見る**まで気づけない。読む側で `lstrip('﻿')` する。

### 見る欄
`Available MBytes` だけでは足りない。**`Pages/sec` と `Memory Compression` の嵩**を併せて見る。
物理が足りないと Windows は圧縮で吸収するので、Available が減る前に圧縮が育つ。
`vmmemWSL` は `WorkingSet` と `PrivateMemorySize` の**両方**を採る——差がそのまま
「圧縮・ページアウトされている量」になる。

## 使い捨てのダッシュボードを立てて測るとき
実機（8787）で測ってはいけない。理由は2つあり、**2つ目は事故になる**。

1. 実機のカードが測定用のセッションで汚れる
2. **`selfheal.json` の `known_versions` が CLI の版より古いと、セッションを1本起こした瞬間に
   無人のカナリアが本物の claude を起こす。** ゲートが落ちれば修復セッション（もう1本）と
   `scripts/cargo`（Docker の release ビルド）まで走る。測っているものが変わるうえ、クォータも使う

### 使い捨て側に必ず入れる3つ
| 設定 | なぜ |
|---|---|
| `selfheal_enabled = false` | 上の2 を踏まないため |
| `state_dir` を専用の場所へ | 実機と記録・オフセットを取り合わないため |
| `claude_settings_path` を影のファイルへ | **利用者の本物の `~/.claude/settings.json` を触らせない**ため（モデル切替が書き戻す）。ついでに `{"model":"haiku"}` にしてクォータを抑える |

### ブラウザを立てずに操作する
ブラウザは**測ろうとしている資源を自分で食う**。`/ws` は素の WebSocket なので、
依存ゼロのクライアントで足りる（`~/wsl-probe/wsclient.py`）。メッセージは
`{"t":"spawn"|"send_input"|"kill"|"archive", …}`。**クライアント→サーバのフレームはマスクが要る。**

### 見張り自身が測定を汚さないようにする
「プロセス生成レート」を測るなら、**見張りが fork してはいけない**。bash のループで
`cat` や `awk` を呼ぶと自分の fork が混ざる。`/proc` を直読みする常駐 python 1本にする
（実測：見張りありで `fork/s` 中央値 3.0、なしで 3.6 ＝ 汚していない）。

### 負荷を上げる実験には、自動で止まる線を先に入れる
人の反応を当てにしない。**しきい値をわざと緩い値へ差し替えて発火させ、畳む動作まで
走ることを確かめてから**本番値に戻す。畳む相手は**親子関係で特定する**（`pkill -f` は使わない）。

## 複数のセッションが同じリポジトリを触るとき
**このプロジェクトでは、複数の claude が同じ作業ツリーで同時に動く**（実測で4本が同じ
作業ディレクトリを持っていた）。1人で触っている前提の手癖が、そのまま他人の作業を壊す。

### `git add -A` ／ `git add .` を使わない。**パスを名指しする**
他人の書きかけが自分のコミットへ丸ごと入る。実際に、十字ボタンのドキュメント更新の
コミット1つへ、**別々の2セッションの実装**（設定の選択肢まわりと、構造化ビューの本文表示）が
入った。

害は2つある。

- **台帳が嘘になる。** `git log` でその機能を探しても、無関係な題のコミットしか出てこない
- **通していない変更が main に乗る。** 巻き込まれた側は、その時点でまだ**コンパイルすら
  していない**ことがある（実際にそうだった）

巻き込んでしまったら**履歴は書き換えない**——共有ブランチで、しかも他が動いている最中に
`rebase` を当てるほうが害が大きい。代わりに**すぐ `cargo check --workspace --all-targets` で
main が壊れていないことを確かめ**、巻き込んだ事実をコミットメッセージか実行レポートへ残す。

### 巻き込まれた側は「自分の変更が差分から消えた」形で気づく
症状は**編集したはずのファイルが `git status` に出ない**。消えた・戻されたと読む前に
`git log --oneline -- <ファイル>` を見る。中身がファイルに残っているなら、誰かのコミットへ
入っている。

### 持ち主は、コミットメッセージの `Claude-Session:` で確かめる
他のセッションから「そちらの `git add` に巻き込まれた」と連絡が来ることがあるが、
**取り違えていることがある**（巻き込んだ第3のセッションが居て、双方が被害者ということが
実際にあった）。トレーラの `Claude-Session:` が持ち主を一意に示すので、**名指しされたら
まずそこを見る**。自分のセッション URL と突き合わせれば、身に覚えのない指摘かどうかが
1秒で分かる。

### 版を上げる作業は、他が動いていない時間にまとめて1回
作業の途中で workspace の版が黙って上がっていることがある（別セッションがリリースを
準備している）。**タグを打つ前に `git log` を見る。** リリースのビルドは十数分かかり、
その間に誰かが push すると**タグがブランチの先端でなくなって 403 で落ちる**（別節）。

### 検査と E2E は、他人の書きかけで落ちうる
`make lint` の `tsc -b` は web の木を丸ごと型検査するので、**他セッションが編集中の
ファイルも一緒に見る**。落ちた場所が自分の触っていないファイルなら、**直さずに切り分けて
報告する**——他人の作業を勝手に直すと、あちらの手元と食い違う。

E2E も同じで、**先にポート（4173 / 4174 / 4178）が空いているかを見る**。
`reuseExistingServer` があるので、塞がっていると**気づかないまま他人のバイナリへ繋ぎに行く**。
