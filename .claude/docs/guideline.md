## フィクスチャを採取するとき

### 本リポジトリは公開（PUBLIC）である
`fixtures/` に入れる実トランスクリプトは、そのまま世界に公開される。採取物は必ず `scripts/sanitize-fixtures.py` を通すこと（`make fixtures` は通す）。

### `type: "attachment"` のレコードは中身ごと落とす
Claude Code のトランスクリプトには、採取内容と無関係に**その環境の構成情報**を書き出す `attachment` レコードが混ざる。実際に確認された中身は次のとおり。

- `skill_listing` … 導入済みスキルの全一覧と説明（1万文字規模）
- `agent_listing_delta` … 定義済みカスタムサブエージェント
- `deferred_tools_delta` / `mcp_instructions_delta` … 接続中のMCPサーバとその指示文
- `hook_additional_context` / `hook_cancelled` … フックの内容とコマンド行

何が入るか事前に列挙できないため文字列置換では消せない。パーサ側では attachment は表示対象外として読み飛ばす種別なので、**中身を落としてレコードの形だけ残す**方式で対処している（`sanitize-fixtures.py` が自動実行）。この処理を外すと個人環境の構成が公開される。

### `type: "system"` のレコードも中身を落とす
`subtype: "stop_hook_summary"` の `hookInfos` に、**利用者のフックのコマンド行**（スクリプトのパスと名前）がそのまま入る。`attachment` とまったく同じ「採取内容と無関係に環境の構成情報が入る」種別で、`sanitize-fixtures.py` が自動で落とす。

`attachment` も `system` も**レコードごと消してはいけない**。どちらも `uuid`/`parentUuid` を持って親子の鎖に参加しており、消すと後続のレコードが置き場所を見失う。中身だけを落として形を残す。

### 追加採取はラベルを絞る
`./scripts/gen-fixtures.sh <ラベル>` で1つだけ採れる。引数なしの `make fixtures` は全部を採り直すが、**既存のフィクスチャを採り直すとゴールデンテストの期待値がずれて無関係なテストが落ちる**。増やしたいときは絞って呼ぶこと。

### 利用者定義のスキル名も伏せる
attachment を落としても、実際にスキルを起動していればツールコールと本文の両方に名前が残る。フックがセッション開始時にスキルを起動する設定になっていると、採取のたびに必ず混入する。`sanitize-fixtures.py` は Skill ツールコールからスキル名を**動的に抽出**して置換する（スクリプトに具体名を書くとそれ自体が公開情報になるため、ハードコードしない）。

### フィクスチャはヘッドレスで採るので、対話モード専用のレコードが入らない
`gen-fixtures.sh` は `claude -p`（ヘッドレス）で採取している。**対話モードでしか書かれないレコード type はフィクスチャに入らないため、ゴールデンテストをいくら通してもそこは検証されない**。

実例：`file-history-delta` は対話モードでファイルを1つ編集するたびに1件書かれるが、ヘッドレスでは現れない。パーサの分類から漏れていたことに気づけず、実運用では編集のたびに「不明なイベント」が履歴へ混ざっていた（`/rewind` の実測で本物のトランスクリプトを読ませて発覚）。

対策として、**レコード type に関わる実装を触ったときは、実物の対話セッションのトランスクリプトを1本パーサに通して `unknown_types` が空になることを見る**こと。`./scripts/rewind-probe.sh` が採取する記録がそのまま使える。

## 本物の claude を実験やテストで起動するとき

### 利用者のグローバル設定を外すには `--setting-sources project,local`
`--settings` は「追加読み込み」なので、**利用者のグローバル設定（`~/.claude/settings.json`）のフックも一緒に動く**。セッション開始時にスキルを自動起動する設定になっていると、そのスキルが権限確認を次々に出し、こちらが TUI へ送ったキー入力が**権限確認の応答として吸われる**。`/rewind` の実測はこれで一度完走できなかった。

`--setting-sources project,local` は読み込む設定ソースから `user` だけを外すオプションで、次が成り立つことを実測で確認済み。

- 利用者のフック・スキルは動かない
- `--settings` で渡した独自フックは**そのまま動く**（9イベントすべて）
- 認証は通常どおり

**利用者の設定ファイルには絶対に触らない。** 起動フラグだけで隔離できる。

他の候補との違い：

| 手段 | 使えるか |
|---|---|
| `--safe-mode` | カスタマイズを一括無効化する。独自フックまで止まる可能性があるので、フックが要る場面では使わない |
| `--bare` | 認証が `ANTHROPIC_API_KEY` 限定になり OAuth を読まないので使えない |
| `--permission-mode bypassPermissions` | キー入力はメニューへ届くが、**背景で動く利用者のスキルが何をしても自動承認される**。採ってはいけない |

### ダッシュボード経由で試すときは実行ファイルを差し替える
製品コードに実験用のフラグを足さないこと。`AGENTDASHBOARD_CLAUDE_BIN` に「フラグを足して `claude` を exec するだけのラッパー」を指させれば足りる（実CLIテストで `--permission-mode manual` を足しているのと同じ手口）。

### 使い捨てセッションの後始末は、CLI が落ちきってから
CLI は**終了する間際にもトランスクリプトへ書く**。先に `~/.claude/projects/<...>` を消すと、その書き込みでディレクトリが復活して残骸が残る。プロセスの終了を待ってから消すこと。消す前に、対象が本当に `~/.claude/projects/` 配下かを必ず確かめる（空文字や `.` を掴むと事故になる）。

## セッションへ指示を送る経路を触るとき
本物の TUI が相手なので、**「正しいバイト列を作れたこと」と「TUI が受け取れること」は別**。純粋関数のテストだけでは足りない。詳細と実測値は設計§18。

### 送る経路は `Session::send_instruction` に集約する
`write_input` を直に呼んでバイト列を組み立て直さないこと。同じ壊れ方が別の場所で再発する。守るべき約束は3つあり、**どれか1つでも欠けると壊れる**。

1. 送る前に `Ctrl+U` で入力行を空にする（残っているものへ追記されるため）
2. 行数によらず bracketed paste で包む（長さで挙動が変わるため）
3. 確定の CR は**本文とは別の書き込み**で送る（貼り付けの処理に飲まれるため）

本文と確定の間の待ちを詰めてはいけない。2つの書き込みが1回の読み取りにまとまると元に戻る。

### 実CLIテストには「境目より長い単一行」を必ず入れる
TUI が貼り付けと判定する境目は 57〜64 バイトの間で、**日本語なら20文字ほど**で超える。短い文字列だけで試すと、実用上ほとんどの指示が届かない状態を見逃す。実際にフェーズ4の実CLIテストは複数行と `/exit`（7バイト）しか試しておらず、フェーズ6の受け入れテストまで気づけなかった。

### 空送信（本文なし）では入力行に触らない
`encode_parts("")` は CR だけを返す。これは TUI のメニューを確定させる用途なので、ここで `Ctrl+U` を送ると選択中のメニューに余計なキーを打ち込むことになる。

## 実 claude を起動して検証するとき（資源の使い方）
本アプリの検証は**本物の claude を PTY で起こす**ので、普通の開発より資源を食う。実測で claude 1本あたり RSS 約464MB。フェーズ6の作業中に WSL が停止しており、寄与した可能性を否定できなかった。

### 同時に走らせるのは1本まで
一覧やグループ化の確認でどうしても複数要るときだけ増やし、**終わったら即座に落とす**。開きっぱなしにしない。

### core を落とす前に、パーサが残っていないか見る
パーサには孤児化しないための見張りが入っているが、**即座ではない**（負荷があると数秒かかる）。落としたら `ps` で確認する習慣にする。

```
ps -eo pid,ppid,cmd | grep '[t]ranscript-parser'
```

### `pkill -f` でプロセスを探さない
`pkill -f 'target/release/agentdashboard'` はパターンが**自分のシェルのコマンド行にもマッチ**して、実行中のシェルごと殺す（実際に起きた）。待ち受けポートから PID を引くこと。

```
PID=$(ss -ltnp | grep 8787 | grep -oP 'pid=\K[0-9]+' | head -1)
```

### ビルドは必要なときだけ
Docker 内の release ビルドはメモリを大きく食う。「直した → すぐ実機で見る」を繰り返すと、ビルドが積み上がる。まとめて回す。

### Playwright MCP のスクリーンショットは出力先を指定する
指定しないと**起動時のカレント（＝リポジトリのルート）に書き出される**。本リポジトリは公開なので、気づかずにコミットされる。実際にフェーズ5で2枚入っていた。`.gitignore` でルート直下の画像を弾いてはいるが、置き場所はスクラッチパッドを指定すること。

## Rust のコマンドを実行するとき

### `cargo` を直接呼んではいけない
ホストに Rust ツールチェーンは入っていない。cargo / rustc / clippy / rustfmt / nextest はすべて Docker イメージの中にあり、`scripts/cargo` がその唯一の入口になっている。

```
scripts/cargo build --release
scripts/cargo nextest run
scripts/cargo tree -i tokio-tungstenite -e normal
```

`cargo: command not found` が出たら、ラッパーを経由し忘れている。Makefile も自己修復機構もこの1つの入口に集約する方針なので、新しい経路を作らないこと。詳細は `.claude/docs/knowledge/開発環境とツールチェーン.md`。

### web を変更したら core を作り直す必要がある
`agentdashboard` バイナリは `web/dist` を**コンパイル時に**取り込む。フロントを直しただけでは
バイナリの中身は古いままなので、動作確認は必ず `make build`（または `make e2e`）を通すこと。
`crates/core/build.rs` が `web/dist` の変更を cargo に伝えるようにしてあるので、ビルド順さえ
守れば自動で作り直される。

### 本物の claude を使うテストは `make test-cli`
`make test` では走らない（`#[ignore]` 付き）。実行すると**本物の claude が起動し、利用者のアカウントのクォータを消費する**ので、明示的に叩くときだけにすること。ビルドはコンテナ、実行はホストという二段構えになっている理由は `.claude/docs/knowledge/開発環境とツールチェーン.md` を参照。

テストから実行ファイルの場所を求めるときは `CARGO_BIN_EXE_*` ではなく `testkit::binary_path()` を使う。前者はコンパイル時のパス（＝コンテナ内の絶対パス）が焼き込まれるため、ホストで実行した瞬間に壊れる。

### ビルドした成果物はホストで動かす
コンテナはツールチェーンの置き場所に徹しており、`agentdashboard` バイナリはホストで実行する。本アプリは PTY で本物の claude CLI を起動し、ホストの `~/.claude` とユーザのプロジェクトを触るのが本質のため。

### 絞り込んで走らせたテストは別バイナリを作り直さない
統合テストの一部は**別の実行ファイル**を子プロセスとして起動する（`transcript-parser` / `fake-claude` / `agentdashboard`）。`scripts/cargo nextest run --test <名前>` のように絞ると、それらのバイナリは作り直されない。**直したはずの挙動が変わらない**という追いにくい状態になるので、絞って走らせるときは先に `scripts/cargo build` を通すこと。`make test`（全体実行）では起きない。

## パーサ（transcript-parser）を触るとき

### 標準出力は IPC 専用。ログは標準エラーへ
core とは stdout の JSON Lines で会話している。1行でも他のものが混ざると core の行パースが壊れ、「繋がっているのに何も届かない」という沈黙になる。デバッグ出力を入れるときは必ず `eprintln!` を使う。

### 再開位置は core が持つ。パーサは覚えない
どこまで読んだかは core が `offsets.json` へ書く。パーサ側に状態を持たせると、自己修復でバイナリを差し替えた瞬間に失われる。パーサは「ここから読め」と言われた位置から読むだけにする。

### ノードIDに URL で意味を持つ文字を使わない
ノードIDは履歴の遡り（`?before=<id>`）でクエリ文字列に載る。`#` を入れるとフラグメント扱いで値が切れる。区切りが要るときは `.` や `:` を使う。

### 「表示しない」と「捨てる」は別
`attachment` / `system` は表示しないが `uuid` を持ち、親子の鎖に参加する。捨てるとその先のレコードが置き場所を見失う。**表示しないが鎖は繋ぐ**という扱いが要る。捨ててよいのは `uuid` を持たない種別（`queue-operation` / `ai-title` 等）だけ。

## 自己修復（selfheal）を触るとき
本物の claude を**無人で起動して自分のソースを書き換える**機能なので、他のどこよりも慎重に扱う。

### 外の世界へ出る操作は必ず `SelfhealOps` 越しにする
cargo・git・本物の claude を直接呼ぶコードを増やさないこと。**Rust のテストは
`scripts/cargo`（= `docker run`）の中で走るので、その中からもう一度 docker は呼べない。**
差し替えられない場所に外部コマンドを書いた瞬間、その経路は自動テストで一切踏めなくなる。

### worktree はリポジトリの中（`.selfheal/`）に置く
`scripts/cargo` はリポジトリだけをコンテナへマウントする。外に作るとコンテナから見えず、
worktree の `.git` が指す親も辿れない。cargo の作業場所は
`AGENTDASHBOARD_CARGO_DIR`（リポジトリ相対）で切り替える。入口は増やさない。

### worktree に `.gitignore` されたものは存在しない
git が持ってくるのは追跡しているファイルだけ。`node_modules/` のようにビルドや検査へ
**必要なのに追跡していないもの**は、worktree では自分で用意しないと無い。用意し忘れると
ゲートは「実行できなかった」ではなく**「落ちた」**として現れ、原因が見えにくい。

用意する手段にシンボリックリンクを選ぶ場合、`.gitignore` の書き方に注意する。git は
リンクをディレクトリとして扱わないので、**末尾に `/` を付けたパターンでは無視されない**。
無視されないと変更範囲の検査に引っかかり、`git clean -fd` でも消える。

### 通していない経路は「動く」と書いてはいけない
上の不具合が出荷まで残ったのは、**別名表の見直しの流れを一度も通していなかった**ため。
契機（CLI の版が上がったとき）を擬似 claude では踏めないことが、そのままテストの空白に
なっていた。踏めないなら**入口を公開してテストから直接呼ぶ**。契機が再現できないことは、
流れを確かめない理由にならない。

### `bypassPermissions` と `--setting-sources project,local` は必ず組で使う
バイパスだけだと、利用者のグローバル設定のフックやスキルまで**自動承認で**走る。
爆発半径をパーサ修復の外へ広げないために、利用者の設定は読み込ませない
（利用者の設定ファイルには触らない。起動フラグだけで隔離する）。

### 修復の合否は「言葉」ではなく「機械」で決める
プロンプトに「パーサだけ直して」と書くのは必要だが、担保にはならない。触った範囲は
`git status --porcelain` で検査し、合否は core が独立に実行したテストだけで決める。
エージェントの自己申告は使わない。

### 「直す」より先に「戻す」を考える
差し替えたあとに異常が出たら、直しにいくのではなくロールバックする。ここで修復へ進むと、
悪いパーサを載せたまま何度も直そうとする。あわせて**版に関わらない全体のクールダウン**を
必ず通すこと。どのパーサでも読めないデータが混ざっていると、率の検知は版に関係なく
何度でも発報するので、これが無いとカナリアと修復セッションが止まらずクォータを使い切る。

### フィクスチャを増やす場所は決まっている
`fixtures/<版>/<ラベル>/session.jsonl` に置けば、発見型のゴールデンゲートが自動で拾う。
テスト側にパスを直書きしないこと（書くと、足したサンプルが検証されないまま
「対応済み」と記録される）。**意図的に壊したデータを `fixtures/` へ置いてはいけない** —
ゲートが常に落ちるようになる。壊れたデータが要る訓練は、worktree の中に置く。

## サーバ⇔ブラウザのメッセージを増減するとき
WebSocket のメッセージ型は Rust と TypeScript で**手書きで二重に定義**している。片方だけ直すと
コンパイルは通るのに動かない、という追いにくい状態になる。1つ増減するたびに次の4箇所を揃えること。

| 直す場所 | ファイル |
|---|---|
| Rust の型 | `server/crates/protocol/src/ws.rs` |
| Rust の往復テスト | 同ファイルの `tests` モジュール |
| TypeScript の型 | `web/src/lib/protocol.ts` |
| TypeScript の突き合わせテスト | `web/src/lib/protocol.test.ts` |

両側のテストは「同じ JSON 文字列になること」を確かめている。ここが唯一のズレ検出手段なので、
種別を増やしたら必ずテストにも足す。

設計に無いメッセージを足す場合は、**設計.md §4 の表にも追記**する。実装と設計が食い違ったまま
次のフェーズへ進むと、どちらが正なのか判断できなくなる。

## セッションに注入するフックを触るとき

### `--settings` は「置き換え」ではなく「追加」
利用者のグローバル設定（`~/.claude/settings.json`）は書き換えないが、**そちらのフックも同時に動く**。
ダッシュボードが起動したセッションでも、利用者のフック（セッション開始時のスキル自動起動など）は
そのまま発火する。「ダッシュボードが注入したものだけが動く」と考えて設計すると食い違う。

### 観測専用のフックは標準出力に何も書かない
UserPromptSubmit / SessionStart 系のフックは「終了コード 0 のときの stdout を Claude への
コンテキストとして注入する」仕様になっている。`hook-post` がここに何か出すと、ダッシュボードが
利用者の会話へ勝手に文字列を差し込むことになる。`{}` すら返してはいけない。

### 失敗しても終了コードは 0
ダッシュボードが落ちていることが CLI の動作を妨げてはならない。宛先不達・URL 不正・stdin 異常、
どの経路でも黙って 0 で終わる。

## テストから自分のサーバを叩くとき

### ブロッキングHTTPはテストのスレッドで待ってはいけない
`#[tokio::test]` の既定はスレッド1本のランタイムで、そこに `axum::serve` を相乗りさせている。
テストのスレッドが `TcpStream` で応答を待つと、その間サーバが動けず、**自分の応答を自分で
待ち続ける形で固まる**。実際にテスト一式が10分以上返ってこなくなった。

`tokio::task::spawn_blocking` で専用スレッドへ逃がすこと。`common::TestServer` の
`post_hook` / `get` は既にそうなっている。新しい入口を足すときも同じ形にする。

### フックの宛先URLは settings に焼き込まれる
`TestServer` は**先に待ち受けポートを確定させてから設定を作る**。注入する settings には
`http://127.0.0.1:<port>/hook/...` が書き込まれるため、後からポートが変わると届かない。

## ローカルイシューのドキュメントを編集するとき

### `MyDocs/` は git 管理外。コミット対象にならない
`.gitignore` に `/MyDocs/` が入っている。ローカルイシューのドキュメントをいくら書いても
`git status` には出ないので、**「作業別にコミットする」の対象に数えてはいけない**。
実装作業の計画にドキュメント更新を含めるときは、その分をコミット単位から外すこと。

リモートへ渡る経路は git ではなく `issue_sync`（後述）だけである。手元に残す唯一の
控えでもあるので、消す方向の編集には別の注意が要る（後述の「情報量を減らす方向の編集」）。

### 設計.md の節番号は振り直さない
`MyDocs/ローカルイシュー/初期実装/設計.md` の `## N. 見出し` という節番号は、`計画.md` と `テスト計画.md` から `§N` の形で参照されている。既存節の番号を振り直すと参照が一斉に壊れるため、節の追加は**末尾への追加のみ**とする。削除や並べ替えがどうしても必要な場合は、参照元2ファイルの `§` 表記を同時に修正すること。

### 追補ドキュメントは統合・削除済み
`〜 追補：〜.md` は 2026-07-28 に本文（`方針.md` / `設計.md` / `計画.md`）の巻末節へ統合し、**ローカルファイルは削除済み**。以後は本文が正。本文には訂正前の旧記述も併記してあるため、経緯を追いたい場合は本文の巻末節を読めばよい。

**リモート側の追補3コメントも削除済み**（2026-07-28 のフェーズ1同期時に確認）。イシューのコメントは `方針` / `設計` / `テスト計画` / `計画` / `実行レポート` の5件のみで、ローカルファイルが復活する余地は無くなった。

## ドキュメントの情報量を減らす方向の編集をするとき
統合・要約・整理などで既存ドキュメントを書き換える場合は、次の手順を踏むこと。

1. 編集前に対象ファイルをスクラッチパッドへ退避する
2. 編集後に `diff` で「削除・変更された行」だけを抽出し、意図した変更と一致するか1行ずつ照合する
3. 統合元がある場合は、統合元の全非空行が統合先に存在するかを逐語検索で確認する

**理由**：`MyDocs/` は git 管理外でありロールバック手段が無い。退避と差分照合が唯一の復元・検証手段になる。

## リモートイシューと同期するとき
本PJTのローカルイシューは GitHub Issue と `issue_sync` スキルで同期される。`要件.md` がイシュー本文、他のドキュメントは1ファイル＝1コメントに対応する。`TS.md` は同期スキルの管理ファイルなので手動編集しない。ローカルでファイルを増減させた場合、次回同期でリモート側にも反映される点を意識すること。

### `要件.md` は毎回「リモートが新しい」と出るが、たいてい嘘
GitHub の issue の更新日時は、**コメントを足したり直したりしただけでも動く**。本文を誰も編集していなくても、コメントを同期した次の回には本文が「新しくなった」ことになる。

判定を鵜呑みにせず、**リモート本文とローカル `要件.md` の内容を突き合わせてから**方向を決めること。一致していればスキップでよい。ここで TS.md を偽の日時で埋めると、本当に本文が編集されたときに検知できなくなる。

## ブラウザ側のストアを触るとき

### 「接続済み」と「一覧が出ている」を同じ意味にしておく
一覧の受信は `requestAnimationFrame` でまとめてから反映する（バーストで届くため）。ただし
**`GET /api/sessions` のスナップショットだけは束ねてはいけない**。接続1回につき1度しか
来ないので束ねる意味が無く、束ねると「接続済みと表示されているのに一覧はまだ空」という
隙間ができる。

この隙間は、テストの後片付けが「カードは0枚」と早合点して切り上げる形で表に出た。残った
カードが次のテストへ漏れ、**落ちるテストが実行のたびに変わる**という追いにくい壊れ方になる。

### E2E の後片付けは画面ではなくサーバに聞く
小窓の数を数えると「まだ描かれていないだけ」と「もう無い」を区別できない。`GET /api/sessions`
を直接読み、消す相手もIDで名指しすること（`.first()` だと消したい相手と押した相手がずれうる）。

### 動きを付けてよいのは低頻度の更新だけ
PTY のバイトと履歴の追記の経路にアニメーションを入れてはいけない（体感速度の生命線）。
一覧の小窓に `layout` を付けるのも禁止 — 並びが変わるたびに小窓が動き、**押そうとした瞬間に
的が逃げる**。一覧は「押して開く」ための画面なので、見栄えより狙いやすさを優先する。

### flex の中で `truncate` を使うなら `min-w-0`
flex の子は既定で中身の幅より小さくならないため、`truncate` を付けても縮まない。長い作業
ディレクトリのせいで隣の状態ラベルが縦に割れる、という形で表に出た。**縮んでよい要素にだけ
`min-w-0`、その他には `shrink-0`** を付ける。

### 端末の見た目は xterm のオプションでしか変えられない
WebGL レンダラを載せているので、カーソルも文字も **canvas に描かれる**。CSS を書いても届かない。
指定する場所は `TerminalPane` の `TERMINAL_OPTIONS` 1箇所に集約してある。

既定値をそのまま使うと**意図と違う見え方になることがある**。実例：`cursorStyle` の既定は
`block` で、カーソル位置の文字を塗り潰すため「上書きモードで打っている」ように見える
（実際の行編集は CLI 側の責務で、挿入モードのまま）。**振る舞いは正しいのに見た目だけが
嘘をつく**ので、動くかどうかのテストでは絶対に見つからない。

### 見た目の崩れはテストでは捕まらない
描画自体はされているので、要素の存在を見るテストは通ってしまう。差分の色が付いていない
（フェーズ3）・状態ラベルが縦に割れる（フェーズ4）は、どちらも**実物を目で見て**初めて
分かった。画面に手を入れたら、ビルドした単一バイナリを起動して Playwright MCP で見ること。

## 利用者が打つ・貼る値を受け取るとき
本アプリは **WSL の上で動き、利用者は Windows 側から値を持ってくる**。パスなら `\` 区切り、
`\\wsl.localhost\...`、`"` で囲まれた「パスとしてコピー」の形が普通に来る。開発者が打つ形
（きれいな絶対パス）だけを想定すると、実運用の初手で弾かれる。

### 入力を書き換えず、解釈を並べて先頭から当てる
「`\` を `/` に置換する」のような**破壊的な正規化はしない**。Linux では `\` もフォルダ名に
使える文字なので、実在のフォルダを開けなくする。`session/cwd.rs` のように
**入力そのままを先頭に置いた候補の列**を作り、最初に当たったものを採ること。
これなら従来の解釈が一切変わらないまま、受け取れる形だけが増える。

### 解釈した結果はエラーに書く
読み替えが効かなかったのか、読み替えた先が無いのかは、利用者からは区別できない。
「見つからない」と言うときは**何として読んだのか**を添える。

## ソースに制御文字を混ぜない
`stores/transcript.ts` の番兵の値に **NUL バイト（`\0`）が混入していた**ことがある。
`'\0root'` は見た目が `' root'` と区別できず、文字列一致での編集が理由の分からない失敗を
起こす（Edit ツールが「見つからない」と言い続ける）。

衝突しない印が要るときは、**そこで使えないと決めてある可視の文字**を選ぶこと。ノードIDは
`#` を含まないと決めてあるので（URL のフラグメント対策）、`#root` のような形にする。

不審な編集失敗が続いたら、`grep -P '\x00'` か Python でファイルの生バイトを確認する。

## 端末の表示を読んで判断するとき
初期実装§10 が定めた「構造化ビューは ANSI を解析しない」は今も守る。ただし
**「キーを送ってよい画面か」「いま TUI が何を表示しているか」を確かめる用途**では
端末を覗く（自己修復のフォルダ信頼の確認、権限モードのフッタ読み取り）。その際の約束。

### 読む対象は画面ではなく生のバイト列
`tmux capture-pane` はレンダリング後の画面を返すが、ダッシュボードが持っているのは
PTY から流れてきた**生のバイト列**である。この2つは同じではない。

実例：TUI のフッタは語ごとに別々に書かれ、間はカーソル移動で埋められる。画面では
`⏵⏵ accept edits on` と見えるが、生の並びは `⏵⏵accepteditson` で**語間の空白が無い**。
画面で見えている形のまま照合すると、単体テストは通るのに実物では永久に一致しない。

**目印を照合するときは、制御シーケンスを落としたうえで空白も取り除く。**
折り返しで語が行をまたいで割れても同じ理屈で拾える。

### 実測するときは、使うときと同じ対象を見る
上の件は、前提の実測を tmux（＝画面）で行い、実装は生のバイト列を読んでいたために
起きた。**測るときと使うときで読む対象が違えば、測った値はそのまま使えない。**
画面で確かめたことは、生のバイト列でも成り立つかを別に確かめる。

### スクロールバック全体を毎回コピーしない
1秒周期の見張りから呼ぶような場所では、`Session::scrollback_text()`（既定 1MiB）を
使うとセッション数だけ無駄が積み上がる。末尾だけ読む `scrollback_tail` を使う。
フッタのように「更新のたびに書き直されるもの」は末尾に必ずある。

## 擬似 claude（fake-claude）を触るとき

### 行編集を切ってあるので、制御シーケンスは自分で解釈する
Shift+Tab（`ESC[Z`）のように**改行を伴わないキー**を受け取るため、起動時に
`stty -icanon` で行編集だけを切っている（エコーは残す。ブラウザの端末に打った文字が
出るのはエコーの働きで、既存のテストがそれを見ている）。

その結果、それまで端末が処理してくれていたものを自分で扱う必要がある。

- `Ctrl+U`（0x15）は入力行を消す
- CSI は**終端バイト（0x40〜0x7E）まで読み切る**。途中で止めると残りが本文へ紛れ込む

### 本物の挙動に合わせる。合わせられないなら、そう書く
擬似 claude は「課金なしで毎回通せる」ことに価値があるので、**本物と違う形にした瞬間に
テストが嘘になる**。フッタの語句・巡回順・フックが運ぶ値は実測に合わせてある
（ローカルイシュー「権限確認省略モード」設計§11）。

### 起動完了の合図（`ready`）を出す位置に気をつける
確認の画面を出しているあいだは `ready` を出さない。先に出すと、受諾より前に届いた
指示が黙って捨てられ、「フックが飛ばない」という分かりにくい形でしか表に出ない。

## 利用者のグローバル設定（`~/.claude/settings.json`）を触るとき
`config.toml` はこのダッシュボードの持ち物だが、`~/.claude/settings.json` は**利用者と
他の claude プロセスの持ち物**である。同じ「設定を書き戻す」でも扱いが違う。

### 書いてよいキーを型で縛る
「このファイルを書く関数」ではなく「**このキーだけを書く関数**」にする。他のキーを
渡せない形にしておけば、あとから範囲が広がる余地がなくなる。

### 解析して書き直さず、その場を差し替える
`serde_json` で読んで書き直すと、**キーの並びが辞書順に変わりインデントもこちらの都合に
なる**。生のテキストから対象キーの値の範囲を見つけて差し替えれば、触らなかったバイトは
1つも動かない（`settings.rs` が `toml_edit` でやっていることの JSON 版）。

### 読めなければ書かない。作りに行かない
無い・壊れている・権限が無い、いずれの場合も何もしない。利用者の設定ファイルを、
ダッシュボードが勝手に生やしてよい理由が無い。

### 対象がプロセスに1つしかないなら、ロックもプロセスに1本
セッションごとに持つと、2本が同時に書いたときに元の値が永久に失われる。
「読んだ時点と違ったら書かない」という自衛だけでは、**汚染を防ぐのではなく汚染を固定する**。

### 戻した値がそのまま残るとは限らない
CLI が起動時に綴りを正規化することがある（`opus` → `opus[1m]` を実測）。意味が同じなら
追いかけない。「戻したのに一致しない」を異常として扱わないこと。

### テストと E2E は本物のファイルを相手にしない
差し替え口（`claude_settings_path`）を設定に持たせ、テストは必ずそちらを指す。
環境変数を書き換える方式にすると、並行して走る他のテストを巻き込む。
`state_dir` を差し替えられるようにしてあるのと同じ理由。

## `trap` で後始末を書くとき

### `exec` があると `trap` は走らない
`exec` はシェルごとプロセスを置き換えるので、`EXIT` の trap は**実行されない**。
終了コードを持ち越して `exit` する形にする。

```sh
STATUS=0
"${TARGET}" "$@" || STATUS=$?
exit "${STATUS}"
```

`scripts/test-cli` でこれを踏み、利用者のグローバル設定が汚れたまま残った。

### 足しただけでは走らない。走ることまで確かめる
偽の対象ファイルを相手に「失敗しても戻る・終了コードは持ち越す・バックアップは片付く」を
一度通しておく。後始末は**壊れたときにしか使わない**ので、壊れる前に確かめないと
壊れたときに初めて壊れていたと分かる。

## 擬似 claude に新しい挙動を足すとき

### 「本物がやらないこと」もやらせない
本物より**気を利かせてはいけない**。例：本物は `/model` でモデルを変えても `statusLine` を

デバウンスや間引きを省くと、擬似のほうが**重くなる**。300ms のデバウンスを省いたせいで
1行ごとに子プロセスが起き、行を多く送るテストが軒並み重くなって、資源を取り合う
別のテスト（コアレッシングの測定）が巻き添えで落ちた。

## 負荷に左右される数値をテストにするとき
「比なら機械の速さに左右されない」は**成り立たないことがある**。他のテストと資源を
取り合うと、比較対象の側も一緒に詰まって比が縮む。

そういう項目は `#[ignore]` を付けて `make perf` 側へ寄せる。Makefile が
「数値を合否にしないのは、他の作業の負荷で落ちるテストは役に立たないため」と
書いているとおり。

**テストを増やしたら、既存の測定が落ちるようになっていないか確かめる。**
変更前のツリーで通ることを確認すれば、自分が原因かどうかは切り分けられる。

## 直した不具合に回帰テストを書くとき

### 直す前のコードで落ちることを確かめて、初めて回帰テストになる
通ることだけを見ると、**何も検証していないテストを緑のまま抱え込む**。直したコードを
一時的に元へ戻し、書いたテストが落ちること・失敗メッセージに現物が出ることまで見る。

### 落ちるはずのテストが通ったら、テストではなく「戻し方」を疑う
同じ変更で複数の仕掛けを入れていると、**片方を戻しても、もう片方が旧挙動の再現を
邪魔する**。実例：学習の条件から語幹の判定を外しただけでは、同時に入れた別の分岐が
先に弾いていて、旧挙動にならなかった。

戻すのは「その不具合を生んでいた判断そのもの」まで。関係する分岐を全部たどること。

## テストが実環境へ書き込んでいないか確かめるとき
`Config::default()` をそのまま使うと、`resolved_state_dir()` は**利用者が普段使っている
場所**（`~/.local/state/agentdashboard`）を指す。テストがそこへ書くと、実運用と状態を
共有することになる。

差し替え口を設定に持たせ、テストは必ずそちらを指すこと。E2E は `state_dir` を、
モデルを扱うものは `claude_settings_path` を差し替えている。環境変数を書き換える方式に
すると、並行して走る他のテストを巻き込む。

**新しく「外の状態」を持ったら、同時に差し替え口も作る。** あとから足すと、それまでに
書き込んだぶんは残ったままになる（実際に実CLIテストが1件書き込んでいた）。

### 差し替え口を作るだけでは足りない。「未指定のとき」が本物へ落ちる
テストごとに差し替えても、**指定しなかったテストは既定の入口＝本物**へ落ちる。
書き込みは各テストで塞いだのに、読み込みがそこから漏れていた実例がある。

共通ヘルパの側で「明示が無ければ使い捨てへ」に倒すこと。個々のテストの心がけに
任せると、新しく書いたテストが必ずまた漏らす。

### 差し替え先が空だと、書き込みは防げても検査が空振りする
存在しないファイルを指した E2E は、読めないので何もせず、**注入も回復も一度も
動かないまま緑**だった。実装を丸ごと消しても通る状態になっていた。

差し替え先は**中身まで用意する**。しかも「動かなかったときの値」と違う値を置く。
同じ値だと、効いたのか何も起きなかったのかを結果から区別できない。

### 「本物ではないこと」は、避けたい相手を名指しして確かめる
`$HOME` の配下でないことで判定すると、`HOME` が `/` の環境（コンテナ）で
一時領域まで巻き込んで落ちる。避けたいのは1点（`discover()` が指す先）なので、
そこと直接比べる。**範囲で否定せず、対象を名指しする。**

## 開発環境でだけ通る差分に気をつける

### 「値が無いから起きない」は、値がある環境で起きる
テスト用の設定が**存在しないファイル**を指していると、そこから読む値は `None` になる。
`None` の経路しか通っていないコードは、値がある実環境で初めて別の道を通る。

実例：起動引数の `--model` と注入設定の `model` が重なる不具合。開発環境では注入する値が
無かったので出ず、**実機でだけ出た**。テストが緑でも安心できない類の差分である。

差し替え口を用意するときは、**値がある場合と無い場合の両方**を通しておくこと。

### 実機で落ちたら、まず「開発環境と何が違うか」を並べる
仮説から入ると外す。実際、上の件を疑って直したが原因ではなかった（直したこと自体は
正しかったが、症状は変わらなかった）。差分を並べてから絞るほうが速い。
