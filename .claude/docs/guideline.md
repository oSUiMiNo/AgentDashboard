## フィクスチャを採取するとき

### 本リポジトリは公開（PUBLIC）である
`fixtures/` に入れる実トランスクリプトは、そのまま世界に公開される。採取物は必ず `scripts/sanitize-fixtures.py` を通すこと（`make fixtures` は通す）。

### `type: "attachment"` のレコードは中身ごと落とす
Claude Code のトランスクリプトには、採取内容と無関係に**その環境の構成情報**を書き出す `attachment` レコードが混ざる。実際に確認された中身は次のとおり。

- `skill_listing` … 導入済みスキルの全一覧と説明（1万文字規模）
- `agent_listing_delta` … 定義済みカスタムサブエージェント
- `deferred_tools_delta` / `mcp_instructions_delta` … 接続中のMCPサーバとその指示文
- `hook_additional_context` / `hook_cancelled` … フックの内容とコマンド行

何が入るか事前に列挙できないため文字列置換では消せない。パーサ側では attachment は表示対象外として読み飛ばす種別なので、**中身を落としてレコードの形だけ残す**方式で対処している（`sanitize-fixtures.py` が自動実行）。この処理を外すと個人環境の構成が公開される。

### 利用者定義のスキル名も伏せる
attachment を落としても、実際にスキルを起動していればツールコールと本文の両方に名前が残る。フックがセッション開始時にスキルを起動する設定になっていると、採取のたびに必ず混入する。`sanitize-fixtures.py` は Skill ツールコールからスキル名を**動的に抽出**して置換する（スクリプトに具体名を書くとそれ自体が公開情報になるため、ハードコードしない）。

## Rust のコマンドを実行するとき

### `cargo` を直接呼んではいけない
ホストに Rust ツールチェーンは入っていない。cargo / rustc / clippy / rustfmt / nextest はすべて Docker イメージの中にあり、`scripts/cargo` がその唯一の入口になっている。

```
scripts/cargo build --release
scripts/cargo nextest run
scripts/cargo tree -i tokio-tungstenite -e normal
```

`cargo: command not found` が出たら、ラッパーを経由し忘れている。Makefile も自己修復機構もこの1つの入口に集約する方針なので、新しい経路を作らないこと。詳細は `.claude/docs/knowledge/開発環境とツールチェーン.md`。

### web を変更したら core を作り直す必要がある
`agentdashboard` バイナリは `web/dist` を**コンパイル時に**取り込む。フロントを直しただけでは
バイナリの中身は古いままなので、動作確認は必ず `make build`（または `make e2e`）を通すこと。
`crates/core/build.rs` が `web/dist` の変更を cargo に伝えるようにしてあるので、ビルド順さえ
守れば自動で作り直される。

### 本物の claude を使うテストは `make test-cli`
`make test` では走らない（`#[ignore]` 付き）。実行すると**本物の claude が起動し、利用者のアカウントのクォータを消費する**ので、明示的に叩くときだけにすること。ビルドはコンテナ、実行はホストという二段構えになっている理由は `.claude/docs/knowledge/開発環境とツールチェーン.md` を参照。

テストから実行ファイルの場所を求めるときは `CARGO_BIN_EXE_*` ではなく `testkit::binary_path()` を使う。前者はコンパイル時のパス（＝コンテナ内の絶対パス）が焼き込まれるため、ホストで実行した瞬間に壊れる。

### ビルドした成果物はホストで動かす
コンテナはツールチェーンの置き場所に徹しており、`agentdashboard` バイナリはホストで実行する。本アプリは PTY で本物の claude CLI を起動し、ホストの `~/.claude` とユーザのプロジェクトを触るのが本質のため。

## サーバ⇔ブラウザのメッセージを増減するとき
WebSocket のメッセージ型は Rust と TypeScript で**手書きで二重に定義**している。片方だけ直すと
コンパイルは通るのに動かない、という追いにくい状態になる。1つ増減するたびに次の4箇所を揃えること。

| 直す場所 | ファイル |
|---|---|
| Rust の型 | `server/crates/protocol/src/ws.rs` |
| Rust の往復テスト | 同ファイルの `tests` モジュール |
| TypeScript の型 | `web/src/lib/protocol.ts` |
| TypeScript の突き合わせテスト | `web/src/lib/protocol.test.ts` |

両側のテストは「同じ JSON 文字列になること」を確かめている。ここが唯一のズレ検出手段なので、
種別を増やしたら必ずテストにも足す。

設計に無いメッセージを足す場合は、**設計.md §4 の表にも追記**する。実装と設計が食い違ったまま
次のフェーズへ進むと、どちらが正なのか判断できなくなる。

## セッションに注入するフックを触るとき

### `--settings` は「置き換え」ではなく「追加」
利用者のグローバル設定（`~/.claude/settings.json`）は書き換えないが、**そちらのフックも同時に動く**。
ダッシュボードが起動したセッションでも、利用者のフック（セッション開始時のスキル自動起動など）は
そのまま発火する。「ダッシュボードが注入したものだけが動く」と考えて設計すると食い違う。

### 観測専用のフックは標準出力に何も書かない
UserPromptSubmit / SessionStart 系のフックは「終了コード 0 のときの stdout を Claude への
コンテキストとして注入する」仕様になっている。`hook-post` がここに何か出すと、ダッシュボードが
利用者の会話へ勝手に文字列を差し込むことになる。`{}` すら返してはいけない。

### 失敗しても終了コードは 0
ダッシュボードが落ちていることが CLI の動作を妨げてはならない。宛先不達・URL 不正・stdin 異常、
どの経路でも黙って 0 で終わる。

## ローカルイシューのドキュメントを編集するとき

### 設計.md の節番号は振り直さない
`MyDocs/ローカルイシュー/初期実装/設計.md` の `## N. 見出し` という節番号は、`計画.md` と `テスト計画.md` から `§N` の形で参照されている。既存節の番号を振り直すと参照が一斉に壊れるため、節の追加は**末尾への追加のみ**とする。削除や並べ替えがどうしても必要な場合は、参照元2ファイルの `§` 表記を同時に修正すること。

### 追補ドキュメントは統合・削除済み
`〜 追補：〜.md` は 2026-07-28 に本文（`方針.md` / `設計.md` / `計画.md`）の巻末節へ統合し、**ローカルファイルは削除済み**。以後は本文が正。本文には訂正前の旧記述も併記してあるため、経緯を追いたい場合は本文の巻末節を読めばよい。

**リモート側の追補3コメントも削除済み**（2026-07-28 のフェーズ1同期時に確認）。イシューのコメントは `方針` / `設計` / `テスト計画` / `計画` / `実行レポート` の5件のみで、ローカルファイルが復活する余地は無くなった。

## ドキュメントの情報量を減らす方向の編集をするとき
統合・要約・整理などで既存ドキュメントを書き換える場合は、次の手順を踏むこと。

1. 編集前に対象ファイルをスクラッチパッドへ退避する
2. 編集後に `diff` で「削除・変更された行」だけを抽出し、意図した変更と一致するか1行ずつ照合する
3. 統合元がある場合は、統合元の全非空行が統合先に存在するかを逐語検索で確認する

**理由**：`MyDocs/` は git 管理外でありロールバック手段が無い。退避と差分照合が唯一の復元・検証手段になる。

## リモートイシューと同期するとき
本PJTのローカルイシューは GitHub Issue と `issue_sync` スキルで同期される。`要件.md` がイシュー本文、他のドキュメントは1ファイル＝1コメントに対応する。`TS.md` は同期スキルの管理ファイルなので手動編集しない。ローカルでファイルを増減させた場合、次回同期でリモート側にも反映される点を意識すること。

### `要件.md` は毎回「リモートが新しい」と出るが、たいてい嘘
GitHub の issue の更新日時は、**コメントを足したり直したりしただけでも動く**。本文を誰も編集していなくても、コメントを同期した次の回には本文が「新しくなった」ことになる。

判定を鵜呑みにせず、**リモート本文とローカル `要件.md` の内容を突き合わせてから**方向を決めること。一致していればスキップでよい。ここで TS.md を偽の日時で埋めると、本当に本文が編集されたときに検知できなくなる。
