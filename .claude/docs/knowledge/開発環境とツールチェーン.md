## 全体像：Rust はコンテナ、Web はホスト、成果物はホストで実行
本PJTはホストに Rust ツールチェーンを入れない。cargo と rustc は Docker イメージの中だけに存在する。一方 Node はホストに導入済みのものをそのまま使い、ビルドした単一バイナリもホストで動かす。

| 対象 | どこで動くか | 理由 |
|---|---|---|
| cargo / rustc / clippy / rustfmt / nextest | Docker コンテナ | ホスト環境を汚さないため |
| npm / vite / vitest / playwright | ホスト | Node は既にホストにあり、追加の汚染が無いため |
| ビルドした `agentdashboard` バイナリ | **ホスト** | PTY で本物の claude CLI を起動し、ホストの `~/.claude` とユーザのプロジェクトを触るのが本アプリの本質。コンテナに入れると認証情報と作業ディレクトリのマウントが芋づる式に必要になる |
| フィクスチャ採取（本物の claude 実行） | ホスト | 認証情報がホストにあるため |

コンテナのベースを bookworm（glibc 2.36）にしているのは意図的。ここでビルドしたバイナリを、より新しい glibc を持つホスト（Ubuntu 24.04 / glibc 2.39）でそのまま実行できるようにするため。glibc の互換性は「新しい側が古い側向けのバイナリを実行できる」方向にある。

## cargo は必ず `scripts/cargo` 経由で呼ぶ
`scripts/cargo` は Docker イメージを起動して cargo を実行するラッパー。**cargo を直接叩く経路を作らないこと**。Makefile も、将来の自己修復機構（設計§9）のテストゲートも、この1つの入口に集約する。

ラッパーが担っている仕事は次の3つ。

- ホストの uid/gid でコンテナを動かし、`server/target/` が root 所有になる事故を防ぐ
- crates.io のレジストリキャッシュを名前付きボリュームに逃がし、毎回のダウンロードを避ける
- `web/dist` を必ず作る。rust-embed は**コンパイル時に**このフォルダの実体を要求するが、vite は build のたびに dist を作り直すため、git で空ディレクトリを追跡する方式では壊れる

リポジトリ全体をコンテナへマウントしているのも rust-embed のため。`server/` だけでは `web/dist` が見えない。

## テストをどこで走らせるか
| テスト | 実行場所 |
|---|---|
| Rust 単体テスト（protocol / config / testkit） | コンテナ |
| PTY テスト（擬似 claude ハーネス） | コンテナ。`/dev/ptmx` はコンテナ内で問題なく使える（検証済み） |
| Web 単体テスト（Vitest） | ホスト |
| E2E（Playwright） | ホスト。**ビルドした `agentdashboard` バイナリを起動して実サーバに繋ぐ**。相手にする CLI は擬似 claude（`AGENTDASHBOARD_CLAUDE_BIN` で差し替え） |
| 実CLI統合テスト（本物の claude を使うもの） | **ビルドはコンテナ、実行はホスト**（`make test-cli`）。詳細は下記 |

E2E を実サーバ構成にしているのは、静的なビルド成果物だけを見ても「本物のサーバと繋がるか」が分からず、WebSocket・PTY・フロー制御が丸ごと検証対象から外れてしまうため。`make e2e` は **web → core の順**にビルドしてから Playwright を動かす。

E2E は **ワーカー1本**で動かす。core サーバを全テストで共有しているため、並列に走らせると別のテストが起動したセッションが一覧に混ざるだけでなく、同じ端末へキー入力が交互に届いて壊れる（実際に混線して失敗した）。

## 実CLI統合テストは「コンテナでビルド、ホストで実行」
本物の claude と認証情報はホストにあり、cargo はコンテナにある。認証情報をコンテナへ渡さずに済ませるため、`make test-cli`（`scripts/test-cli`）が次の2段構えで動く。

1. `scripts/cargo test --test real_cli --no-run --message-format=json` でテスト実行ファイルだけを作る
2. 出来上がった実行ファイルを**ホストで**動かす（PATH 上の claude を使う）

コンテナのベースが bookworm（glibc 2.36）でホストがそれ以降なので、ここで作った実行ファイルはホストでそのまま動く。

### 押さえておくべき3点
- **`CARGO_BIN_EXE_*` を使ってはいけない**。コンパイル時のパスが焼き込まれ、コンテナ内の絶対パスを指してしまう。ホストで実行すると存在しないパスになる。代わりに `testkit::binary_path()` が実行時に自分の位置から辿る
- **`#[ignore]` で既定スキップ**。`make test` では走らない。実行すると**本物の claude が起動しアカウントのクォータを消費する**
- **`--test-threads=1`**。複数の claude を同時に起動すると待ち時間と出力が混ざる

## web のビルド成果物はバイナリに焼き込まれる
`agentdashboard` は `web/dist` を rust-embed で**コンパイル時に**取り込む。ここで2つ落とし穴がある。

- **デバッグビルドでも埋め込む設定にしてある**（`rust-embed` の `debug-embed`）。既定ではデバッグ時だけ実行時にフォルダを読みに行くが、本PJTは cargo をコンテナで動かしているため、埋め込まれるパスがコンテナ内の絶対パスになり、ホストで実行すると見つからない
- **`crates/core/build.rs` が `web/dist` の変更を cargo に伝えている**。これが無いと、フロントを直しても cargo が「変わっていない」と判断して古い画面のままのバイナリが出来上がる

どちらも「直したはずなのに反映されない」という原因の分かりにくい形で現れるため、外さないこと。

## Rust のバージョンをどう固定しているか
`rust-toolchain.toml` は使わず、**Docker イメージのタグで固定**している。`rust-toolchain.toml` を置くと、コンテナ起動のたびに rustup が指定バージョンを取りに行ってしまうため。

バージョンを上げるときは `docker/Dockerfile.rust` の `FROM` と `scripts/cargo` の `IMAGE_TAG`、`Makefile` の `DOCKER_IMAGE` を揃えて変更し、`make setup-rust` でイメージを作り直す。

## よく使うコマンド
```
make setup    初回セットアップ（Docker イメージ・npm・Playwright の chromium）
make test     Rust と Web のテスト
make test-cli 実CLI統合テスト（本物の claude を起動する。クォータを消費する）
make e2e      ブラウザからの通し確認（擬似 claude 相手・課金なし）
make lint     rustfmt / clippy / tsc / oxlint
make build    web ビルド → rust-embed 同梱 → 単一バイナリ
make ci       lint → test → build を通しで
make fixtures ゴールデンフィクスチャの採取と匿名化
```
