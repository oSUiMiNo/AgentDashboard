# このリポジトリの読み方
初めてこのPJTへ入る者が、**どこから読めば最短で作業に入れるか**を書く。何が正しいかではなく、**何をどの順で読むと早いか**の文書である。

規模の目安は、実装が Rust 約46,000行＋web、約束事の文書が2つで約5,000行、イシューの記録が6MB。**通読は成立しない**ので、入口を選ぶことが読む速さそのものになる。

## 読む順序
上から順に読む。どれも次を読むための地図であって、それ自体が目的ではない。

| 順 | 読むもの | 何が手に入るか |
|---|---|---|
| 1 | `.claude/CLAUDE.md` の「重要ファイル」表 | **実質このリポジトリの地図**。約60行の1行1ファイルで、責務が併記されている |
| 2 | `.claude/docs/knowledge/いま動いているもの.html` | いまどのポートで何が動いていて、どの URL がどれを指すか |
| 3 | 台帳3種（後述） | 外から何ができるか・境界がどこか・何を捨てているか |
| 4 | `server/Cargo.toml` | 依存ごとの採否の理由 |
| 5 | 触る範囲のイシュー（後述） | なぜ今その形になっているか |

**1 の表は信用してよい。** 名指しされたパスはほぼ全部が現存する。唯一ずれるのは言い換えの表の「旧名」欄だが、あれは**旧名を載せるのが役目**なので正しい。

**2 は入口としては正しいが、数字は当てにしない。** 走っている版や枚数は、**走っている本人に聞くほうが確実**である（詳細はガイドライン「現物の状態を数えるとき」）。

**4 は珍しく読む価値がある `Cargo.toml`。** 依存1つずつに「なぜこの版か」「足すと実行ファイルが何 KB 太るか」が**実測値つき**で書いてある。版を上げる判断がそこで完結する。

## 仕様の正は1箇所ではない
**初期実装イシューだけでは、いまの仕様を説明できない。** あれが扱うのはフェーズ0〜6＝ローカルモードまでで、DB の語が1度も出てこない。その後の機能は**それぞれのクローズ済みイシューが正**になっている。

| 知りたいこと | 正はどこか |
|---|---|
| 状態機械・PTY・パーサ・自己修復・WS プロトコル | `MyDocs/ローカルイシュー/クローズ/初期実装/設計.md` §1〜§18 |
| crate 分割・A2S・画面配信・DB・認証3方式・配布 | `クローズ/セルフホスト化・マルチテナント対応/` |
| 版の保管・予約・乗り換え | `クローズ/CICD/` |
| CLI の口と台帳 | `クローズ/ユーザがGUIから行える全ての事をエージェントがCLIで行えるように提供/` |
| ログの7欄・捨てている結果の台帳 | `クローズ/あらゆる経路のログを開発エージェントが読みやすいように整備/` |
| **画面の見た目** | **`DESIGN.md`**（リポジトリ直下。イシューではない） |

分散は事故ではなく前提である。**このPJTには既に参照の作法がある**——他イシューの設計は `セルフホスト化設計§25` のように**名前を前置して**参照する。新しく書くときも同じ形にすること。

**`MyDocs/` は git 管理外である。** clone しただけの環境には、上の表のうち `DESIGN.md` 以外が1つも無い。

## 実装は台帳から読む
このPJTの特徴は、**設計上の約束のほとんどが `make ci` で落ちる形に落とし込まれている**ことである。したがって台帳を読むと、コードへ入る前に地図が手に入る。**実コードと食い違えば落ちる**ので、内容が古いということが起きない。

| 台帳 | 何を機械で見張るか |
|---|---|
| `server/crates/core/tests/cli_surface.toml` | 画面でできることは CLI でもできる。**ブラウザが叩ける口が1つ残らず載る**ので、「この道具が外から何をできるか」の完全な一覧になっている |
| `server/crates/core/tests/dependencies.rs` | crate 境界。PTY を持つのはどこか、DB を持つのはどこかを `cargo metadata` で辿って検査する |
| `server/crates/core/tests/swallowed.toml` | 製品コードで結果を捨てている箇所が、1件残らず理由つきで載る |

他に、アカウント分離の総当たり・未解明事象がログだけで辿れるかの検査・配布物の顔ぶれ・消す道を実際に走らせる門がある。**「テストを読む」より「台帳を読む」ほうが先である。**

## イシューは メタ.md → 実行レポート.md の順
`MyDocs/ローカルイシュー/` の下は、単独のイシューと、複数をまとめた**イシューグループ**が混在する。

**グループは `メタ.md` から読む。** 1つの設計として解くのか順に片付けるのか、イシューどうしがぶつかるのか、着手の順序に依存があるのかが、そこにだけ書いてある。個別の `要件.md` から読むと、なぜまとめられているのかが分からないまま前提を壊す。

**着手済みかどうかは、機械的に判定できる。**

```bash
find MyDocs/ローカルイシュー -name '実行レポート.md' -not -path '*/クローズ/*'
```

`実行レポート.md` があれば着手済み、無ければ未着手。**例外は無い**（全件で確認済み）。

**いちばん価値があるのは、実行レポートの「実装時に起きた問題と対応」である。** ここに書かれた罠は、多くが後からガイドラインへ書き戻されている。つまり**ガイドラインの各節には、それを書かせた実例がイシュー側に残っている**。規則の理由が分からないときはそちらを引く。

## 約束事の文書は、通読しない
`.claude/docs/guideline.md` は5,000行規模で、**ほぼ全部が実際に踏んだ罠から作られている**。通読向きの構造ではない。

**大見出しが「〜するとき」の形で並んでいるので、これから行う作業の名前でそのまま検索する。** 「配布物を作るとき」「DB を相手にするとき」「画面の見た目を作る・直すとき」のように、探している語がそのまま見出しになっている。

## 読み違えやすいところ

### ファイル名から中身を推測すると外す
名前と責務がずれているファイルが複数ある。**開くまで中身を決めつけない。**

### 同じ機能が2箇所に分かれている組がある
片方だけ読んで「実装されている」と判断すると誤る。**画面から叩く経路と CLI から叩く経路で、通る道が違うことがある**——たとえば保護や確認が片方にしか無い、という形で現れる。設定値の宣言と、それを使う実装が別 crate に分かれている組もある。

「ある機能がどう動くか」を答える前に、**入口が何通りあるかを先に数える**こと。

### 数字だけ拾うと理由を落とす
しきい値・上限・間隔の類は、**コメントに実測の根拠が併記されている**。「なぜこの値か」が横に書いてあるので、数字を動かす前にそこを読む。根拠を読まずに動かすと、その値が守っていたものが分からないまま壊れる。

### 文書は実装より遅れる
`README.md`・理解ドキュメント・優先順位の一覧は、実装より後から直される。**数値や挙動が争点になったときは、実装を正とする。**

ただし**画面の見た目だけは逆**で、`DESIGN.md` が正である。実装がそちらに合っていなければ、実装のほうが間違っている。
