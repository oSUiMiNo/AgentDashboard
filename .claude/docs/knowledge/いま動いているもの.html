先に用語

このプロジェクトを知らないと意味が取れない言葉だけ並べる。以降の説明では必ずこの名前を使い、▽ を付ける。

言葉意味
ローカルモードダッシュボードと「PC 側の一式」が1つのプロセスに同居する動かし方。落とすと、走っている claude も道連れで死ぬ
サーバモード--mode server で起こす動かし方。擬似ターミナルを持たず、ブラウザへの配信だけを受け持つ。落としても、繋がっている PC のセッションは死なない
セッションホストagentdashboard-agent。利用者の機械に常駐し、claude を擬似ターミナル上で動かして、サーバへ報告する
Cloudflare Tunnel待ち受けポートに、インターネットから届く URL を割り当てる仕組み。サーバのポートを1つも開けない——中から Cloudflare へ繋ぎに行き、その道を逆流させる。名前付きトンネルは行き先をドメインに固定したもので、使い捨ての trycloudflare.com と違って URL が変わらない
ソースビルド配布物を取ってこず、リポジトリで make build して出来た実行ファイルを直接起こすこと。リリースを出しても、この動かし方には何も届かない

これはいちばん気づきにくいずれ方である。ヘッダに出る版はサーバに聞いた答えなので古いタブでも新しい版が表示される。「揃っているのに古い」という形になるので、数字ではなく「最後に起こし直したのはいつか」で判断すること。
次に落とすときも、抱えている claude を先に数えること。起こし直すと道連れになり、作業中のセッション自身がその中に居ることがある（今回も居た）。いつ落としてよいかは人にしか決められない。

Windows から 8787 が開かないとき（2026-08-16 に踏んだ）。 症状は ERR_CONNECTION_RESET で、約2.04秒ぴったりで切れる。WSL の中から curl すると 200 が数ミリ秒で返るので、アプリは無罪である。

原因は Windows 側に残っている netsh portproxy（0.0.0.0:8787 → 192.168.147.44:8787。持ち主は svchost.exe の iphlpsvc）。これが 0.0.0.0:8787 を先に掴むのでWSL の localhost 転送が出番を失い、転送先の WSL 側にはダッシュボードが 127.0.0.1 にしか耳を出していないので誰も居ない。2.04秒はその転送が諦めるまでの時間。

切り分け方。 使い捨ての口を別のポートで立てて Windows から叩くと通ってしまうので、ポートを変えずに確かめること（変えると変数が2つ動く。実際にそれで一度読み違えた）。決め手は netstat.exe -ano | grep :8787——Windows 側に LISTENING が居れば、それが横取りしている。

直し方は2つ。 ①WSL 側の bind_addr を 0.0.0.0 にする（管理者権限が要らない。いまはこちら）②netsh interface portproxy delete v4tov4 listenport=8787 listenaddress=0.0.0.0（管理者権限が要る。耳は 127.0.0.1 のままで安全だが、スマホからは開けなくなる）。

①は WSL の IP が変わると、また同じ症状で壊れる。 portproxy の行き先は 192.168.147.44 と数字で焼き込まれているのに、WSL の IP は起こし直すたびに変わる。ずれた瞬間に「2秒でリセット」へ戻るので、WSL を再起動したあとに開けなくなったら、まずここを疑う（hostname -I と portproxy の行き先を突き合わせる）。恒久的に嫌なら②を選ぶ。

スマホから開くには、さらにファイアウォールの受信規則が要る。 宛先は Windows の LAN 側の IP（<LAN の IP>:8787）。この数字を覚えないこと。 DHCP のリースなので、Wi-Fi を変えても、同じ Wi-Fi に繋ぎ直しても変わる（08-28 は 192.168.0.11、08-30 は 192.168.0.12。Wi-Fi の名前は同じままだった）。聞かれたら毎回引き直す——powershell.exe -NoProfile -Command "Get-NetIPAddress -AddressFamily IPv4 | Where-Object { $_.InterfaceAlias -eq 'Wi-Fi' }"

WSL の 192.168.147.44 でも、WSL 仮想アダプタの Windows 側 192.168.144.1 でもない——あの2つはこの PC の中からしか見えないので、別端末に打たせても永久に届かない。PC のブラウザではどちらでも開けてしまうため、「さっきまで開けていたアドレス」をそのまま別端末に渡すと、ここで嵌まる。

受信の既定は NotConfigured＝ブロックなので規則が要る。いまは AgentDashboard という受信規則が入っている（TCP 8787・Allow・有効・プロファイルは Any）。

プロファイルを Any にしてあるのは、Wi-Fi が Public に分類されることがあるためである。Windows は繋いだ Wi-Fi ごとに Private／Public を決めるので、-Profile Private だけの規則だとWi-Fi を変えた瞬間に届かなくなる（分類は Get-NetConnectionProfile で見る。2026-08-28 時点の Wi-Fi は Public）。

ただし鍵はある。 bind_addr を 127.0.0.1 から広げると入口が合言葉（LanPassword）へ切り替わり、合言葉が登録されていなければ起動そのものを拒否する（server-core/src/auth.rs の ensure_lan_password）。素通しで外へ出ることはない。それでも公衆 Wi-Fi では開かないこと——隔てているものが合言葉1つしか無い。

ずらしたままでよいかは、変更の中身で決まる。 0.1.20〜0.1.28 はブラウザへ配る画面だけの修正だったので、サーバを入れ替えた時点で効いていた。0.1.29 は違う——session-host-core を触っているので、セッションホスト▽を起こし直すまで効かない。入れ替えが要るかは版の数字ではなく、どの crate を触ったかで決まる。

同じことは以前も起きている（08-09 に 0.1.11 で揃えるまで、実機だけにログ整備が 入っていた）。版番号で揃っているかを判断できないのは、この構成の性質である。

AWS にログが残るようになったのも 0.1.11 から。それまで箱には logs/ ディレクトリすら無かった。0.1.11 で dashboard-state という 置き場所が付いたので、以後は箱を作り直しても消えない。
ログの置き場所。手元3台は <state_dir>/logs/<種別>-<pid>.<日付>.jsonl へ 1行1レコードの JSON で残す（7日・合計 512 MiB まで。起動時に古いものを掃く）。 端末へ出るぶんは今までどおり RUST_LOG で決まり、出力先は stderr。
  • 実機 … ~/.local/state/agentdashboard-run/logs/
  • trial … ~/agentdashboard-trial/server/logs/
  • セッションホスト▽ … ~/agentdashboard-agent/state/logs/
  • AWS … 箱の中の /var/lib/agentdashboard/logs/（dashboard-state という置き場所。0.1.11 から）
~/agentdashboard-run.log などの run.log は端末のぶんで、これまでどおり残る。

読むときは --state-dir が要る。 agentdashboard logs は設定を読まないので、上の3台のように state_dir を移していると既定では当たらない（「ログの置き場所がまだありません」と出る）。

agentdashboard logs --since 24h --state-dir "$(agentdashboard state-dir)"
agentdashboard-agent logs --since 24h --state-dir ~/agentdashboard-agent/state

セッションホスト▽側に state-dir の口は無いので、 agent.toml の state_dir を直に渡す。生ファイルは今までどおり jq でも読める。

ドメインとトンネル

  • ドメインは underschaft.com（お名前.com で登録。登録はあちらのままで、DNS だけ Cloudflare が預かっている）
  • ダッシュボードは dash.underschaft.com。apex と www は触っていない——お名前.com のレンタルサーバを指したまま
  • メール（MX / SPF / DKIM）もそのまま動く。mail の A は必ず「DNS only」にしておくこと——プロキシを通すと配送が失敗する
  • トンネルの設定はCloudflare 側に置いてある（config_src: cloudflare）。EC2 に設定ファイルは無く、行き先を変えるのは Cloudflare の管理画面か API
  • EC2 の /etc/cloudflared/token が接続用の鍵。これが漏れると誰でもこのトンネルに成り代われる

AWS EC2 について

  • 箱（コンテナ）で動いているので、版のドロップダウンは出ない。「compose.yml の image: を書き換えて」という案内のカードだけが出る。壊れているのではなく、そう作ってある（設計§14）
  • 以下は、立て直したときに再び効く手順である（いまは入口が無い）。更新は SSH で入って3行——compose.yml の image: の版を書き換え、sudo docker compose pull、sudo docker compose up -d
  • AWS 認証も SSH も通らない。 失効ではなくアカウント閉鎖によるもので、aws sts は InvalidClientTokenId、43.207.237.211 の 22番・443番はどちらもタイムアウトする。「認証を入れ直せば入れる」と読まないこと
  • t3.small で概ね4円/時。残す判断を取っているので、勝手に壊さないこと
  • 止めるときは ~/Dev/Test_AgentDashboard で terraform destroy。ただし利用者の明示的な承認が要る

更新の約束

残す基準はひとつ。「次に触る人がこれを知らずに動くと事故るか」。 是なら書き、否なら書かない。ここは「いま」だけを持つ場所で、履歴は積まない。

大きな作業が一区切りついたら見直す

作業の途中経過は流さない。動いている最中の状態を書いても、次に読む人が見る頃には嘘になっている。

したことここへの反映
常駐するものを起こした／起こし直した行を足す・版を書き換える
常駐するものを落としたその行を消す
トンネルを張った／張り替えたURL とその先を対で書く。古い対応は消す
外に何かを立てた／壊した立てたら足す。壊したら消す
ログの出力先や設定の場所を変えたいまの場所へ書き換える

足すより、消すほうを忘れやすい

役目を終えたもの——落としたプロセスの行、壊した環境の項、戻した設定の注記——は、 その場で消すか、いまの姿へ書き換える。「前はこうだった」は残さない。それは各イシューの実行レポートの仕事。

迷ったら分量で気づく。ここが増える一方なら、実行レポートに書くべき粒度が混ざっている合図。 開いて数十秒で現状が掴めなくなった時点で、書きすぎている。

書くのは「何が・どこで・どの版で・どう起こしたか」の4つだけでよい。

なぜ「版」を必ず書くのか。 ソースビルド▽で動かしているものは、リリースを出しても何も変わらない。 更新するには git pull → make build → 画面の「いま入れ替える」（または agentdashboard version restart）が要る。端末で起こし直す行は要らない——その場で自分を新しい実行ファイルへ入れ替えて同じ PID のまま戻ってくる（手元の新しい版をGUIだけで効かせる）。抱えている claude は道連れになる。 「リリースしたのだから最新のはず」という思い込みが、いちばん時間を溶かす。
